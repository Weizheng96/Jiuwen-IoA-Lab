# 成约证据与履约权限

## 问题与决定

原 Client.start 可能先取得定金 checkout 并付款，再发送 work.start，因此成约登记不能以已经开工为前提。首次合法合同 checkout 或开工请求核对原承诺、实际签1/2/3、已选价款与身份，保存冻结原件；控制收件不再按新候选的公示、意向或未选择条件判断。新的付款仍核当前许可及预算。

原 work.start Task 持续承载环节与交付；step.authorize 的 Reply 可引用它，Task.op 仍为 work.start。平台保存实际任务关联及签名环节请求，答复须来自卡载用户，任意内联自签密钥不能获得权限。

合同预览明确全部材料的摘要与发送阶段；开工材料授权不得超出本机真实用户批准。后续存证、付款、结清仍沿原 SDK 和同一业务关系，不新增合同字段或状态机。

## 实施与验证

实现冻结成约权限、原任务/用户环节归属、分轮生产与材料预览，扩展原市场存证、付款及原子结清。助手验收调用原 Client.accept；丢失实际付款回执时用独立确定性控制消费原凭证、补原通知，不重签7或发起另一笔付款。

正常履约及付款回执丢失两种情况分别覆盖提案与待批准，另验证错误交付拒绝，共5项通过；新候选资格失效、任意用户自签、缺实际付款结清及重复付款查询一并核验。内容验收运行真实 WASM，宿主与用户由显式测试驱动。联合付款原子性/原投递检查19项曾通过。

首轮原 WASM 检查发现旧报价夹具返回值不能被原 WASM 执行，改为原 status 格式；内容检查再按原 Context.files 接口读取实际文件，未放宽验收器。原版九问完整生产、原生网页、进一步故障矩阵与新版影片仍待完成，产品依据不提前升级。

原版九问复验的第一次提案遇到原生问题，测试没有自动回答未知业务问题。公开事件表明报价参数正确，但附有宿主 call_goal 元数据，在进入业务回调前被原宿主 Schema 拒绝。本仓适配层单独接纳并分离该元数据，保留显式同名业务字段和原 Schema，不修改九问源码/全局指令。3项适配边界检查通过；真实九问两种成约重新通过，共2项、82.16秒，证据仍仅证明成约。

第一次完整回归为336项通过、1项失败、5项跳过，530.64秒。失败发生在付款已恢复和结清之后的新查询：扫描线程与回执任务可能重复收敛，留下控制任务 unknown。收敛集中于同一所有者后，两种丢回执用例通过；加入结果已保存而任务未收敛时的并发屏障，2项再次通过，37.96秒。

第二次完整回归为337项通过、1项失败、5项跳过，513.90秒。旧保留期测试在活动 WS 上将同一时钟推进90天，连接租约因此按设计失效；改为断线后推进清理时间、恢复时钟并重新认证，继续核对原承诺、UUID与消息，未放宽租约或业务校验。保留期及两种丢回执联合3项通过，37.81秒。最终完整测试338项通过、5项默认模型跳过，511.90秒；两条既有 Windows 私有临时目录清理告警保留记录。版本、57份文档、仓库自检与构建检查均通过。
