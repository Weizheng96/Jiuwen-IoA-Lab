# 助手通信与宿主确认

## 问题与决定

将共用运行时接入真实角色前，补齐宿主轮次、规则版本、会话及确认的可执行契约。原版九问公开 SDK 的交互回答必须回到同一进程；普通模型问题与 SDK 受保护动作的用户批准不能混为一体。

SDK 负责确认对象、不可变规则和可靠投递；可选九问适配负责公开进程接口及会话关联。规则起草与模型业务工具由其所属模块负责，运行时和适配器不出现会议或美甲分支。用户可通过本机受控页面批准 SDK 动作，脚本不取得批准入口的访问凭据，confirmed 布尔值不具有效力。

## 实测诊断与边界

真实模型首次测试在一个请求内尝试了建议值；工具参数摘要与原回执证明原因是测试收信规则未明确接收方的调整范围。补充规则要求保留本次输入、冲突只返回建议、等待发送方新请求，同时统一工具输出与接口字段约定；通用 SDK 和宿主不加入业务场景分支。之后真实 HTTP/WS 与原版九问两轮成功，沿用一个交互 UUID 和实际 Session，证据见[助手通信实测](../../deploy/verification/assistant-messaging.json)。

原生 ask_user 也通过真实模型、原子进程回调及本机浏览器答复实测，回答前无工具效果；证据见[原生问题](../../deploy/verification/assistant-native-question.json)。这是测试驱动的用户通道验证，不声称真实人或九问原生网页已验收。

定向测试另外覆盖受控用户确认、发布响应丢失/本地映射失败、重复发送、关闭、未知工具效果、最终回复回调丢失、原生问题等待和模型名额竞争。桩、真实模型与安装资源验证分别表达各自范围。

本轮不宣称旧产品技能、委托/服务方角色、官方日程邮件、原生网页可见性或四个新视频完成。产物 VERSION 继续保留实际旧依据；SDK 主流程切换和完整部署仍需后续交付。
