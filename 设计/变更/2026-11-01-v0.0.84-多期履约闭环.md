# 多期履约闭环

## 问题与决定

现有旧版两期测试只覆盖旧工作流，不能证明常驻SDK完整履约。沿原A2C期次、签名、任务及AP2推进，不另建分期状态机；把逐期确认、真实付款、容量和重启文件保留一起验证。

| 归属 | 职责 |
|---|---|
| A2C | 原模板期次、签名链、应付金额、验收与付款依据 |
| 个人助手端 | 每期真实确认、原操作和原文件；区分部分验收/付款与整单结束 |
| 服务方端 | 前期实际应付款齐备后继续原Session；当前期的环节及生产分别核对 |
| 平台 | 原合同归属、付款事务、结清和容量原子释放；不替参与方执行生产 |
| 安装元数据 | 本轮干净并发安装暴露未知元数据；读快照与文件替换共用短锁，仍核完整内容；实际损坏不自动修复，测试失败保留原目录和任务 |

不增加合同字段，不修改用户九问。解除接口仍是独立待实现项，不把两期成功当作解除或完整原生接入已完成。

## 验证

多期复测暴露第二期文件HTTP读取中断被误归为业务未知：只有原本地记录证明本期未签6且未缓存时，返回已知读取失败；重传原操作返回原失败，在原取件请求内可新建读取操作重试。已有签6的中断仍依据原回执恢复，不重签。

最终安装验收又暴露元数据读句柄与原子替换的Windows竞争。真实句柄测试可稳定产生PermissionError；改为共用短期元数据锁，不持锁等待pip。仍拒绝损坏元数据，异常只附类型不泄露配置。旧检查工具会在失败退出时清理仍运行的安装目录，现保留失败现场；成功清理目标须核实为本次临时目录。
