## 逻辑问题与统一解决

| 问题 | 统一规则及归属 | 验证入口 |
|---|---|---|
| 接收端生成 UUID，发起端如何继续 | 本地映射和 opened 回执同事务；平台核原始双方并登记；发起 SDK 自动补齐、后续自动带 ID | 消息中心、运行时；M03/M03a |
| 建立回执丢失 | 同源重投或按本端身份及起始消息补查；不得创建第二 UUID | M03a |
| 还未建 UUID 就被拒绝 | 以原消息返回终态错误，允许无 UUID；退出 awaiting_open | M03b |
| 同源不同 UUID 或关闭/建立竞争 | 平台唯一约束与原子开关，迟到 opened 不重开 | M03b/M03c |
| 平台与本地按不同作用域去重 | messageId统一为全局UUID，平台强制唯一且核原发送者；跨发送者同ID拒绝，不让本地合并两条合法消息 | T07a |
| 建立、送达、接单、完成混淆 | 分离消息投递、开始许可、本地执行、容量承诺和 A2C 证据的权威 | T02/D02/M03c |
| 多候选与原生会话竞争 | 接收端独立会话；发起会话可关联多个子交互，实际同 Session 串行 | M04/M08 |
| TTL 被当合同期限或签名新鲜度 | 长期离线仅保存意向；协议校验独立，过期不代签 | T03/T04 |
| 开始执行与过期/撤权竞争 | 平台 request.start 原子准入；本地保存实际执行，撤权不伪称追回既成效果 | M02/M03c |
| 关闭后迟到结果被丢弃 | 关闭仅阻止新请求，已受理请求的结果凭 inReplyTo 返回；不重开 | M09 |
| 普通保留期清掉活跃合同关联 | 活跃交互、请求关系与 admission 按业务生命周期保留 | T03/D06 |
| 拟卡费先付、容量后查 | 服务方 SDK 决策，平台权威 admission；可靠回传预留后才进入 AP2，事务协调 | D02/D03 |
| 本地和平台各算容量 | 平台仅一份权威计数，本地保存镜像与恢复依据 | D02/D06 |
| 有效提案被提前释放 | 按上游签署与开工窗口保留；未中选不代表撤销 | D04 |
| 已付拟卡费但没有承诺 | 明确失败后关闭原入口、核实无在途效果再释放；保留费用凭证，不自动退费 | D06 |
| 等用户阻塞全部模型线程 | 业务检查点持久化；接单容量与执行并发分开；原生 ASK 不假回答 | D05/M08 |
| 同账号重连重复赠币 | 密码登录操作幂等；连接刷新和自动重连不走新登录赠币 | T08 |
| 用户手写格式门槛过高 | 九问自然语言起草收信规则，SDK检查/预览，用户确认发布；工具能力缺失不虚构 | M01/M01a |
| 规则正文与公开接口混淆 | 本地收信规则包含处理步骤；公开收信接口仅声明格式/说明，权限不泄露全名单 | M01/M02 |
| 发布 ACK 丢失或更新覆盖 | 稳定发布操作、不可变本地版本、平台修订与摘要、乐观并发检查 | M01a |
| 新交互仍选择旧接口 | 新交互只接受当前启用修订；既有交互保留原修订并复核权限 | M02 |
| 系统失败不符合业务输出 Schema | 标准结果封套区分 outcome/error 和正常 output | M06 |
| 邮件受理冒充已入历 | 本地预留、邀请提交和真实接受分别记录 | M05/M06 |

方案没有增加通用工作流引擎、消息中间件或独立微服务；新增关系、投递和容量记录分别由既有消息中心、委托中心及本地运行时承担，避免双权威状态。

依赖核实：A2C `request_digest` 排除 signature，`sign_request` 仅附签名，因此预留与拟卡费绑定未签请求摘要、随后签署同一请求不会改变摘要。签名前仍需核时效和内容未变，不能用另一请求替换。

## 术语决定

交互方式只保留“委托交易”和“助手通信”；用户配置称“收信规则”，对外声明称“收信接口”，格式称“接收格式/回复格式”。代码字段在术语表映射，标识由 SDK 管理，不要求模型手抄。原历史中的“定向交流/私人交互”只按当时记录理解，不作为现行并列术语。
