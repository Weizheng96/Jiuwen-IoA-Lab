# 案件输入与复核入口

## 实施前的整体审查

原案件恢复与Core所有权之后，继续核对真正人工可操作的闭环：只有review提交入口而没有列表/本案读取，管理员无法发现并复核；按期次任意开案会与一份裁定终止整张卡矛盾；读到他人文件不代表可以再转授原fileId；Core重启后相同逻辑模型ID可能映射到其他部署模型。以上均需在开发前明确，而非通过隐藏分支补齐。

## 选择与职责

| 方面 | 选择 |
|---|---|
| 案件唯一性 | 原admission只有一份终止型案件，改理由/发起人也不另建；操作仍严格校验原指纹 |
| 材料 | 受理冻结有权上传的分组引用和实际摘要；原签4交付集合精确匹配，不建立追加材料/反复复算引擎 |
| 人工 | 网页管理员有明确列表、所属案件读取及本案材料下载，再复核或明确重评；非当事身份每次重核，不继承消息审计权限 |
| 模型 | 保存原逻辑模型集合及非凭据登记映射摘要；原资源变化先核实，不默换模型或公开密钥 |
| 历史文书 | 按原市场和原签署时点验签，不能复用实时信誉查询的新鲜度窗口而让离线用户的历史裁定失效 |
| 资金/执行 | 沿用现行实际writer/协议Task收敛、原应付款齐全再释放关闭的联合条件；不新增自动裁定付款或新合同字段 |

实际已安装Core/SDK隔离复测中，原预览确认未到开工期限；旧HTTP仲裁入口却在没有交付期次时于api_v1.py的periods索引返回500。原实验关于提前归责的假设未到达，保留原失败记录，只确认无交付500缺陷；新入口需基于原admission/证据进行理由校验，不能复用该raw-card路径。

规范分别归委托中心、平台接口、个人助手SDK、共用恢复、管理员界面及验收；本记录不是案件实现证明。旧HTTP及市场仲裁在新闭环和调用整体切换前保留覆盖，不作为新SDK入口。远端发布限制仍未解除。

## 原申请受理阶段

新增委托中心所属案件存储，接入真实WS arbitration.request、原操作恢复、按caseRef/原admission的双方查询，以及独立网页管理员的列表、本案依据和材料读取。材料保持原上传身份与实际摘要，交付集合核原签4；角色和连接在最终事务重核。各模块经所属接口协作，未调用旧raw-card仲裁或新建参与方运行时。

新增4项案件用例与原证据、公开请求生命周期共享回归共22项通过；补齐拟卡费0/1且无合同卡的请求后，新案件文件6项通过。全部使用真实HTTP/WS/A2C/AP2和明确宿主/用户动作测试替身，无真实模型或邮件。设计、文档、diff空白及全仓自检通过。随后执行当前完整回归，不能用此前Core快照替代本次案件代码证明。

本阶段只产生queued或needs_review的原受理记录；不产生裁定、付款或容量释放。评估/复核、原终局事务、通知、SDK门禁与实际收尾以及案件工作台交互仍待开发，旧入口仍待覆盖和调用整体替换后归档。未升产物依据，未提交、打标签或推送。
