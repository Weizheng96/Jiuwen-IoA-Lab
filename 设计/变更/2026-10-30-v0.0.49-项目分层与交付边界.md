# 项目分层与交付边界

## 用户确认

用户要求将项目本身分层，而非只整理设计文件；提出将平台、SDK/技能、九问、官方服务归入 src，并让各 Demo 集中剧本、代码与视频。评审提案已确认，本次将其写入正式设计，代码迁移随后依据设计分阶段进行。

## 采用的结构

| 决定 | 原因与结果 |
|---|---|
| `src/platform`、`src/access`、`src/hosts/jiuwen`、`src/official` | 按平台、通用接入、宿主适配、业务资源分责；平台仍为模块化单体 |
| 三个 Python 发行包及官方资源包 | 保留 ioalab、ioalab-sdk，独立可选 ioalab-jiuwen；官方配置与工具不另建执行框架 |
| 一个 SDK、两个角色、共用运行时 | 身份、连接、收发、持久化与恢复只实现一次；技能及 CLI 经本机认证 IPC 调用 |
| 九问本体放 vendor | 本仓只维护公开适配与扩展，不修改原版；Git 源码依赖仍随仓固定 |
| 官方业务工具与 SDK 分开 | 日程、邮件及预约回执留在业务工具；通用 SDK 不硬编码会议或美甲场景 |
| 三个 Demo 分场景聚合 | 每场景有源、生成剧本、正式素材、视频、证据和版本；公共制作工具共用 |
| 正式实验与 temp 分开 | 可复现验证入库；临时调查、草案、一次性脚本忽略；持久数据不按临时文件清理 |
| 设计与实际实现分别记录 | 架构写最终规范；开发计划保留旧新映射与实施门槛，实际使用命令暂保留现有路径 |

## 核查发现与迁移约束

- 现有 platform.py 混组装及业务协调，market 同含 A2X/A2C，身份实现放在支付目录；新结构按领域归属和跨中心用例拆开。
- 现有参与方仍有 HTTP 轮询及公网服务端点；管理员观察 WS 不等于统一参与方长连接。统一运行时、容量预留和支付原子性属于后续行为重构，不能只靠改目录完成。
- 官方服务读取及平台种子初始化依赖相邻源码目录；改为显式配置输入、安装资源定位和经 SDK 登记发布。
- 公共录制与配音工具存在相邻 A2C 主仓依赖；后续需随仓收录来源，保持独立复现。默认官方服务仍使用的美甲资产不能与固定 Demo 剧情一起移走。
- 现有根包版本直接读取设计 VERSION；后续发行包应使用自己的实现依据。旧产物不随设计统一升级。

结构审阅补齐了宿主能力探测、真实用户答复可信关联、业务工具与运行时共享稳定操作键、技能/示例版本归属。保留既有 UUID、A2C、AP2 和业务成功判定规则，不引入新的协议字段或状态机。

## 本次交付范围

更新架构、术语、相关接入/部署/验收/示例规范，维护索引、开发计划及实际入口说明；为 temp 添加仓库忽略规则。design 技能仅增加一条项目结构审查经验，沿用已有检查脚本。

没有搬迁业务代码、调整依赖安装包、修改业务产物 VERSION、重制视频或触发真实邮件与付费业务。维护检查继续针对现有产物路径；实际迁移时需同步构建与检查入口。
