# 常驻协议执行与提案签认

## 问题与决定

原协议投递必须接入常驻 SDK，不能让模型自行拼装签名、轮询或操作私有数据库。两端复用原 Client/Provider；每个交互有独立协议存储、原任务及宿主会话，业务报价与审查仍由参与方九问执行。

正式提案经服务方当前连接申请市场签3；平台核原已开始的签名请求、接单记录、卡与请求不变量，先在事务外核包与准备签认，再在短事务内复核当前执行代次并保存签认原件、业务绑定及操作回执。原报文不新增字段。

## 实施与验证

常驻两端已装配原 Client/Provider 与 AP2；每交互独立协议存储和原任务，控制预检与模型执行分开。服务方实际接单、零费/付费提案、市场签3及未知结果恢复已贯通。等待中的业务不占尽控制线程，已接取任务的控制进展不受新任务队列上限阻塞。

报价 Schema 根据实际模板交付件生成，明确三类验收器为可选种类；本单保存决定前核验真实包种类和摘要。真实九问失败轮次曾把同一脚本包误填到三类，后又缺交付件映射；通过公开工具事件定位，修正通用 Schema 和说明后原版九问通过，未修改九问源码或全局指令。误填包类型的回归验证在同一模型轮次内纠正，不重复收费。

原任务与单次回复的同名附件分别传递并验摘要；文件读取权与原结果事务一致。针对数据库提交失败、签认准备后执行代次接管、响应丢失及双端重启的检查保留原签名、费用、交互和会话，不重做业务。

完整回归312项通过、3项需显式模型配置的测试跳过，耗时357.78秒；另有2项既有 Windows 私有测试目录清理警告。真实模型结果见[常驻提案实测](../../deploy/verification/resident-proposal.json)，本轮原版九问独立测试通过。其用户确认由隔离测试驱动，不能证明原生网页、生产交付或影片完成；产物依据不提前升级。
