# 接单策略与暂停恢复

## 依据与决定

原生入驻中，模型说“先不接受委托”，但本地accepting仍为true。现有SDK既未实现设计中的pause/resume，又会在新意向及公示刷新时写回启动配置；平台对held的提交也再次检查开关，与只暂停新单的边界冲突。

| 问题 | 统一决定 |
|---|---|
| 实际开关归谁 | 平台admission策略；本地配置是输入，上次应用快照只用于识别哪些字段被明确修改 |
| 用户说暂不接单 | 产品技能调用provider.pause，核实际回执；可先暂停再公示，不靠自然语言或杀进程代替 |
| 重启/重连/重公示 | 同配置不重新应用默认开关；容量变化只改容量，明确改变accepting或resume才重新开启 |
| 既有预留 | 暂停拒绝新的预留；原有效held继续按期限、当前连接和原授权提交，committed/合同控制不受影响 |
| 写入结果未知 | 一个profile的策略写入串行，原请求先存、原WS操作恢复，终局前不越过；原回执与当前状态分开 |
| 本地检查点 | 待处理请求单独持久保存，终局回执、配置快照及待处理移除同事务；不另建业务状态机或兼容分支 |

SDK只复用admission.configure/status，不修改A2C合同或金额规则。凭据入口、业务验收与完整原生发布仍为独立缺口，本轮不提前认可。

## 验证范围

| 范围 | 实测结果 |
|---|---|
| 完整检查 | 494 passed, 13 skipped, 1 warning in 853.71s；设计、文档及仓库自检通过；一项既有临时目录清理警告保留 |
| 关键规则 | 公示前暂停、未就绪恢复拒绝、原回执/当前状态分列、重启/公示保持暂停、单字段配置、并发、原操作未知恢复及检查点事务通过 |
| 跨端业务 | 暂停的新意向返回service_paused，未收费/未调模型；原有效held仍可过账提交，既有合同在暂停后仍完成原授权、WASM、付款及结清 |
| 安装 | 两ZIP干净安装及原合同接管通过，27.10秒；实际原生导入17个文件逐字节匹配 |
| 原生九问 | 普通自然语言请求后实际调用pause，已安装公开脚本复核accepting=false、容量2、占用0；重传原操作修订号仍为1，原九问配置及稳定身份不变 |
| 边界 | 首次安装中模型出现超时重试、状态参数错误，随后自行恢复；不能当作完整接入体验验收。暂停不撤销公示，模型相关表述不作证据；私密凭据、完整原生公示/生产、Linux及新影片仍未验收 |

本轮还发现暂停原被泛化为not_ready，使委托方保持unknown；已统一为service_paused，沿现有拒绝路径正确终结，未增加兼容分支。证据见[接单策略报告](../../deploy/verification/admission-policy.json)和[原生暂停画面](../../docs/progress/native-provider-paused.png)。
