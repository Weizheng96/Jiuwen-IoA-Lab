# 候选与信誉依据

## 原因与取舍

现行设计有compare，新SDK尚无该公开入口；inspect没有返回实际信誉，技能依靠逐个报价状态自行整理。统一比较负责取得真实条款及依据，不替九问作业务判断或预选服务。首次合同确认与比较共用原件核验，补齐原签名请求关联，避免两套规则。

## 统一边界

| 问题 | 处理 |
|---|---|
| 是否新建分析引擎 | 复用现有非模型作业与operations.get，不增比较服务或独立状态机 |
| 如何判断验收充分 | 提供真实固定包、可审阅程序和notCovered；摘要、条目数和程序展示完整均不等于业务覆盖充分，九问依据用户需求解释 |
| 是否强制三家 | 不将演示最低数量固化为权限；此前用户要求先核模板和多选能力。旧链路1—8策略不迁入新通用流程，用户数量偏好作为业务要求执行 |
| 如何提交信誉 | 既有SDK按真实证据自动Provider.close；公开只读查询实际签名信誉，不新造重复提交或评分接口 |
| 公开操作与任务工具 | SDK启动前命令、常驻RPC、固定上下文及本单宿主工具分开；去掉文档中未存在且不需要的通用确认申请/inspect别名 |

## 规则归属与验证
