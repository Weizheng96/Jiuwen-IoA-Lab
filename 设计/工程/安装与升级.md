# 安装与升级

## 目的与范围

职责：定义Linux受管部署和Windows可信本机体验的私有输入、目录所有权、启动停止、升级与失败恢复。发行、依赖、环境、进程及数据锁边界均由本页定义；业务实例见[官方实例](官方实例.md)，人类逐步操作只见[部署教程](部署.md)。普通用户已有九问不由本安装器接管。

## 重部署与保留

可选trial安装项只保存受限config文件和已安装controller_python的绝对引用，试用origin、模型代理secret、席位和控制状态仍归原试用配置；缺省不安装/启用该可选应用。Linux按真实venv安装身份核解释器链接，不把合法venv链接当作任意源码入口。试用公开停止核验须检查真实所属容器退出状态，历史回执不能替代当前资源核验。

部署管理层是本部署进程生命周期的唯一owner。平台核心、官方协调器、管理员宿主/SDK和可选试用协调器保持独立运行；试用协调器通过原持久owner记录管理席位、模型代理和转发器。核心不创建业务参与方或反向导入试用应用，外部参与方不属于部署停止范围。

Linux提供同一部署的公开start/stop/status和受管服务组；服务依赖不仅表达启动顺序，还须在核心退出时触发依赖组件收敛。正常stop先关闭准入与新任务，沿原SDK排空，再停止所属宿主和试用资源，最后核心；状态须分别报告停止请求、实际控制组为空和执行锁释放。核心异常退出暂停新准入并触发受管组件收敛，保留未知操作，不将失联认定为成功或静默启动混合版本；恢复须先核原所属写入者和锁。

本轮采用清退旧部署后全新安装，不提供bootstrap-upgrade专用恢复入口。旧运行数据、配置、凭据和失败证据归档保留，新部署独立初始化；已完成安装的一般升级能力仍按本页既有规则维护。旧进程无法正常退出时，先固定归属、业务与备份证据，再由部署者明确批准的受限维护处置清退，不能把异常终止当作正常排空通过。

Windows和Linux每次部署均先通过原部署所属的公开停止入口清理此前运行进程，核全部写入者、Windows Job或Linux控制组已空，以及真实OS/SDK锁已释放，再构建和安装受审候选。首次新装核专用路径无未知归属进程。不得尝试保持旧进程运行来升级；部署流程负责归属核验，不要求普通操作者手工审PID。

清理仅指本部署进程，不删除原账号、数据、密钥、模型、工作区、人工设置或操作回执。原状态未知、所属句柄丢失或锁未释放时拒绝启动第二写入者，保留现场；异常恢复按需处理，不以删状态、强杀通用进程名或换根伪装正常部署。受审备份、环境激活及既有配置显式迁移仍复用下述同一安装链。

## Windows可信本机体验

复用windows-x86_64受审内容发行和现有独立环境安装器，核core、participant、swarm实际身份、依赖锁及原版依赖摘要；开发venv或同名版本不能代替此核验。最低环境及业务边界见本页交付单元，实际步骤只在[部署教程](部署.md)维护。

本机装配归deploy.windows_local，只调用现有发行、环境、SDK及原版公开入口，不承载业务状态或轮次销毁。

启动装配读取明确的本机私有输入，核原部署标识、持久目录及端口归属后，依序启动核心、原版公开Web/Process入口及所属SDK。程序只接管自己创建并能核PID、创建时间、运行身份和安装来源的进程；不按通用进程名杀进程，不占用或停止未知现有服务。组件使用各自持久工作目录及明确回环地址；端口冲突或依赖缺失明确失败，不自动漂移、不改原版源码或宿主全局配置。已有工作区、模型配置、身份及业务状态复用原所属配置，不反复初始化、登录赠币或重放授权。

停止先经原SDK的runtime.stop及bootId核对请求排空，保留原操作、合同、付款与未知结果，再通过经核实的原版公开关闭入口及本启动器确证所属的Windows进程控制处理网页、Front与Worker。分别核全部所属写入者和真实OS锁释放，才能报告已停止；仅父PID退出不代表Worker结束。Popen.terminate/TerminateProcess或强制终止不作为正常停机证据；公开关闭未支持、归属不明或仍有执行时报告未完成并保留数据，不补调用私有关闭函数伪装支持。

本机关闭、重启及升级均不执行trial reset、轮次销毁或清空历史。身份私钥、确认、会话、合同原件、账本、取件、操作恢复记录、人工配置与日志保留在原持久目录；再次启动沿原引用恢复，不创建试用身份来替代用户账号。升级候选沿同一发行校验，先排空和备份再切换，未核释放或新实例可能已有业务时不原地覆盖或自动回退数据。Windows正常关闭及真实业务需分别实测，静态适配声明不代表通过。

## Linux受管入口与前置条件

以下各节定义Linux受管安装；Windows启动装配遵守上节，并复用其中的发行校验及组件公开契约，不引入systemd依赖。

| 入口 | 行为 |
|---|---|
| deploy/install.sh --config <JSON> | 从显式本地源码准备发行、三个运行环境及官方实例，启动后核验实际就绪 |
| deploy/upgrade.sh --config <同一初始JSON> | 从已同步的本地源码生成候选，排空、备份、切换及核验；不执行Git更新 |
| python -m deploy status --state <目录> | 读取本部署及服务的真实状态，不安装、启动或修改业务 |
| python -m deploy repair-bootstrap --state <原状态根> --operation <失败安装操作> | 在下述首次启动控制器修复边界内复用原候选，提交关联原失败操作的修复任务 |
| python -m deploy bootstrap-upgrade --state <原状态根> --operation <失败安装操作> | 按下述未完成初装升级准入，从已同步的新来源构建真实新候选，显式导入原配置并续接首次bootstrap |

以下受管安装默认运行根为/opt/ioalab-runtime，状态根为/var/lib/ioalab，配置根为/etc/ioalab；可用--root、--state、--config-dir显式选择。三根与源码目录互不嵌套。入口使用CPython3.11、systemd及统一cgroup v2，Linux首批目标为x86_64；Windows本机入口按上节独立装配进程，不能冒充systemd部署成功。

部署者预先同步完整本仓，可通过GitCode或目录复制；安装器不拉取Git、不使用子模块，也不复制整棵开发工作区。普通包走配置的HTTPS镜像，构建只用固定的独立build环境，运行不使用根requirements或editable包。源码、构建、发行、运行环境与持久状态分别定位。

## 安装任务与模块边界

安装/升级由本部署记录的独立systemd临时service执行；前台命令只提交或观察原任务，SSH断开或观察结束不终止安装，也不启动第二写入者。原操作保存输入/源码摘要、单位及实际控制组；同一操作仍在执行时只查询。进程状态未知、原控制组仍有活进程或部署OS锁不可取得时禁止重启安装；实际终止且组已空后才允许继续原阶段。失败保留原环境、操作和日志，不通过清理状态制造新任务。

| 模块 | 唯一职责 |
|---|---|
| deploy.__main__ | 命令解析、发起/观察原任务及脱敏状态 |
| deploy.installation | 固定安装/升级阶段及原操作记录；未完成初装升级仍复用既有构建、备份、激活及bootstrap，不另建安装引擎 |
| deploy.jobs | 本部署安装临时service的发起、原任务观察、准入和不可变父子请求关联 |
| deploy.migrate_configuration | 受审旧输入的显式一次性导入和原件归档，只生成唯一平台JSON，不承担SDK登录或业务状态迁移 |
| deploy.linux | 系统账号、角色目录/配置权限、systemd状态及内核控制组的窄操作 |
| deploy.units | 从已安装包入口确定性生成业务单位，不运行协议或访问业务库 |
| deploy.configs | 首次配置及生成凭据；已完成后保留人工运行设置 |
| deploy.backup | 原写入者释放后的一致性备份及校验，不自动回退业务数据 |

状态只保存部署事实，不复制SDK调度、确认或A2C合同状态机。任务完成状态与实际进程组已空分别检查；日志、PID和状态JSON不能替代执行所有权证明。

## 安装输入与平台配置

安装输入保留运行根、状态根、配置根、包镜像与所选官方组件等部署意图；以platform_config字段引用唯一的[平台配置文件](平台配置.md)。平台地址、监听、模型、管理员和发币/认证参数不在安装输入或core.env再次定义。先验证同一文件及所有权，再使用组件公开接口装配；安装记录保存引用与原部署身份，不因一次合法动态修订便重放初始化或拒绝同一部署。

新部署采用[平台配置](平台配置.md)的默认管理凭据；已配置密码、模型和其他人工设置保留。已有环境变量/core.env部署须显式一次性导入受审新文件并切换启动引用，再移除旧执行入口；不自动猜测或运行两套参数源。迁移保存原文件与业务数据，不改账号、密钥、合同、付款及未知操作，不补造初始赠币。正式切换前验证同一配置与原公共URL，禁止改址伪装重装。

官方资源及管理员助手的持久工作区、通知、收信、原授权和模型设置仍属其组件，不因平台动态改限流/发币而重建；部署更新须显式处理其自有配置，不能把主平台文件变成跨参与方配置后门。

## 目录与权限

| 位置 | 所有者与内容 |
|---|---|
| 运行根 | root管理的builder、内容发行、不可变envs及环境集合；服务只读安装包，不读取源码 |
| 状态根/.deployment | root私有的部署标识、初始输入、凭据、原操作、服务/路径归属及备份索引 |
| 状态根/core、cache/core | ioalab-core拥有的核心数据库、机构密钥、日志与独立缓存 |
| 状态根/agents、cache/agents | ioalab-agents拥有的官方SDK、九问工作区、用户接口、预约/通知回执及独立缓存 |
| 配置根/core | 核心账号独占的配置叶目录及唯一平台JSON，文件与临时文件受限且支持原子热写；上级配置根仍root管理，不授予agents或其他用户读取，不保留core.env执行链 |
| 配置根/agents | 各角色自己的环境与配置；服务协调器不接收管理员或助手通知凭据 |
| 状态根/backups | root私有一致性备份；不包含运行环境、发行物及可重建缓存 |

Linux受管部署的核心与参与方必须使用不同系统账号。不可变运行前缀及其非敏感安装元数据由root拥有，允许服务账号读取/执行且不可写；不能依赖调用者umask。部署私有记录、构建日志及含凭据配置不因此公开。公共父目录只允许必要的遍历，敏感叶目录及文件按所属方限制访问；不能通过把整个状态树交给agents来解决权限。初次工作区准备后只移交所属状态叶目录；后续公开九问查询以所属服务账号执行，不能在agents工作区生成root所有的数据库或配置。系统账号、三根和单位文件的归属在首次建立时记录；未知旧目录、冲突的账号用途、越界链接或非本部署单位拒绝接管。不提供旧布局兼容、空数据规避或自动删除。

## 初始化与启动

1. 先以排他创建的归属标识认领明确的新目录，再持有本部署实际OS锁；部分认领只继续同一标识，竞争不得覆盖对方。原所有者和完成证据存在时复用，不因PID/状态文件存在便认定完成。
2. 准备固定build环境、内容发行及core/participant/swarm环境，核各单元完整身份与真实导入；放行非敏感安装资源后，以core/agents的真实服务身份再次执行导入与安装身份检查，确认父路径可遍历，不改运行根之外的目录权限。失败保留原日志；未知安装不自动重建。
3. 生成首次核心、官方服务和管理员助手配置；通过原版公开接口初始化两个独立的官方/管理员九问工作区。已有完整配置与工作区只核归属，不重放模板。受管SDK启动前以自身账号调用同一显式登录入口，先复用有效缓存或恢复原登录，再处理确实失效的凭据；不删除账号库、身份或未知操作，也不以反复启动赠币规避错误。
4. 生成已安装包入口的systemd单位；启核心并核实际公共入口；内部账号和分类由显式种子输入初始化，SDK自己创建参与方密钥。
5. 按官方实例的prepare/authorize流程设置受审服务资产声明的必要账号与服务；只有短期初始授权进程取得管理员凭据，正常serve不继承，不在安装器另维护业务数量。
6. 在管理员网页进程启动前，准备ISC_001业务助手的原生通知扩展和固定预设，再移交所属状态目录。升级复用原准备回执及人工设置，不重装扩展或重新授权。
7. 启管理员原版AgentServer、Gateway和预构建网页，再以同一九问适配/SDK入口运行助手；使用原版模块及明确回环端口，不使用自动漂移端口或强杀子进程的外层启动器，不现场npm构建；通过原版JIUWENSWARM_CLI_PORTS=1保留注入端口，不被工作区.env中的旧端口覆盖。分别报告SDK连接、宿主、公示/索引、接口及通知能力；缺邮件时明确禁用会议预约，不能伪称邀请可用。

正常服务只调用安装包。原版网页与官方生产使用不同工作区；网页访问地址携带本部署固定的原生user_id，通知与网页归属一致。管理员网页只开放回环访问，部署者可通过受控本机或SSH通道使用；公开运维入口在相应后续设计中定义。

## 激活与升级

环境集合在envs/sets/<集合摘要>中引用三个已核验真实环境；集合摘要覆盖发行摘要和各实际安装身份/路径，不能只以发行摘要假定不同Python补丁环境相同。环境目标留在环境根内；集合另含release链接，固定原发行及其种子/接入包，目标仅能是本部署运行根releases中的原目录。服务通过current/release读取发行资源，不复制可漂移资源或为升级改写人工配置。current只指向一个完整集合，以一次符号链接替换激活，不能逐个切换造成混合环境。稳定命令与工作区路径不因包更新变化；SDK仍按真实安装前缀及完整身份核对。原版Python可以链接到系统解释器，环境前缀按bin/Scripts的父目录定位；不能沿二进制链接误读系统目录。

| 阶段 | 前提、结果与失败规则 |
|---|---|
| 候选 | 原所属进程已停止且写入者/锁已释放后，核本地输入、构建并安装受审候选，不原地修补旧环境 |
| 排空 | 停官方协调器和管理员SDK，使用原实例的停止入口/实际执行锁核释放；再停原版网页服务及核心。SDK独立serve将SIGTERM映射为同一排空意图；参与方SDK及核心使用mixed模式，管理员原版九问使用control-group模式向其Front/Worker发送SIGTERM（原版Front停止只断开Worker，不终结Worker）；全部禁用最终SIGKILL且不设置强制停止期限；原控制组cgroup.events的populated必须为0，且SDK实际执行锁可取得；残留执行或观察超时阻止备份/切换 |
| 备份 | 在写入者已释放后备份核心、参与方、九问工作区、配置及原操作；保存校验摘要及旧集合引用，含未知付款/通知等证据 |
| 切换 | 核对候选、旧集合及原升级记录，单次替换current，更新本部署单位；不改身份、合同、会话、接单开关或规则 |
| 重启 | 分别保存实际运行状态与开机启用设置；只恢复升级前实际运行的本部署单元，保持原开机设置，手动停止的单元不被重新启动；已有官方准备/授权和管理员预设复用，不重新赠币、公示授权或启用已撤销内容 |
| 中断与失败 | 原操作先保存再执行；重复命令查询实际阶段并继续原候选，不并发启动第二写入者。保留失败现场、旧环境及备份；不在新实例可能已有业务后自动回退数据或重放未知效果 |

升级不代表合同结清。无法安全接管的配置/业务变化先由所属方处理原合同；不新增通用兼容执行器。回退须先停止当前执行并核对新发生业务、原件和备份，不能只换旧代码便声称数据已恢复。

## 初次启动的控制器修复

原安装尚未完成且原操作已确证停止、失败阶段为bootstrap时，可由部署者显式提交repair-bootstrap。入口只接受原状态根和失败操作标识，不接受替换三根、初始输入、模型、强制或兼容参数；已完成部署使用正常升级。

部署任务组件复用原Job、实际OS锁、来源摘要、进度和systemd执行链；修复组件只验证准入与不可变父子关联，不另建调度器或业务数据库。首次提交及新worker首次写进度前，均核实原三根所有权、原输入摘要、完整当前集合与原候选一致，两个原服务账号已就绪且仍存在，原路径与单位归属不变，父任务和所有原服务控制组已空。状态或归属未知即拒绝；不创建缺失账号、不认领未知目录，也不先强停服务来满足条件。

新旧完整来源逐文件比较。只有受审的部署控制修复文件deploy/__main__.py、jobs.py、installation.py、repair.py、units.py、layout.py及检查入口tools/check_scope.py可变化，且不得删除原输入；平台、SDK、服务资产、凭据接线、构建器、依赖锁、vendor和其他来源均须保持原摘要。请求固定父操作、父来源、原输入摘要、原完整候选及每个允许差异的前后摘要。此入口不能把业务配置变更伪装为控制器修复，也不能将新控制器来源当作已重建运行产物。

子操作标识由父操作与新来源摘要确定；同一请求重复提交只观察或继续同一子任务。先持久化不可变子请求，再原子切换任务指针；两者之间中断只补齐同一关联，其他任务指针或不一致请求拒绝。父请求、进度、日志及原始来源不改写。首次worker重复核准入后保存原候选与bootstrap阶段；已有合法修复进度沿原阶段恢复，不因中途服务已启动重做首次全停要求。

修复沿原Installation.bootstrap及就绪检查继续，不重新构建候选或激活集合，不重置工作区、账号、模型、密钥和业务准备回执。完成条件与首次安装相同，须核完整官方服务实际可用；失败保留真实阶段及错误，不采用升级时保留暂停服务的放宽规则。相同子任务完成后重复查询不重放登录、赠币或授权。

## 部署方九问工作区

工作区初始化是部署准备步骤，不是普通用户接入步骤。配置先校验全部字段；首次模型配置仅支持核心和官方实例共同使用的OpenAI兼容端点。name为API模型名，Process模型选择键从公开model.list取得，不能拼接资源ID或默认使用模板占位模型。

| 阶段 | 所有权与恢复规则 |
|---|---|
| 认领 | 只在空的新目录写入部署标识、绝对工作区路径及所有者记录；无记录的既有目录、链接路径或不同部署标识拒绝接管。整段准备持有实际OS锁 |
| 初始化 | 只调用原版prepare_workspace(overwrite=False)，在独立后续解释器调用公开配置接口；不改安装包模板、全局指令、工具权限或其他工作区。固定官方版本的新工作区关闭自身自动更新 |
| 配置模型 | 使用已保存的固定model_id，经公开upsert_model_resource配置；写前保存原请求阶段。中断后先查询该资源，内容相同复用，缺失才继续原创建，内容不同停止，不覆盖人工设置或增加重复资源 |
| 缺少模型 | 保存awaiting_model并明确报告未配置；可补齐同一次准备的模型输入，不把模板占位模型当作就绪，不调用生产模型或邮件 |
| 完成与重装 | 保存原模型资源引用；每次读取当前资源及公开目录以解析有效选择键，保留人工修改的模型、权限和技能。不同首次配置输入拒绝静默重配；资源缺失或目录歧义保持未就绪 |

工作区配置记录和日志属于本机私有部署数据。模型密钥只经子进程标准输入交给原版公开配置接口，不进入命令行、返回JSON或共享日志。子进程不继承其他项目凭据或Python导入路径；Windows保留架构等OS必需变量。完成初始化及目录查询只证明配置可读，不证明真实模型生产、接单、公示或systemd部署完成。

网页引用的静态样式和脚本带内容摘要；源码修改后由固定工具同步摘要并检查，避免部署新页面仍使用浏览器缓存的旧资源。

各 Python 发行包使用各自实际产物 VERSION，不从设计 VERSION 推断实现完成。接入发布清单记录 SDK、适配、技能、Process SDK 的兼容组合及摘要；官方资源包另列资源和工具依赖。产物依据的归属见架构，迁移目录不自动升级依据。

仓库根 `requirements.txt` 只作为开发环境入口；生产环境按安装单元使用明确依赖清单。可安装包通过包资源或显式配置定位文件，不读取相邻源码目录；运行入口不手工修改 `sys.path`，资源定位不隐含依赖调用者工作目录或相邻 A2C 仓库。

Windows本机最低环境为Windows x64、一套CPython3.11和浏览器。core、participant、swarm使用同一Python建立三个依赖锁隔离的venv，不要求用户安装三套Python；沿用内容发行及独立环境安装器，不另造安装链。原版wheel自带网页静态资源，默认使用SQLite及内置记忆；Redis、Milvus、Elasticsearch或其他可选外接能力不成为本机启动前提。

本机启动装配归deploy，仅负责受审安装身份、私有配置、明确回环地址和本任务进程的启动、状态及停止，不调度合同或替用户签署。一个原版九问指一个网页实例与原版安装，个人助手及服务方仍可通过其公开Process接口建立各自会话；不承诺只有一个OS进程。官方资源及参与方仍在核心外经同一SDK运行，不把生产移入平台核心。

本机数据及凭据由本机用户控制，不能将该路径当作陌生用户的在线隔离服务。模型凭据只由所属组件按原配置契约使用，保存于受限私有配置，不进源码、发行包或日志；核心读取同一受限平台配置文件，不新增Windows专用凭据接口。A2UI答复仍是结构化输入，SDK保护动作继续要求原可信确认，不以启动成功或模型文字代替用户批准。本机进程管理及数据保留按本页Windows可信本机体验和重部署规则执行。

Python 发行包从隔离源码快照构建，排除 build、dist、egg-info、字节码和开发环境；构建后按源码清单核对模块，已有构建缓存不得使已删除的旧模块重新进入安装包。 A2C依赖同步仅从干净的已提交Git源码提取原blob构建，核对包内字节和版本；未提交源码、构建期间换提交或混入模块均拒绝入库。Windows工作区的自动换行不能改变来源提交所代表的包内容。

### 运行环境与发行清单

| 环境 | 包与权限边界 |
|---|---|
| core | 平台、A2C、A2X及其普通依赖；不安装参与方SDK、Process SDK、官方业务或九问本体 |
| participant | 统一SDK、九问适配、官方包、A2C和Process SDK；不安装平台或九问本体 |
| swarm | 固定原版九问及随仓Git依赖；不安装本平台或参与方SDK；部署方新建工作区与用户既有九问分开 |
| build | 仅固定构建工具，生成上述wheel及接入包；不作为任何服务的运行环境 |

发布构建从本仓固定输入生成ioalab.deployment-release/1清单，包含目标OS/CPU、CPython主次版本、各单元本地wheel名称/版本/原始SHA256、普通依赖锁及摘要、初始化数据与两接入ZIP摘要。路径为发行目录内的相对路径，拒绝越界、链接或未登记的Git依赖。整体清单内容摘要确定发行目录，完成后不原地改写。生产安装不使用根开发requirements、editable安装、VCS或Node/npm构建。

普通包分别按目标平台解析为精确版本锁；core、participant和swarm的直接依赖由实际wheel元数据取得。Git直接引用只映射到清单中已固定的本地wheel；其余直接URL拒绝。锁不包含安装源、远端引用或其他requirements文件，安装源由部署者选择的HTTPS国内镜像提供。纳入摘要的依赖锁固定UTF-8/LF字节，先写定再计算摘要，并核对Git暂存或克隆后的同一字节；不得让平台默认换行转换改变已记录摘要。锁的直接输入摘要必须与当前wheel依赖一致；Windows解析不能代替Linux解析，解析成功不代表Linux实机通过。首批提供Linux x86_64/CPython3.11与Windows开发核验清单，其他目标单独生成和验证。

安装环境按单元清单、实际平台及Python版本确定独立目录。安装前核全部摘要，安装后核精确版本、依赖及禁止混入的组件；参与方沿用[共用安装身份](../接入/SDK共用机制.md#安装与实例核对)。只有验证完成才发布ready。完整环境不原地修补；失败保留现场，已确认失败可显式重试，只有旧状态而无真实完成/所有者证据时保持未知。运行数据不放在环境目录内。 Windows使用短环境目录及短尝试名，目录摘要前缀只用于定位，所有权必须核对完整身份摘要；前缀冲突拒绝接管。安装前核路径预算，安装后核原生库路径及真实依赖导入，避免pip检查通过而Windows加载DLL失败；不通过修改系统长路径或安全设置解决。

Linux运行路径经受控的current符号链接指向已核验完整集合；更新前须停止相关单元并确认SDK执行权释放。集合、环境链接及发行资源的路径边界由[安装与升级](安装与升级.md)定义。官方配置引用稳定的swarm入口和固定工作区，包升级不因此改写准备绑定、身份或业务定义；核心与参与方实际安装身份仍按真实环境路径核对。

## 进程与网络

Linux受管部署采用Python3.11、隔离venv、systemd和可选Nginx；Windows可信本机按上述本机装配运行，不引入systemd或Docker依赖。跨设备部署只需平台公共HTTPS/WSS入口可达；本机入口只监听回环。个人助手和服务方主动连接，不要求公网IP、端口映射或用户服务反代。

| 实例 | 内容 | 数据与模型 |
|---|---|---|
| 平台核心 | 身份、注册、委托、支付、消息、观察与 Web | 平台数据库/机构密钥；发现和仲裁模型独立配置 |
| 官方服务 | 用 SDK 共用运行时加载官方服务配置，经九问适配按需执行 | 独立服务密钥、合同、工具和会话；独立模型设置 |
| 管理员助手 | 同一运行时的个人助手角色及原版九问，自动配置 ISC_001 | 独立账号、日程、通知凭据和会话 |
| 普通参与方 | 自己电脑/服务器上的运行时及九问 | 用户自己的本地数据、模型、技能和工具 |
| 实验客户端 | 通过公开 SDK 产生委托与助手通信 | 独立实验身份与可追溯输入，标记 experiment |

核心默认本地 8750。反代支持 `/ws/agents` 与 `/ws/admin` 升级、心跳和足够空闲超时；断线由运行时恢复，反代不能将消息缓存成另一套投递队列。正式外网使用 TLS，回环测试可显式使用明文。

安装顺序：安装核心 → 初始化账号与分类 → 配置官方服务及管理员助手 → 校验九问/模型/工具 → 绑定身份并发布 → 建立连接 → 开放接单。未配置模型或通知能力时显示具体不可用项，不能用桩替代真实运行。

部署清单显式选择 `src/official/` 的资源及初始化数据，通过受控本机初始化命令或管理员授权入口创建内部账号与分类。核心校验传入数据，不跨目录读取官方参与方源码；初始化不能覆盖已有账号凭据或重置运行状态。自有JSON来源的清单摘要按UTF-8/LF规范字节计算，Windows检出产生的CRLF不改变同一来源；业务内容变化仍使摘要失效。第三方归档与wheel继续按原始字节核验，不做换行归一。私钥由参与方本地创建，身份绑定与服务模板发布通过同一 SDK 完成，不能把初始化当作代签。

## 依赖与发布

所有 Git 源码依赖随本仓固定，按 `vendor/SOURCES.json` 保存来源、提交、许可证、摘要及构建信息。服务器不访问 GitHub，不使用子模块、VCS 安装或现场 Node/npm 网页构建。可从部署方配置的 GitCode 远端同步或导入完整源码目录；来源 URL 仅用于追溯。

| 依赖 | 发布形式 |
|---|---|
| A2X | 普通源码快照；本平台分类数据由本仓配置生成 |
| A2C、九问 Process SDK | 锁定 wheel，并保留相应源码来源与摘要 |
| 九问及其 Git 依赖 | 原始固定源码归档、许可证、预构建 wheel；网页资产随包 |
| 普通 PyPI 依赖 | 锁定依赖及部署者可访问的国内镜像；不宣称全离线 |
| 产品接入技能 | 从源构建安装包，包含 SDK、九问适配、官方可选工具、A2C 和固定 Process SDK 的 wheels、引导与校验清单；两个技能使用同一兼容清单，生成物不回拷为第二份源码 |

`ioalab-official` 同时交付服务资源和业务工具。服务目录、验收源码及初始化摘要脱离源码仓库后仍可读取；构建按声明的源码根检查完整模块及资源，排除旧build输出。相同源码和构建环境采用固定归档时点，重复构建的wheel及接入发布摘要一致，修改技能说明本身不产生新的依赖环境。

官方工具随产品接入环境安装，但只有本机显式配置的工厂才被加载；安装本身不创建安排、开放接口、读取私人日历或发送通知。通用SDK独立安装不因此依赖官方工具。

技能安装脚本先验证清单与摘要，在用户目录准备隔离接入环境；相同账号、相同实例的另一角色复用已有运行时，仅增加角色配置。依赖或状态版本不兼容时停止接管并明确报告，不同时启动两个身份库写入者。完成检查后发布安装标记；已完成环境不可原地修补，标记损坏明确失败。启动及业务调用按[SDK共用机制](../接入/SDK共用机制.md)核对实际安装身份，发布更新不能被相同账号或配置掩盖。SDK 的调用脚本经本机认证的 IPC 操作常驻组件，不另开同一身份数据库。

普通用户接入以其已经安装且可用的九问 Swarm 为前提。接入安装器只管理独立的 SDK/适配环境及 IoA 本地配置和数据，不写九问安装目录或全局配置，不安装、覆盖、升级或降级九问，也不更改其模型、工具权限、全局指令、自动更新及技能市场设置。用户通过九问原生入口导入接入技能，指定已有宿主命令或公开接口；额外工具和扩展仅在现有版本原生支持且用户显式配置时启用。能力缺失明确报告未就绪，不以更换宿主或自动放宽权限补齐。

随仓固定的九问版本用于官方实例和复现实验，不要求普通用户替换已有安装。部署方安装器仅可配置自己新建的独立实例，保留已有用户实例。适配先检查公开能力，不使用网页内部资源 ID 代替进程模型选择键；真实用户答复关联不可用时保持待确认。

九问网页通知使用适配包随附的 IoA 通知扩展，遵循九问原版应用扩展机制；使用[通知契约](../接入/九问网页通知.md)的准备命令配置本扩展原生命名空间，凭据不写全局环境。协议能力核对不通过时保留队列并报告具体缺项；不修改上游源码或历史数据库来补齐。

| `experiments/` | 正式可复现实验源码与非私密配置；入库，通过公开 SDK 运行，实测私有数据仍放运行目录 |

核心、服务、助手分别备份；数据库和业务文件使用一致性快照，恢复后核对签名、支付操作与接单台账，再开放新任务。部署、SDK、业务工具不得隐含读取临时目录才能工作。

升级需保留身份、原合同、模板、授权、支付与投递回执；不能清理数据来规避期限或容量。尚未具备接管条件的合同先在原环境完成或按协议结束，再停止原进程部署；新旧执行器不能同时持有同一智能体的活动执行权。

模型调用中断后先核操作回执再恢复。业务工具使用运行时传入的稳定操作键保存业务回执；工具自己的预约/邀请状态与运行时检查点分别管理，邮件/付款结果未知不得自动重做。离线期间合同计时继续。队列、磁盘和配额达到上限应拒绝新业务并可观察，保留已有合同的控制及恢复通道。

验收分别覆盖无 GitHub 的依赖安装、原版九问接入、协议闭环和 Linux 实机/systemd；各层证据独立保存。部署成功不自动代表真实邮件、原生网页审批或视频质量已验收。

## 平台核心的数据所有权

| 边界 | 要求 |
|---|---|
| 取得 | Platform完整角色在固定公共地址、写A2X凭据、打开/迁移DB及装配组件前，取得数据目录的真实OS排他锁；init/serve入口不得提前写配置或日志。同目录的第二实例明确拒绝，不能先修改配置再报占用 |
| 归属 | 存储层提供所有权句柄，由平台生命周期持有；普通DB连接仍只是连接，不等同一个Core角色，不从SDK或部署包反向导入实现 |
| 证明 | 核实际OS锁和持有句柄，不以PID文件、旧状态、进程内RLock或端口占用声称全程单实例；不删除其他实例的锁或运行数据 |
| 失败 | 构造/启动失败及lifespan异常均有清理路径；未启动实际writer时可安全释放，不留下须重启进程才能解除的占用 |
| 退出 | 先停新工作并等待本Core实际后台writer/传输退出，再关闭DB和释放句柄；writer仍活跃时不得报告已停或允许第二实例恢复同数据 |
| 崩溃 | OS释放排他句柄后下一实例才能接管；持久queued与未知已开始动作区分，不能自动重跑后者 |
| 其他入口 | 初始化、停服备份和清理也先取得同一所有权；运行中明确拒绝。锁文件只作持有句柄，不作为可删除的PID标记；清理和备份不删除或恢复该文件来改变锁状态 |

部署仍使用同一默认命令，管理员不需手动维护PID或锁文件。该机制不改变参与方SDK的各自数据所有权，也不修改原版九问。
