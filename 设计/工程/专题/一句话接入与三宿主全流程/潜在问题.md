# 潜在问题

2026-11-16本轮只读审查及方案分析。代码定位以仓内实际文件为准；官方文档说明机制，不代替三宿主实机验收。以下建议没有自动变为用户已定决策。未实现产品代码，未运行新的模型业务或部署。后续用户已明确废弃12小时空闲方案，改为反向可调用性检测；下表原空闲方案问题仅记录变更原因，当前规则见决策D16。

## 优先解决的技术前置

| 问题 | 已核实依据与影响 | 建议及完成证据 |
|---|---|---|
| 独立客户端回投Codex桌面原会话尚未证明 | `src/client/hosts/codex/ioalab_codex/host.py`的`_command`启动独立stdio App Server，`run`在原thread为active时直接拒绝。前次桌面`send_message_to_thread`成功只证明本聊天内部工具可用 | 最先验证独立进程到桌面当前原会话的公开通道、用户可见性、活动／空闲两种状态；不能用另开CLI线程替代 |
| Claude活动会话推送存在适用条件 | [官方Channels](https://code.claude.com/docs/en/channels)为研究预览，需会话启用，受认证方式、组织与插件白名单约束；标准MCP本身不推送。接入允许扩展配置也不保证原来打开的会话立即可收消息 | 适配器探测并报告实际能力；验证首次接入后原会话能否生效、是否需重开、如何保持原Session。不可宣称所有认证方式均已支持，不默认降级为下次Skill调用带回 |
| 现有宿主配置只能选择一个执行宿主 | `src/client/ioalab_client/runtime.py`的`HOSTS`按单一`host.type`选装配，`merge_host`拒绝切换；不能直接满足默认宿主接外部新业务、其他宿主原会话收回投 | 设计可登记多个宿主配置／能力、一个默认宿主及每业务持久宿主会话绑定。共享同一客户端与数据写入者；新增入口不切默认 |
| 客户端自建执行会话与用户原会话不同 | 两宿主`host.py`恢复前校验本轮workspace中的原Session和definitionDigest；Codex还传工作目录、工具定义与权限覆盖。现有逻辑用于客户端所有的固定执行会话，不能原样套到用户已有聊天 | 在统一宿主适配契约内区分投递既有用户会话和运行客户端自建会话；不改用户原聊天的工作目录、工具定义或原指令来强行通过绑定核验。统一维护会话串行，用户打开或接手会话时核原生活动状态 |
| 原生可见会话与后台Session尚非同一验收 | Claude工作目录影响resume列表；九问Process执行终态不代表网页历史可见。已有九问扩展使用公开`session.create`／`history.append_record`，历史追加不自动证明模型实际处理 | 三宿主分别验证原生列表、打开历史、继续对话与客户端后续续接；Claude须能在`claude --resume`找到，并返回必要的实际工作目录／可执行入口。不得自行写宿主私有会话库补齐 |

## 统一接口与接入仍需收口

| 问题 | 依据与影响 | 建议 |
|---|---|---|
| 宿主差异既存在文档，也存在共用代码 | README_AGENT、`skills/_shared/references/host-setup.md`包含三套定位／配置说明；`ioalab_client/native_skills.py`按宿主选目录，`onboarding.py`按宿主拼入口及判断九问通知 | 依D23把宿主专属操作移到hosts内统一契约实现；只改文案不够。同角色Skill正文／引用一致，实际安装包装和绑定路径可以不同 |
| 通用Skill不能自己可靠证明当前宿主与原会话 | 当前`skills/_shared/ioalab.py`只绑定解释器、配置、角色，再转交命令；未附带经过宿主适配关联的会话上下文 | 由接入时配置的原生适配机制获取／传递调用宿主、真实会话与工作目录等中性上下文。不能重新让模型选择三套参数，也不能以工作目录或PID猜会话归属 |
| 下一次打开智能体不等于自动执行Skill | 原生安装、原生发现、实际调用和客户端启动是不同事件 | 至少在每次IoA业务调用前统一ensure-running。需要启动时自动执行则由各宿主原生生命周期机制适配并实测，不把文档一句“自动读取”当证据 |
| 首次接入仍要求已有Git与CPython3.11 | `src/client/bootstrap.py`在代码执行前已依赖Python，安装内部又强制3.11和官方GitCode标签；既有草案中的uv与GitHub develop尚未实现 | 单独设计无适配依赖时的安装引导与uv兜底；宿主识别入口不能要求客户端适配包已经装好，避免启动循环依赖。缺命令、权限或认证时给准确下一步；不声称任何未登录／不能执行命令的宿主也能零交互完成 |
| 后装其他宿主的依赖尚无明确补齐路径 | bootstrap只安装所选宿主extra；只安装新宿主Skill文件不代表其反向适配依赖已存在 | 新宿主登记先补齐其适配与可选依赖、核同一环境和发行来源，再安装相同Skill；不重注册、不换账号、不改变默认宿主、不启动第二个写入者 |

## 业务边界与草稿冲突

| 问题 | 依据与影响 | 建议／待确认 |
|---|---|---|
| 旧空闲方案已废弃，健康检测待实施验证 | 用户以能否反向调用处理私人消息／委托定义在线，不再采用12小时空闲退出 | 子智能体调研已完成，摘要见现状与证据。D25—D27已确认只测默认宿主、默认600秒、安全退出和现有暂停恢复接口；35实现退出与新请求的竞争收口，不能丢已接收业务 |
| 全部工具开放涉及现行明确拒绝，不是仅删白名单 | Claude的`tools=[]`、`plugins=[]`、`setting_sources=[]`和非deny直接拒绝；Codex关闭hooks／plugins／shell／MCP等且强制只读。开放后不自动获得缺失资源／凭据 | 依D7修订所属规范并在各适配落实真实能力；仅表示宿主实际可用工具，不宣称三宿主工具功能完全相同。原生工具、业务工具与SDK受保护动作各有职责；防止同一业务在SDK回调与Skill入口重复执行或形成递归调用链，不增加本期逐项权限配置 |
| 模型并发控制不等于累计模型费用封顶 | `RuntimeConfig.max_model_runs`为并发；业务scope预算约束拟卡／合同等交易支出，不是宿主模型账单 | 遵守D17复用既有控制、不新增费用体系；准确报告现有保护范围，不宣传已有统一LLM费用上限 |
| 在线试用仍可能绕过置灰入口访问 | `src/platform/ioalab/web/trial.py`仍提供`/trial`、`/api/trial/entry`及确认入口，`web/app.py`仍注册路由 | 交原在线试用04跟踪，不能把置灰当后端关闭；本轮只拟定客户端专题，不夹带相关WIP或擅自停服务器 |

## 验证与交接

优先顺序建议：独立客户端三宿主原生会话验证 → 统一宿主契约与通用Skill → 生命周期及单实例 → 四流程和跨宿主验收。技术缺口保留为先行验证票；用户不接受的降级不得自行作为完成标准。Codex以桌面版实际入口为准，Linux本轮不测；三宿主分别记录已实现、已提交、已发布和实机验收，专题草稿不是上线证明。

Codex协议参考：[官方App Server](https://developers.openai.com/codex/app-server/)支持线程创建／恢复与活动轮次steer；方法存在不证明本客户端已能连接桌面原连接。Claude会话参考：[官方会话](https://code.claude.com/docs/en/agent-sdk/sessions)、[CLI参考](https://code.claude.com/docs/en/cli-reference)。
