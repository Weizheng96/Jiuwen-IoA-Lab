# 43：Process 按需初始化提交资源

状态：待实施，与当前设计有偏离。解除官方服务在九问 Process 提交前的资源误拦截。验收覆盖常规报价、复签和生产的提交路径，以及显式提交资源和工具回调资源。依据为[宿主提交与资源规则](../../../组件/客户端/共用运行时/接口/宿主提交.md#文件排队与等待)和[九问宿主适配](../../../组件/客户端/宿主适配/接口.md#agenthost-实现)。

## 现状

测试服务器的 `ioalab-jiuwen 0.0.178` 仍会在两组 `HostResource` 列表均为空时调用装配层绑定的资源工厂。服务方复签使用 `HostInput(prompt)` 和默认冻结定义，也未注入 `resource_io`。Registry 按原授权规则拒绝，原 S01 回执为 `not_ready / resources / not_submitted`，未进入九问原生轮次。本机无模型对照已复现该拦截。

报价与复签共用 `HostPolicy.decide`，生产也走同一 `ProcessHost.submit`。这些路径经 SDK 准备的业务材料可以已在本轮工作区落盘，仍可能没有显式 `HostResource`。真实故障证据、上层错误传播和旧作业恢复归[专题42](42-委托复签未知结果与诊断.md)。

## 修复方案

| 场景 | Process 适配器处理 |
|---|---|
| 无显式输入或定义资源 | 跳过工厂、资源文件布局和清单生成，直接走现有原生提交。普通 SDK 工具回调仍沿真实会话绑定及授权执行。 |
| 有显式输入或定义资源 | 原生提交前，使用原 operation 与完整 attempt 取得本轮 `ProcessFiles`，经原 reader 读字节、核摘要并落盘，将真实映射清单附到本轮输入。授权、摘要或布局失败仍返回 `phase=resources / dispatch=not_submitted`。 |
| 工具回调返回显式资源 | 原回调完成后才按需获取同一个 `ProcessFiles`。首次资源来自回调时也走原工厂。映射失败保留原回调值，以 `callback_resources / accepted` 报告，并保存原生终态及原业务回执。 |

在 `Submission.submit` 内让两处资源分支共用按需获取逻辑，成功创建的控制器只在本次 attempt 内复用。同轮如可并发进入资源分支，保护首次创建和同一资源的落盘，复用现有工厂、`ProcessFiles.materialize` 和 Registry 的 I/O 检查。保持改动局限于九问 Process 适配器及定向测试，沿用现行接口、权限、文件布局与回执格式。

## 验收目标

- [ ] 常规提交：使用绑定真实 Registry 的工厂，无 `resource_io` 且两组显式资源为空。新建及续接能到达 Process 协议边界，工厂调用为 0、无资源清单和资源布局；有普通 SDK 工具时，真实会话与请求绑定后，回调只执行一次。
- [ ] 提交资源：分别传入输入资源和定义资源，核对宿主收到的路径能读到原字节，摘要与冻结定义保持一致；同轮提交与回调均有资源时，复用一次成功的工厂初始化。缺授权、跨作用域或摘要不符时，Process 边界调用为 0，回执保留 `resources / not_submitted`。
- [ ] 回调资源：提交时为空，第一次带资源的回调才取工厂，成功时返回可读文件及原回调值。缺授权或映射失败时，保留原回调值、`callback_resources / accepted` 及真实终态，原回调调用次数为 1。原资源作用域的关闭与隔离用例通过。
- [ ] 本机回归：复用现有 runner 定向运行 `test_jiuwen_resources.py`、`test_jiuwen_submission.py`、`test_submission_resource_scopes.py` 和 `test_business_skills.py` 的相关用例。在 Process 协议边界使用替身，保存实际退出码和回执。额外的真实模型验收按下项记录。
- [ ] 服务器验收：确认测试服务器实际安装修复包。通过现有可信确认发起一笔获授权的新官方 SQL 委托，核到 `decision` 的实际原生请求、会话、终态，以及平台的服务方复签和成约状态。报价与生产共用提交入口，在本机按各自调用形态回归。若本次实单覆盖报价或生产，分别记录实际轮次及回执。旧作业按专题42处理。
