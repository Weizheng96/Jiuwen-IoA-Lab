# 部署教程

新装创建独立目录；再次部署先停止并核清本部署的旧进程，再保留原数据、账号、工作区和模型配置重新部署。不要删除数据库、配置或锁文件来重试。以下路径可整体替换为自己的专用路径。

> 命令按当前公开入口核对。新Linux基线已完成核心、官方/助手就绪、三类组件模型通路及正常停启、保数据升级；实际版本和边界见[部署事实](实施资料/部署发行.md#新服务器验收基线2026-11-11)。三席开通与各业务专项继续独立验收。

## 本项目测试服务器策略

用户已明确本服务器为可清空内部数据的测试环境：只保留最新项目。每次更新采用显式`python3.11 -m deploy test-reset --state /var/lib/ioalab`，原部署身份和安装输入自动复用。该任务正常停止并核实际写锁与角色进程释放，清空内部账号、余额、合同、消息、九问会话与工作区，保留部署私有参数、模型密钥、HTTPS证书和外部邮箱授权，再初始化最新部署并清理旧环境、旧发行及历史备份。只在task.status=completed且真实runtimeReady通过后视为完成；不得通过删除原进程锁或伪造状态推进。

如果本次test-reset已经清空旧数据、失败于initializing，且必须换来源修复，先保留原请求与日志，在新的已提交、已推送固定来源执行：

```bash
sudo python3.11 -m deploy test-reset --state /var/lib/ioalab --resume-from FAILED_OPERATION_ID
sudo python3.11 -m deploy status --state /var/lib/ioalab
```

入口仅接受已停止的指定失败阶段，绑定父来源及候选；新候选先构建，再核原控制组及实际锁，继续初始化而不再次清空新账号。父请求不可改写；子任务完成后必要父证据收进当前任务。普通同来源重试仍用原入口；其他阶段或输入冲突保持原现场，不用此参数绕过。

历史源码和独立旧实验目录由维护者按明确路径核对不再被进程或当前部署引用后删除，不留多版本恢复副本；本策略已授权丢弃旧内部测试数据。正式生产环境另行确定保留要求，普通upgrade的数据保留语义不因此改变。现实现及验收见[部署06](../组件/部署/进展/06-单版本测试服务器与数据重置.md)。

## Linux服务器部署

平台、官方实例与在线试用只在 Linux 服务器部署；Windows 不提供部署方式，Windows 开发机只做单元测试、自检与本机平台开发运行（见 develop 技能）。

需要 Linux x86_64、CPython 3.11（含 venv）、systemd、cgroup v2、sudo、Git、Nginx、OpenSSL 与可访问的国内包镜像。下面按 Debian/Ubuntu 的 Nginx 目录举例。仅允许的访问来源需要 TCP 22、80、443；内部CA不要求向公网开放。先确定公共 HTTPS 地址，平台首次初始化后不改公共地址。采用运行根 `/opt/ioalab-runtime`、状态根 `/var/lib/ioalab`、配置根 `/etc/ioalab`；源码目录与三根互不嵌套。

**1. 连接服务器。** 在本机终端运行以下命令，将 `SERVER_IP` 换成真实地址。首次连接核对服务器指纹；此命令不经过 SSH 代理跳板。

```powershell
ssh -o ProxyCommand=none -o ProxyJump=none root@SERVER_IP
```

**2. 获取固定发布源码。** 先由发布方将 GitHub 已验证的 main 同步至 GitCode，并提供两仓一致的完整提交 SHA。在服务器 Bash 执行以下命令，将 `PUBLISHED_SHA` 换成该值；不要取其他会话的未提交工作树。

```bash
set -euo pipefail
git -c http.proxy= -c https.proxy= clone https://gitcode.com/WeiZheng96/jiuwen-IoA-lab.git /root/ioalab-source
cd /root/ioalab-source
RELEASE_SHA=PUBLISHED_SHA
git checkout --detach "$RELEASE_SHA"
test "$(git rev-parse HEAD)" = "$RELEASE_SHA"
test -z "$(git status --porcelain)"
```

GitCode 请求显式直连；服务器无需访问 GitHub。Git 来源依赖使用随仓固定原件，普通包使用安装输入指定的国内 HTTPS 镜像。已有源码目录不要覆盖：先在原源码完成下一步停机，再将新发布置于独立源码目录。

发布维护者在合入 main 前建立验收基线时，可将已提交并推送 GitHub develop 的固定候选通过 Git bundle 复制到服务器独立源码目录，核对完整 SHA 与干净工作树后执行下述同一安装入口。此时是待发布候选；保存实际候选与回执，通过发布检查和服务器验收后再按交付流程合入 main、同步 GitCode，不能把未提交工作树作为候选。普通部署仍使用上面的双仓发布来源。

**3. 先停止旧部署。** 新装跳过；已有部署在其原源码目录执行公开停止并查询状态。`stop` 返回 `waiting` 时稍后再执行同一 `stop`，继续原停止请求。仅当停止回执同时给出 `phase=stopped`、`allOwnedGroupsEmpty=true`、`executionLocksReleased=true` 才进入下一步；外层 `status=completed` 不是全部停止。

```bash
sudo python3.11 -m deploy stop --state /var/lib/ioalab --wait-seconds 30
sudo python3.11 -m deploy status --state /var/lib/ioalab
```

正常停止保留账号、数据库、密钥、模型、工作区及原操作。超时、归属不明、旧初装未完成或锁未释放时，到此停止，按部署技能处理异常；不要直接 `kill`、删除锁、修改任务记录或再启动一套写入者。完整安装过的实例全停后，在第6步选择已有升级链。未完成初装不套用此入口，归档后新装的特殊处理也不是日常保数据重部署步骤。

**4. 填写模型与地址。** 新装执行第一条，认领独立目录并生成唯一私有配置；第二条打开文件。已有配置保留，停止后仅编辑原文件。

```bash
sudo python3.11 -m deploy.configure --root /opt/ioalab-runtime --state /var/lib/ioalab --config-dir /etc/ioalab
sudoedit /etc/ioalab/core/platform.json
```

填写下表的模型及管理员字段，无需开发者 profile。API key 只写文件，不贴入命令或聊天。

| 字段 | 填写内容 |
|---|---|
| `llm.api_key` | 自己的模型服务 API key |
| `llm.base_url` | 该 key 对应的 OpenAI 兼容 API 地址，例如阿里云百炼 `https://dashscope.aliyuncs.com/compatible-mode/v1` |
| `llm.model` | 服务商允许调用的主模型名称 |
| `llm.discovery_model` | 可调用的检索模型名称，可与主模型相同 |
| `llm.embedding_model` | 可调用的嵌入模型名称；阿里云示例为 `text-embedding-v4` |
| `admin.password` | 自己设置的管理员密码，账号默认 `admin` |
| `runtime.admin_email` | 管理员接收会议邀请的邮箱，默认 `zhengw.cc@outlook.com`；也可在管理员工作台保存，正式停启后应用到助手 |

另设 `runtime.public_url` 为已确定的 HTTPS 地址；本项目为 `https://ioalab.openjiuwen.com`（公网IP部署可用 `https://公网IP`），保持 `runtime.bind=127.0.0.1`、`runtime.port=8750`；`authentication.trusted_proxy_addresses` 填 `["127.0.0.2"]`，与反代的独立来源一致。保存并退出，密钥不进入命令、Git或普通日志。已有配置按当前修订规则停机编辑，不重跑初始化或用示例覆盖原文件。

**5. 准备 HTTPS。** 已有合格证书及续期时复用。按网络条件选择下面一种分支；本项目使用内部CA域名分支，无需公网CA连接或DNS TXT权限。当前实现已在固定develop候选完成Linux部署，尚未合入main/GitCode；具体来源与验证边界见[域名实测](实施资料/部署发行.md#域名与内部ca实机验收2026-11-13)。

### 内部CA与域名（本项目）

已有CA必须复用，CA私钥只留服务器。首次没有CA时，部署者才在新目录显式创建；以下创建命令发现原文件就停止，不在更新或test-reset时执行。

```bash
sudo apt-get install -y nginx openssl python3.11-venv
sudo install -d -m 700 /etc/ioalab-tls/internal-ca
sudo sh -c 'set -eu; umask 077; test ! -e /etc/ioalab-tls/internal-ca/ca.crt; test ! -e /etc/ioalab-tls/internal-ca/ca.key; openssl req -x509 -newkey rsa:3072 -nodes -sha256 -days 3650 -subj "/CN=IoA Restricted Deployment CA" -addext "basicConstraints=critical,CA:TRUE" -addext "keyUsage=critical,keyCertSign,cRLSign" -keyout /etc/ioalab-tls/internal-ca/ca.key -out /etc/ioalab-tls/internal-ca/ca.crt'
```

先核原CA来源及公钥指纹，创建受限登记输入。下面SHA256命令输出的64位值填入JSON，不填冒号；当前项目实际指纹见部署事实。四个文件路径须不同，父目录和文件均不能是符号链接，私钥和登记JSON只允许所属维护身份读取。

```bash
openssl x509 -in /etc/ioalab-tls/internal-ca/ca.crt -outform DER | sha256sum
sudo install -d -m 700 /etc/ioalab-bootstrap
sudoedit /etc/ioalab-bootstrap/authority.json
sudo chmod 600 /etc/ioalab-bootstrap/authority.json
```

```json
{
  "format": "ioalab.internal-ca/1",
  "ca_certificate": "/etc/ioalab-tls/internal-ca/ca.crt",
  "ca_private_key": "/etc/ioalab-tls/internal-ca/ca.key",
  "ca_sha256": "填写已核64位DER_SHA256",
  "server_certificate": "/etc/ioalab-tls/domain/server.crt",
  "server_private_key": "/etc/ioalab-tls/domain/server.key"
}
```

在第2步选定的固定来源执行维护入口。issue复用原CA，准备带目标DNS SAN的90天叶证书，不自动改变Nginx或平台地址；已有合格叶证书复用。再把同一CA公共证书加入服务器系统信任，供核心就绪检查使用。

```bash
sudo python3.11 -m deploy.tls issue --state /var/lib/ioalab --authority /etc/ioalab-bootstrap/authority.json --hostname ioalab.openjiuwen.com
sudo install -m 644 /etc/ioalab-tls/internal-ca/ca.crt /usr/local/share/ca-certificates/ioalab-internal-ca.crt
sudo update-ca-certificates
if ! sudo test -e /etc/nginx/sites-available/ioalab; then
    sudo install -m 644 deploy/nginx.conf /etc/nginx/sites-available/ioalab
fi
sudoedit /etc/nginx/sites-available/ioalab
```

已有同名站点时先核归属并编辑原站点，不用模板覆盖。将模板listen改为443 ssl、server_name改为ioalab.openjiuwen.com，加入以下证书引用与独立HTTP跳转server；保留模板的map、/official/、根路径、/ws/、上传限制、proxy_bind 127.0.0.2和来源头覆盖。同名map只留一次，不让域名站点依赖待清理的旧IP站点。

```nginx
# 以下两行加入HTTPS server内部：
ssl_certificate /etc/ioalab-tls/domain/server.crt;
ssl_certificate_key /etc/ioalab-tls/domain/server.key;

# 以下server与HTTPS server并列：
server {
    listen 80;
    server_name ioalab.openjiuwen.com;
    return 308 https://ioalab.openjiuwen.com$request_uri;
}
```

首次才创建站点链接；已有链接核指向本应用。验证配置再重载，并使用正确域名及信任链检查握手。应用尚未启动时API可502，证书校验须先通过。

```bash
sudo ln -s /etc/nginx/sites-available/ioalab /etc/nginx/sites-enabled/ioalab
sudo nginx -t && sudo systemctl reload nginx
curl --noproxy '*' --fail https://ioalab.openjiuwen.com/api/config
sudo python3.11 -m deploy.tls status --state /var/lib/ioalab
sudo python3.11 -m deploy.tls install-renewal --state /var/lib/ioalab
sudo python3.11 -m deploy.tls renew --state /var/lib/ioalab
sudo systemctl list-timers ioalab-tls-renew.timer
```

renew每日检查，剩余30天内换叶证书，复用原服务器私钥，nginx检查/重载后核实际SNI指纹，失败恢复原证书。未到期changed=false是正常结果。成功应用部署自动更新维护单元到当前固定来源，旧源码清理前核WorkingDirectory；CA及其登记保留在test-reset清理之外。证书或私钥不得随应用重新生成。

客户端公共CA由部署者使用`python3.11 -m deploy.tls export-ca --state /var/lib/ioalab --origin https://ioalab.openjiuwen.com --output <新公共导出目录>`导出，再经受审发布打入统一客户端；只导出公钥证书和清单。当前候选已内置本项目原CA并限定此Origin，SDK的HTTP/WSS共享同一信任上下文，无需导入客户端系统根证书。其他部署域名或CA必须重新受审打包。浏览器不读取SDK资源，浏览器信任由用户或组织单独管理；已有显式旧IP客户端不自动迁移域名。

完成本分支后直接进入第6步，不执行下面Certbot命令。后续同域换公共CA时保留客户端系统默认CA信任，不做叶证书指纹锁定；实际公共CA切换仍待验证条件具备。

### 公共CA的公网IP分支

此分支要求公网验证者能直连80。局域网来源限制下外部验证超时应停止，不反复签发或扩大来源。首次将变量换为实际IP，创建本应用专用HTTP站点，不删除其他站点。

```bash
PUBLIC_IP=SERVER_IP
sudo apt-get install -y nginx python3.11-venv
sudo install -d -m 755 /var/www/ioalab-acme
sudo tee /etc/nginx/sites-available/ioalab-acme >/dev/null <<'NGINX'
server {
    listen 80;
    server_name _;
    location ^~ /.well-known/acme-challenge/ { root /var/www/ioalab-acme; }
    location / { return 404; }
}
NGINX
sudoedit /etc/nginx/sites-available/ioalab-acme
sudo ln -s /etc/nginx/sites-available/ioalab-acme /etc/nginx/sites-enabled/ioalab-acme
sudo nginx -t && sudo systemctl reload nginx
```

编辑时把 `server_name _` 改为实际 IP，避免其他默认站点接收验证请求；同名文件或链接已存在时先核归属。证书使用独立工具环境。先测试签发，再申请正式短期 IP 证书：

```bash
sudo python3.11 -m venv /opt/ioalab-certbot
sudo /opt/ioalab-certbot/bin/python -m pip install --index-url https://pypi.tuna.tsinghua.edu.cn/simple certbot==5.9.0
sudo /opt/ioalab-certbot/bin/certbot certonly --webroot -w /var/www/ioalab-acme --ip-address "$PUBLIC_IP" --required-profile shortlived --cert-name ioalab-ip --agree-tos --register-unsafely-without-email --non-interactive --dry-run
sudo /opt/ioalab-certbot/bin/certbot certonly --webroot -w /var/www/ioalab-acme --ip-address "$PUBLIC_IP" --required-profile shortlived --cert-name ioalab-ip --agree-tos --register-unsafely-without-email --non-interactive
```

任一步失败即停止，保留报错；不禁用 TLS 校验或临时走代理。接着复制仓内反代模板并编辑：

```bash
sudo install -m 644 deploy/nginx.conf /etc/nginx/sites-available/ioalab
sudoedit /etc/nginx/sites-available/ioalab
sudo ln -s /etc/nginx/sites-available/ioalab /etc/nginx/sites-enabled/ioalab
sudo nginx -t && sudo systemctl reload nginx
```

将模板的 `listen 80` 改为 `listen 443 ssl`、`server_name` 改为实际 IP，并在 server 内加入以下两行。保留原 HTTP 验证站点供续期使用；模板中的旧环境变量注释不作为当前配置入口。

```nginx
ssl_certificate /etc/letsencrypt/live/ioalab-ip/fullchain.pem;
ssl_certificate_key /etc/letsencrypt/live/ioalab-ip/privkey.pem;
```

保留模板 `/official/`、上传限制、根路径及 `/ws/`。后两者均以 `proxy_bind 127.0.0.2` 连接核心，并用 `$remote_addr` **覆盖** `X-IOALAB-Client-IP`。不能信任用户送来的同名头或 X-Forwarded-For，也不能将这个代理地址列入本机免限流来源。

最后创建正常续期后的 Nginx 检查/重载钩子和每天两次的检查任务；这不重新部署应用。已有续期任务先核其路径，不创建重复任务。

```bash
sudo tee /usr/local/sbin/ioalab-cert-reload >/dev/null <<'SH'
#!/bin/sh
set -eu
/usr/sbin/nginx -t
/bin/systemctl reload nginx
SH
sudo chmod 700 /usr/local/sbin/ioalab-cert-reload
sudo tee /etc/systemd/system/ioalab-cert-renew.service >/dev/null <<'UNIT'
[Unit]
Description=Renew IoA IP certificate
[Service]
Type=oneshot
ExecStart=/opt/ioalab-certbot/bin/certbot renew --quiet --deploy-hook /usr/local/sbin/ioalab-cert-reload
UNIT
sudo tee /etc/systemd/system/ioalab-cert-renew.timer >/dev/null <<'UNIT'
[Unit]
Description=Check IoA certificate twice daily
[Timer]
OnCalendar=*-*-* 00,12:00:00
RandomizedDelaySec=1800
Persistent=true
[Install]
WantedBy=timers.target
UNIT
sudo systemctl daemon-reload
sudo systemctl enable --now ioalab-cert-renew.timer
sudo /opt/ioalab-certbot/bin/certbot renew --cert-name ioalab-ip --dry-run --run-deploy-hooks --deploy-hook /usr/local/sbin/ioalab-cert-reload
sudo systemctl list-timers ioalab-cert-renew.timer
```

短期证书依赖服务器自己的续期任务，不依赖本机 SSH 会话。ACME 网络异常及已部署实例的专项诊断见部署技能，不能把单次签发当作续期已验。

**6. 安装。** 第一条创建受限输入目录；第二条复制不含密钥的安装选项模板；第三条打开它，核 `platform_config=/etc/ioalab/core/platform.json`、国内 `pypi_index` 与 `max_model_runs=4` 后保存。

安装前核服务器自身能用系统信任链访问公共HTTPS地址，外部机器按第5步所选CA分支验证。部分云主机的EIP不支持本机经云网关回访：外部可连接、本机访问超时，且 `ip route get "$PUBLIC_IP"` 显示经云网关时，可只为本机自己的EIP建立回环路由。域名分支先将`PUBLIC_IP`设为经核验的本机域名A记录地址；以下变量不填写域名。先核同名单位不存在、地址确属本机；不对其他服务器地址配置该路由：

```bash
test ! -e /etc/systemd/system/ioalab-public-loopback.service
IP_COMMAND=$(command -v ip)
sudo tee /etc/systemd/system/ioalab-public-loopback.service >/dev/null <<UNIT
[Unit]
Description=Route this host's own IoA public IP through loopback
Wants=network-online.target
After=network-online.target
Before=nginx.service ioalab-core.service
[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=$IP_COMMAND route replace local $PUBLIC_IP/32 dev lo src 127.0.0.1
ExecStop=$IP_COMMAND route del local $PUBLIC_IP/32 dev lo
[Install]
WantedBy=multi-user.target
UNIT
sudo systemd-analyze verify /etc/systemd/system/ioalab-public-loopback.service
sudo systemctl daemon-reload
sudo systemctl enable --now ioalab-public-loopback.service
curl --noproxy '*' --fail "https://$PUBLIC_IP/api/config"
```

尚未安装核心时可暂时返回 502，但必须先通过证书验证；核心启动后须取得真实配置回执。该路由保留公共 URL、HTTPS 证书与 Nginx 的真实来源覆盖，仅修复本机回访，不证明外部或 CA 可达。公共CA仍连接超时时核来源限制；若选择内部CA，回第5步按专用分支核可信证书链，不关闭校验继续安装。

以下创建输入只用于新装；已有实例沿用原受限安装JSON，不用模板覆盖。

```bash
sudo install -d -m 700 /etc/ioalab-bootstrap
sudo install -m 600 deploy/deployment.json.example /etc/ioalab-bootstrap/deployment.json
sudoedit /etc/ioalab-bootstrap/deployment.json
```

第一条提交独立 systemd 安装任务，SSH 断开后仍继续；第二条查询同一任务，重复查询直到 task.status=completed、lastReadiness.runtimeReady=true，且所属单元及官方服务实际就绪；外层 status=completed 只表示查询成功。失败保留任务、日志和原数据。

```bash
sudo bash deploy/install.sh --config /etc/ioalab-bootstrap/deployment.json
sudo python3.11 -m deploy status --state /var/lib/ioalab
```

完整安装过、已按第3步全停的实例，用以下第一条**替代**上面的 `install.sh`，仍引用原输入和三根。查询原升级任务直到成功，再显式启动并查询：升级保留原运行状态，全停后的实例不会自动重新启动。失败或任务仍在执行时不调用 `start`。

```bash
sudo bash deploy/upgrade.sh --config /etc/ioalab-bootstrap/deployment.json
sudo python3.11 -m deploy status --state /var/lib/ioalab
# 仅确认原升级任务完成后执行：
sudo python3.11 -m deploy start --state /var/lib/ioalab
sudo python3.11 -m deploy status --state /var/lib/ioalab
```

升级与新装均不执行Git更新；保持选定源码不变。`start` 返回 `waiting` 后查同一部署，须核 `runtime.phase=running`、`runtime.runtimeReadinessVerified=true`及各所属组件实际连接，不把任务完成与运行就绪混为一谈。已完成的保数据升级范围见[部署事实](实施资料/部署发行.md#当前验收入口)。

已有 ISC_001 管理员助手的一次性替换：先按上述步骤全停并完成新发行升级，保持停止。以下命令为服务器独立授权腾讯 Agently Mail：终端会给出授权链接，用微信打开并选择自己的 Agent 邮箱，确认授权后等待终端返回 `completed`。Windows 的授权不能代替 Linux 授权；凭据保存在服务器受限目录，不复制到仓库。本项目内部试用邮箱为 `wuming5402@agent.qq.com`，其他部署者应替换成自己的邮箱。

```bash
sudo python3.11 -m deploy mail-login --state /var/lib/ioalab --sender wuming5402@agent.qq.com
sudo python3.11 -m deploy replace-admin-assistant --state /var/lib/ioalab
sudo python3.11 -m deploy start --state /var/lib/ioalab
sudo python3.11 -m deploy status --state /var/lib/ioalab
```

替换命令停用旧身份并撤下其两个接口，归档旧实例后新建 admin 助手；不迁移旧身份、密钥、会话或收信规则，ISC_001 账号及余额保留。正常启动先准备新助手，再启动原生宿主与后台 SDK。邮箱授权与刷新显式直连，固定官方 CLI 经摘要校验安装；预约邀请同时发给管理员和该次请求的本人邮箱。必须分别核对真实提交、双方收件与 Outlook 邀请识别；提交不表示接受。配置邮箱后用正常 `stop`、`start` 应用，已提交或结果未知的历史邀请不重发。

**7. 检查并访问。** 第一条检查核心回环接口；第二条读取核心最近日志。然后用浏览器访问第4步配置的公共 HTTPS 地址，以自己的管理员密码登录。

```bash
curl --noproxy '*' --fail http://127.0.0.1:8750/api/config
sudo journalctl -u ioalab-core.service -n 30 --no-pager
```

在另一台机器访问同一公共地址：公共CA使用默认信任链；内部CA的curl显式指定经核验的公共CA文件（`--cacert <CA文件>`），SDK用受审包内资源。域名匹配DNS SAN、IP匹配IP SAN，不加 `-k`。再核 HTTPS 首页、登录权限、官方目录及登录后的实时 WebSocket，分别记录成功与失败。公网伪造客户端来源头不能取得本机豁免；回环 SDK 请求的豁免也需单独验证。仅核心接口 200 或 Nginx 不再 502 不代表整套应用就绪。

管理员九问只监听回环。在本机另开终端，以下命令把服务器网页转发到本机；保持终端运行，再打开 `http://127.0.0.1:18753/?user_id=ioa-admin`。

```powershell
ssh -o ProxyCommand=none -o ProxyJump=none -N -L 18753:127.0.0.1:18753 root@SERVER_IP
```

分别检查平台实际模型检索、官方宿主无业务问答和个人助手无业务问答，不以配置存在代替三类模型已可调用。未配置邮件时会议通知保持禁用。

三席在线试用是独立应用，不能靠填平台 key 自动开通。供应商 key 只归模型 sidecar，席位仅持本轮 token 和内网代理地址。当前尚缺完整实机就绪与常规开通交接，本教程不将其写成已经开放；纳入常规交付时须在本节补齐已验证的创建、模型、HTTPS及检查命令，不要求读者另找必需步骤。
