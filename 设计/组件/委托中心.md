# 委托中心

## 目的与范围

提供 A2C 模板签认、合同认证、公共存证、信誉与仲裁服务，并维护 IoA 接单容量台账。合同字段、签名链、成约方式、期限及验收器直接遵守上游 A2C SDK，依据版本见[设计索引](../README.md)。

服务发现归[注册中心](平台/注册中心/接口.md)，付款归[支付中心](平台/支付中心/接口.md)，生产与委托方验收在参与方本地完成。平台不代参与方签字、验收或执行服务生产。

## 职责与数据

| 数据 | 权威与约束 |
|---|---|
| 模板/合同公共证据 | 保存原签名对象、摘要及认证结果；不重写字段或自建第二套合同状态机 |
| 接单台账 admission | 预留 ID、服务/发起身份、请求或合同摘要、状态、期限与付款/任务关联；属于 IoA 运行数据 |
| 仲裁文书 | 验证证据后独立签署并引用合同摘要，不写入合同卡 |
| 信誉 | 从可验证结清与裁定导出；实验交易如实标记，不填充虚构历史 |

服务方端 SDK 决定是否愿意接单，向委托中心申请预留、提交、查询及释放；平台负责并发原子性，本地只保存镜像。admission、交互 UUID、连接和会话信息都不增加 A2C 合同字段。

## 成约方式与接单容量

普通用户服务默认待批准或提案模式。预批准仍是 A2C 合法模式，但本期普通服务接入不启用；没有原子容量保证时不能绕过预留直接成约。各模式复用 A2C 的同一合同与算价规则。

| 模式 | 比较阶段可取得的对象 | 用户具体确认与成约时点 |
|---|---|---|
| 提案 | 服务方签2、市场签3的正式提案卡 | 用户选择并确认该卡后，委托方签1采纳，才形成合同 |
| 待批准 | 依据有效模板确定算价的未签卡，明确标为待服务方批准 | 用户选择并确认具体卡后才发起接单预留、签1和复签请求；服务方签2即形成合同 |

不得为横向比较而向多个待批准候选先请求复签，再让用户选一家；那会提前形成多份合同。候选报价的可比对象见[个人助手端 SDK](../接入/个人助手端SDK.md)，不能要求先成约才满足比较门槛。

容量单位是**尚可能独立成约的承诺或未结束合同**，并包括有效短期预留；不是模型线程数。一个交互若发出多份同时有效的承诺本应分别计数；本期通过限制同一交互只保留一个未结束承诺简化管理，不能在旧承诺仍有效时另发替代版本。

| 台账状态 | 含义与计数 |
|---|---|
| held | 尚未开始付款或有效签署的短期预留，绑定 holdUntil；计入容量 |
| committed | 付款或有效承诺已开始，后续按真实业务终态核实；计入容量 |
| released | 已核实安全释放，不再计入容量；保留历史关联 |

平台在同一事务核容量并创建预留；相同请求重传返回原记录，不能占用多个名额。服务方配置的 max_active_delegations 与[本地接入组件](本地接入组件.md)的 max_model_runs 分别控制接单与模型并发。

## 预留、付款与签署规则

| 阶段 | 不变量 |
|---|---|
| 离线意向 | 可按消息 TTL 排队；不承诺接单、不支付拟卡费、不声明成约 |
| 建立交互 | 只确定双方关联，不授予容量；须继续由服务方决定并向平台申请预留 |
| 申请预留 | 绑定服务、发起者、交互及待提交请求摘要/待批准卡摘要；换对象须重新检查，不能复用原资格 |
| 返回预留 | 服务方可靠返回预留 ID、绑定摘要和截止；发起端核实际回执后才能进入正式请求 |
| 待批准 | 用户已确认具体卡、原绑定摘要与委托方签1均有效后，服务方业务审查并复核期限，提交预留，再签2；不能先签后补容量 |
| 有拟卡费提案 | 先预留，由支付入口核绑定和有效期，在平台应用事务内提交预留并执行 AP2，取回原凭证后签请求 |
| 无拟卡费提案 | 不创建虚假支付；服务方输出有效签名承诺前仍须提交预留 |
| 提案输出 | 复核响应期限与预留，持久化签署检查点，再签署及请求市场认证；模型、排队、断线均计入原期限 |
| 暂停 | 新预留以service_paused明确拒绝，委托方将其作为业务拒绝结束，不保持unknown；既有原预留重传不重新占用或检查新开关 |
| 满额 | 拒绝新增预留；已有委托的授权、交付、验收、付款、解除和恢复照常处理 |
| 等待用户 | 接单名额继续占用，模型执行名额可以释放 |

预留资格、付款唯一性及有效期由平台内明确应用事务协调；支付中心不自行决定接单。服务方输出结果未知时保留 committed，并查询原签名/任务，不能另签一份承诺来掩盖失败。

准备请求摘要须使用 A2C 原语，不自行修改摘要算法。正式签署仍须遵守请求新鲜度；消息中心的持久投递不能延长 A2C 时间窗口。

## 意向与容量控制契约

| 对象/操作 | 规则 |
|---|---|
| 委托意向 | 绑定 formation、templateDigest、scopeDigest、bindingDigest 及原未签 request 或 card；摘要使用 A2C 原语。模板必须为该服务当前有效公示，主体、币种和支付方须匹配授权与平台 |
| 意向登记 | 消息中心负责投递；委托中心保存业务绑定。分类授权使用注册中心实际归属，不依赖在线状态；是否执行另外检查 |
| 交互建立 | 原接收端本地生成 UUID 并随 interaction.opened 返回；平台不可变登记原意向、双方、类型及绑定摘要，后续预留和付款均使用同一关系 |
| admission.configure | 服务当前执行连接提交expectedRevision、maxActiveDelegations、accepting；上限为1—1000。平台策略是实际接单开关与容量的唯一权威，只影响此后新增预留，不取消已有有效held、committed或合同；暂停不阻止原有效预留提交，原期限、在线、授权及协议检查仍执行 |
| admission.reserve | 仅该服务当前连接可申请；绑定已开始的原意向与交互，校验当前授权、公示和接单策略；同一交互/协议绑定只有一份原预留 |
| 预留期限 | held 默认最长120秒，且不超过意向、模板及本轮用户许可截止；到期先关闭未付费/未签署资格再释放；重试不延长原截止 |
| admission.commit | 仅零拟卡费提案或待批准使用；待批准还须核具体选择、委托方签1及原卡，提交后才能签2。有拟卡费提案必须走协调付款入口 |
| ap2.pay 控制 | 外层含 admissionId 与原 ap2 body；当前委托方连接提交，平台准备 AP2 校验后，在同一短事务内复核双方租约、原绑定、范围预算与预留并过账；返回原 AP2 响应 |
| 原结果恢复 | admission 自有操作与付款关联按业务生命周期保存；普通消息清理不删除活动预留及原付款事实。恢复原结果不重新检查已经完成动作的当前许可，也不重新执行 |

新接入服务的公网 AP2 地址不得绕过外层交互、执行代次与 admission；SDK 传输适配通过当前长连接提交原 AP2 body，不增 AP2 字段。有效范围授权不等于具体合同确认；待批准意向只有在用户选定原卡后才可预留。未完成的执行、签署或付款保持明确未就绪。

## 原协议执行适配

委托中心核对原交互、admission、调用方向及协议对象绑定；接收端复用原 A2C Provider/Client 执行，不在平台复制合同状态机。服务端每个交互单独保存协议 Store、任务与宿主 Session；同一服务的多个交互可并行，本单控制消息不能因其他委托等待模型而阻塞。

待批准的签1卡可在 held 仍有效时投递并取得审查开始许可。该许可仅允许审查；SDK 在原 Provider 的审查回调通过后提交 admission，成功后才返回批准并允许原 SDK 签2。提交失败或预留到期则拒绝，不产生签2。平台返回含签2的结果前复核 committed、原签1与绑定卡及服务方签名；不能要求“提交后才投递签1”，造成双方相互等待。提案正式请求仍须先完成拟卡费或零费用的容量提交。

正式提案的市场签3也须核已提交 admission 与原 requestDigest，不能从公共签认入口绕过零拟卡费提交。首次取得有效合同卡后固定其 cardDigest；已接受 work.start 的未知结果按可能已开始处理，直到真实结清或合法终态核实，不按模型“完成”释放名额。协议期限使用签名原件判断，投递或上传不能刷新时效。

委托中心保存正式请求的签名原件、实际接收开始事实及首次签认卡绑定，保留期随接单业务，不依赖临时消息正文。签认操作经当前服务连接调用；准备与最终提交间发生断线接管、撤权或期限变化时拒绝新提交。市场快照和原签3回执一起提交，提交失败不留下可用的另一份承诺。已成功的原签认恢复不重新签署，也不因后续撤权改写原事实。

履约首次接收有效成约卡时，核对原接单、已选 cardDigest、固定的签1/2/3及归属，保存冻结模板、合同和证据。后续原任务继续依据这些事实，不再使用新候选的当前公示、意向 TTL 或范围“尚未选择”检查。首次 work.start 仍核原开工窗口；其开始许可或真实回执一经保存，未知结果按可能已开始处理。环节请求及答复必须绑定原卡、原交付任务和卡载用户密钥，不能只接受任意自签的 jwk。

个人助手在确认成约后通过 contract.bind 登记原有效卡，不以已有开工或定金回执为前提；第一次合法合同 checkout 及 work.start 须核实同一登记。服务方通过原 Provider.bind_contract 接收本单生效签1，不触发生产。冻结原件与原 Task/环节请求属于委托中心的权限依据，不是另设一套履约状态机。新候选资格与既有合同权限分开核验；平台公共 HTTP 原市场入口不能绕过同一接单与结清约束。

存证按合同与期次保存不可替换的原清单、签4及签5；准备与提交分开，最终复核当前执行代次和已有证据前缀。同一原操作恢复原签5，不能签出同一期另一份清单。结清复用原 Market 校验，并核对相应定金/分期/解除的实际过账凭证；原结清日志、接单释放与关闭通知同一应用事务提交。市场信誉只能引用该真实日志，不能由服务方自报次数或仅凭“模型完成”增加。

## 承诺窗口与释放

| 情况 | 释放前必须满足 |
|---|---|
| held 到期 | 尚未付款或有效签署；原子关闭原付款/签署资格后释放 |
| 待批准已签2、未开工 | 至少保留至签2时刻 + startWithin，再按 A2C 核未开工及终态 |
| 待批准已提交但签2未知 | 保留原签1 + respondWithin + startWithin 的可能承诺窗口，并核无已获许可的开工；不能把缺少本地签2当作未签署证明 |
| 提案已签3、未开工 | 至少保留至签3时刻 + respondWithin + startWithin；只等响应窗口结束不够 |
| 已开工 | 依据 A2C 终态和必要凭证核实，不因失联或模型结束释放 |
| 已付拟卡费但无承诺 | 明确拟卡拒绝/失败或期限结束；先关闭原入口并核无在途有效签名，再结束预留；保留实际付款凭证 |
| 付款或签署未知 | 先查原操作、凭证、任务及签名；保留 committed，不按 holdUntil 自动释放 |
| 未中选提案 | 用户页面选择不撤销协议承诺；保留至合法窗口关闭 |

已签认但未中选的提案由现有维护循环核实：原请求、模板、签2/3和协议终局回执完整，已超过签3 + respondWithin + startWithin，且该卡未被平台选择、未登记合同、未获开工许可、无合同付款或在途/未知协议调用时，才能自动释放。接单释放、原意向关闭、交互关闭及双方可靠通知必须同一事务提交；保留原提案和实际拟卡费，不生成结清、裁定或信誉。缺证据或任一条件不满足时保留 committed，不能按本地计数、在线状态或模型说明释放。

无法自动核实的情况进入待核实，不以清库或手动改本地计数释放。服务重启先对账再接新单；活动 admission 按业务生命周期保存，不受普通消息元数据清理影响。

## 验收、仲裁与证据

| 项目 | 规则 |
|---|---|
| 验收器分发 | 按摘要寻址，SDK 解析包地址并核摘要；包只在 A2C WASM 沙箱执行 |
| 正常验收 | 委托方使用自己的模型执行 L2；模型观察，验收器程序判定；平台不替用户签7 |
| 仲裁模型 | disputeModels 仅用于仲裁复算，须来自部署方明确登记的集合；缺配置拒签相应模板 |
| 争议受理 | 核当事方归属、合同签名链、交付摘要与验收报告，不接受任意第三方冒名申请 |
| 裁定 | 独立文书引用合同摘要；不直接触发付款 |
| 信誉 | 服务方提交原结清卡，复用 A2C card.close 核签名链与结局，再按可验证结果签发信誉条目；接口不接受自报成功次数，助手通信不记成交易信誉 |

卡载金额、亲签条款、验收及支付依据按 A2C 原义处理。模板轮换只影响新签约，旧模板与原验收依据须保留，官方服务的轮换策略见[官方实例](../工程/官方实例.md#模板有效期与轮换)。

## 争议案件与原证据

仲裁由本中心拥有案件、证据快照、评估与裁定；不复制A2C合同状态机。接单台账提供原承诺/请求，合同权威提供原卡/签名/回执，协议转发提供完整原请求及全部进展，支付中心提供实际原凭证。各模块经只读证据接口协作，不依据监控投影或模型描述判案。取证不执行验收器、模型、付款或业务，不更新原合同。

| 对象 | 规则 |
|---|---|
| 争议对象 | 以原admissionId关联；subject区分contract与proposal-request及其原摘要。拟卡费超时可能尚无合同，不伪造卡或合同结清日志 |
| 预览 | 返回原对象、理由、期次、assessedAt、截止、eligible、route、依据摘要及缺少的材料；只是当前取证，不创建案件或批准 |
| 案件标识 | 平台生成caseRef，受理时持久保存并返回双方；后续查询、材料、通知和结束回执均引用它，不增加A2C字段 |
| 原申请 | 相同身份/operationId的同内容恢复原案件，异内容拒绝。同一admission只受理一个终止型案件；换理由、期次、操作或申请方不能另起并行裁定。双方通过原admission取得已有caseRef，新申请不复算或覆盖它 |
| 案件状态 | queued、evaluating、needs_review、unknown、ruled；申请和受理不是裁定。无效或尚不成立的理由在受理前拒绝；正式案件的程序/人工终局均为ruled，不另建撤案重开引擎 |
| 完整历史 | 读取原协议请求及全部已受理进展，按原签名请求摘要去重环节并关联原答复；不能只读最后一个step或用空steps/vouchers代替历史。保留期不足须明确history_gap |
| 证据完整性 | 核原双方身份、模板/请求/合同签名、真实存证前缀、失败报告原签名及实际凭证；已签历史按原时刻验证，当前模板过期不使旧合同证据失效 |

| 理由 ground | 申请方与必须成立的事实 | 处理路径 |
|---|---|---|
| acceptance-failed | 委托方；本期原签5、原清单、委托方亲签失败报告及摘要匹配的交付件 | 市场按签认快照调用原A2C recompute；模型只观察，程序裁定 |
| start-overdue | 委托方；原有效卡超过startWithin，确无有效接单回执 | 按原start_deadline判断，不要求存在交付记录 |
| deliver-overdue | 委托方；原接单回执、完整环节停表记录，本期无签5或实际签5晚于deliver_deadline | 复用原期限函数，不忽略等待授权的时间 |
| accept-overdue | 服务方；签5后超过acceptWithin，既无签7也无亲签失败报告 | 按原accept_deadline判断，失败报告不能算拖延验收 |
| payment-overdue | 服务方；本期原签5/签7、正额应付款，超过respondWithin仍无实际付款凭证 | 已付及零额不成立；不因客户端漏存凭证宣称未付 |
| authorize-overdue | 服务方；合法原环节请求超过authorizeWithin，确无原答复 | 按实际请求及全部答复判断 |
| proposal-overdue | 委托方；原提案请求实际已提交、实际拟卡费已付，超过respondWithin无正式答复 | 请求摘要为对象；仅付款而未提交请求不成立 |
| fetch-failed、declaration-mismatch、authorize-refused | 原取件调用、拒收文书/材料或原拒绝答复，不能仅用网络异常或布尔值推断因果 | 不能由原程序直接判断的因果交独立人工复核 |
| termination-refund、termination-compensation | 原解除、真实定金/退款及报价；单方补偿须遵守原A2C本期上限 | 不凭空增加退款时限或自动确定补偿，由独立人工复核 |

原recompute返回的pass/fail直接遵守A2C语义，包括其将仲裁时仍pending、验收器程序错误或无效认证原件归为fail；不得另改判据。尚未完成原复算的快照缺失、运行资源或平台调用异常不构成裁定，保留原案件和检查点待核实，不自动重调模型或指定责任方。

复算不持数据库事务。提交终局前重新核对证据摘要及最新权威事实，事实变化则待核实，不用旧快照压过已存在的真实签7、付款或解除。人工复核只由非本案当事账号的网页管理员执行，限本案提交的证据，记录实际操作者与明确理由；SDK、模型及后续运维助手不能替人裁决。

### 材料与复核边界

| 边界 | 要求 |
|---|---|
| 材料快照 | 申请携带本案所需材料分组和完整文件引用，受理时冻结。核原上传身份、就绪状态、名称、摘要、大小和实际字节；所有分组合计沿用消息附件最多32项及单文件/账号配额，不接受URL或服务端路径 |
| 已收到的文件 | 收到读取权不等于可以再次转授原引用。SDK使用本机已获准读取的原字节，按本次用户确认另建所属上传引用；不能把其他账号的fileId直接报送或共享 |
| 交付复算 | deliveryFiles必须与本期原签4清单的文件名/摘要集合完全一致；原程序仍核实际字节，不接受另一份卡或模型说明代替交付件 |
| 后续读取 | 材料属于冻结申请，不提供追加后重试挑结果的接口。双方只能读取本案件；非当事网页管理员只读本案提交的证据。不能据此取得原账号的其他私有文件或消息正文 |
| 人工入口 | 管理员先取得案件列表及本案证据，再按原依据摘要复核或明确重评；每次读取和提交均核当前角色及非本案当事身份，记录实际操作者。本案授权不等于全局消息审计权限 |
| 固定模型 | 固定原卡的disputeModels及受理时部署登记的非凭据模型映射摘要。恢复或明确重评前核同一映射；改变登记时停止并核实原资源，不默换模型。密钥轮换不进入该摘要或案件公开内容 |

字段和入口只在[平台接口](../接入/平台接口/仲裁接口.md#仲裁接口)定义；本中心拥有材料、尝试和文书，不从网页参数或观察投影反向推定原事实。

### 复核依据与决定证据

| 依据 | 规则 |
|---|---|
| 冻结申请 | 原申请、原basisDigest、材料和已知程序结果保持不变；不追加材料或重写原结果 |
| 当前事实 | 原事实收集与理由成立判断分开。案件详情可读取同一admission最新已验证的卡、签名、环节、实际付款及协议进展；已验收或已付款导致原理由不再成立，不阻止独立管理员查看这些真实事实 |
| 复核确认 | 管理员看到冻结申请、已知结果和当前事实后，提交其实际看到的复核依据摘要。提交事务内重收集并比较；事实、程序结果或案件状态变化时拒绝旧确认，不以冻结申请摘要冒充当前依据 |
| 复核条件 | 仅needs_review或unknown且本案没有活动评估writer时允许人工复核；queued/evaluating继续原评估，ruled只恢复原文书。独立网页账号、明确理由和原操作幂等回执必须同时满足 |
| 程序判据 | 已知程序结果不删除、不重算或翻转，人工只可沿原归责或明确中立。尚无完整复算结果时只可中立或按原模型明确重评，不能凭人工意见补出验收pass/fail；确定性理由可沿当前原期限判据复核，理由已消解只能中立。因果复核类仍由独立管理员依据实际材料说明归责 |
| 最终决定 | 案件另存决定时的实际原事实，含当前市场结局；仍未结束的原卡调用A2C record_ruling，可补付义务以决定时真实原卡为准。原申请快照仍保留，不能漏掉申请后的签7或协商解除 |
| 已有合法终态 | 原卡已正常结清/解除结清时，案件仅可中立；保留原市场结局、信誉及已释放容量，不再次record_ruling或释放，案件执行状态标为已结束。已有其他裁定时拒绝覆盖，明确核实原文书 |
| 公开证据 | 双方与管理员可核对决定证据的公开视图及其签名绑定摘要；原AP2请求凭据和私人传输封套不公开。SDK从公开视图重新计算摘要，核其原合同身份/签名及本单引用，不只相信摘要字符串相等 |

无卡请求保持原subject；原respondWithin之后不得新签认正式提案，已有正式答复也不能再按未答复受理。取证与承诺检查使用同一权威时钟，不增加请求转合同的案件迁移流程。

人工补偿只允许在原单方解除补偿案件中明确提出；金额为非负十进制定数，不超过原卡该未验收期金额，币种与原卡一致。它只是裁定说明，不进入AP2自动付款。字段和摘要边界见[平台接口](../接入/平台接口/仲裁接口.md#仲裁接口)。

### 评估所有权与核实

Core数据所有权先按[部署](../工程/安装与升级/进程与数据.md#平台核心的数据所有权)取得，再恢复案件。queued可开始评估；前一实际Core写入者退出后遗留的evaluating转unknown，不自动再次调用模型。原评估结果先持久保存，后续只恢复该结果的提交；重复申请、重启或换发起方都不能重算挑结果。

独立网页管理员只能对没有已知结果、原评估writer已结束的unknown案件显式重新评估，保存尝试、操作者和原因；材料、原依据摘要及固定模型集合不得改变。已知程序结果和已签文书不得重试；这不是通用SDK强制重跑能力。人工复核不推翻相同依据下已完成的程序判据。

人工复核可明确liable=none，表示双方均不归责，不伪称程序通过或失败；仍为终局裁定并终止原卡。中立文书本身不新增服务方失败或完成，不进入成功率分母；原已合法结清的信誉保留。无合同卡的原请求裁定由案件所有者提供可验证结果，归责明确时只计一次信誉，不写伪造合同ledger或与同一义务重复计数。

## 裁定、执行与容量收尾

| 阶段 | 规则 |
|---|---|
| 终局提交 | 冻结决定证据、原裁定、A2C市场结局及双方可靠contract.ruling通知由同一应用事务提交；仍未结束的已成约卡用决定时真实原卡调用record_ruling，已有合法终态按上文保留，未成约请求不冒充合同ledger |
| 合同最终性 | 裁定终止原卡，拒绝新增开工、交付、环节、验收及新定金；不能用新的操作ID重启本卡。双方继续合作须新卡 |
| 资金 | 裁定不触发划转；冻结原卡中已签5/签7的应付款及已有协商解除余额仍按原AP2和有效用户许可处理。不得补付被裁定禁止的新定金、接受新签7或用裁定新增付款用途 |
| 本地收敛 | SDK确定性消费原裁定，停止未开始工作，等待原模型/生产/工具实际writer结束；未知效果保留名额和原证据，不把断线、停止请求或超时当结束 |
| 结束回执 | 原服务方提交caseRef及原执行关联；平台核裁定、实际writer/原协议Task收敛，以及冻结卡的上述原应付款齐全后，原子释放容量并关闭交互。原Task可真实canceled，不伪报正常完成；不调用Provider.close或造解除。裁定新增补偿不自动过账，也不伪装为原AP2应付款 |
| 恢复 | 同一裁定、通知及结束动作沿原记录恢复；执行结束与债务已付分别展示，未核实原效果时不释放。一个义务最多一份终局裁定 |

## 异常与恢复

| 情况 | 处理 |
|---|---|
| 预留响应丢失 | 按原请求查询台账，恢复原预留，不重复占位 |
| 正式请求过期 | 返回协议错误；发送端先核未知效果及授权，再准备新的合法请求，不改旧签名时间 |
| 认证或输出未知 | 保留原签署检查点与 committed，查原任务/合同，不另造签名承诺 |
| 结果延迟读取 | 按原协议核验结果；不能一概要求重签已有效结果 |
| 通信关闭请求 | 已成约必须依据合同终态，未成约也须核承诺与费用；投递关闭不能替代业务解除 |

## 解除的事实与释放

解除依据归本中心：不可变原成约卡、单调推进的已核签名链、按摘要保留的原解除报价及通知。合法旧前缀只记历史、不回退当前进展，分叉或替换原件拒绝；显示投影不能反向成为权限依据。平台只接受已绑定双方在同一交互提交的原件；单方和协商解除复用 A2C 校验，不能关闭通信来替代解除。原验收及市场存证只增不退；解除后拒绝新的履约开始及追加证据。

结清前分别核协议终态、原执行收敛和实际应付款。未开工合同不要求伪造开始许可；没有交付时不要求空存证，已有交付则核真实前缀。解除款按实际已付定金确定方向，负余额缺退款不得结清；单方解除不按裁定自动过账。未知开工、生产或工具效果继续占用，待原执行者核实后收尾。结清、释放容量及关闭通知同一事务，信誉只消费原结清日志。具体跨端顺序见[A2C适配](../接入/A2C适配.md#解除与结清)。
