# 委托中心

## 目的与范围

提供 A2C 模板签认、合同认证、公共存证、信誉与仲裁服务，并维护 IoA 接单容量台账。合同字段、签名链、成约方式、期限及验收器直接遵守上游 A2C SDK，依据版本见[设计索引](../README.md)。

服务发现归[注册中心](注册中心.md)，付款归[支付中心](支付中心.md)，生产与委托方验收在参与方本地完成。平台不代参与方签字、验收或执行服务生产。

## 职责与数据

| 数据 | 权威与约束 |
|---|---|
| 模板/合同公共证据 | 保存原签名对象、摘要及认证结果；不重写字段或自建第二套合同状态机 |
| 接单台账 admission | 预留 ID、服务/发起身份、请求或合同摘要、状态、期限与付款/任务关联；属于 IoA 运行数据 |
| 仲裁文书 | 验证证据后独立签署并引用合同摘要，不写入合同卡 |
| 信誉 | 从可验证结清与裁定导出；实验交易如实标记，不填充虚构历史 |

服务方端 SDK 决定是否愿意接单，向委托中心申请预留、提交、查询及释放；平台负责并发原子性，本地只保存镜像。admission、交互 UUID、连接和会话信息都不增加 A2C 合同字段。

## 成约方式与接单容量

普通用户服务默认待批准或提案模式。预批准仍是 A2C 合法模式，但本期普通服务接入不启用；没有原子容量保证时不能绕过预留直接成约。各模式复用 A2C 的同一合同与算价规则。

| 模式 | 比较阶段可取得的对象 | 用户具体确认与成约时点 |
|---|---|---|
| 提案 | 服务方签2、市场签3的正式提案卡 | 用户选择并确认该卡后，委托方签1采纳，才形成合同 |
| 待批准 | 依据有效模板确定算价的未签卡，明确标为待服务方批准 | 用户选择并确认具体卡后才发起接单预留、签1和复签请求；服务方签2即形成合同 |

不得为横向比较而向多个待批准候选先请求复签，再让用户选一家；那会提前形成多份合同。最低候选报价数的统计与可比对象见[个人助手端 SDK](../接入/个人助手端SDK.md)，不能要求先成约才满足比较门槛。

容量单位是**尚可能独立成约的承诺或未结束合同**，并包括有效短期预留；不是模型线程数。一个交互若发出多份同时有效的承诺本应分别计数；本期通过限制同一交互只保留一个未结束承诺简化管理，不能在旧承诺仍有效时另发替代版本。

| 台账状态 | 含义与计数 |
|---|---|
| held | 尚未开始付款或有效签署的短期预留，绑定 holdUntil；计入容量 |
| committed | 付款或有效承诺已开始，后续按真实业务终态核实；计入容量 |
| released | 已核实安全释放，不再计入容量；保留历史关联 |

平台在同一事务核容量并创建预留；相同请求重传返回原记录，不能占用多个名额。服务方配置的 max_active_delegations 与[本地接入组件](本地接入组件.md)的 max_model_runs 分别控制接单与模型并发。

## 预留、付款与签署规则

| 阶段 | 不变量 |
|---|---|
| 离线意向 | 可按消息 TTL 排队；不承诺接单、不支付拟卡费、不声明成约 |
| 建立交互 | 只确定双方关联，不授予容量；须继续由服务方决定并向平台申请预留 |
| 申请预留 | 绑定服务、发起者、交互及待提交请求摘要/待批准卡摘要；换对象须重新检查，不能复用原资格 |
| 返回预留 | 服务方可靠返回预留 ID、绑定摘要和截止；发起端核实际回执后才能进入正式请求 |
| 待批准 | 用户已确认具体卡、原绑定摘要与委托方签1均有效后，服务方业务审查并复核期限，提交预留，再签2；不能先签后补容量 |
| 有拟卡费提案 | 先预留，由支付入口核绑定和有效期，在平台应用事务内提交预留并执行 AP2，取回原凭证后签请求 |
| 无拟卡费提案 | 不创建虚假支付；服务方输出有效签名承诺前仍须提交预留 |
| 提案输出 | 复核响应期限与预留，持久化签署检查点，再签署及请求市场认证；模型、排队、断线均计入原期限 |
| 满额 | 拒绝新增预留；已有委托的授权、交付、验收、付款、解除和恢复照常处理 |
| 等待用户 | 接单名额继续占用，模型执行名额可以释放 |

预留资格、付款唯一性及有效期由平台内明确应用事务协调；支付中心不自行决定接单。服务方输出结果未知时保留 committed，并查询原签名/任务，不能另签一份承诺来掩盖失败。

准备请求摘要须使用 A2C 原语，不自行修改摘要算法。正式签署仍须遵守请求新鲜度；消息中心的持久投递不能延长 A2C 时间窗口。

## 意向与容量控制契约

| 对象/操作 | 规则 |
|---|---|
| 委托意向 | 绑定 formation、templateDigest、scopeDigest、bindingDigest 及原未签 request 或 card；摘要使用 A2C 原语。模板必须为该服务当前有效公示，主体、币种和支付方须匹配授权与平台 |
| 意向登记 | 消息中心负责投递；委托中心保存业务绑定。分类授权使用注册中心实际归属，不依赖在线状态；是否执行另外检查 |
| 交互建立 | 原接收端本地生成 UUID 并随 interaction.opened 返回；平台不可变登记原意向、双方、类型及绑定摘要，后续预留和付款均使用同一关系 |
| admission.configure | 服务当前执行连接提交 expectedRevision、maxActiveDelegations、accepting；上限为 1—1000。只影响新接单，不取消已有承诺；SDK 未就绪时不得宣称可接单 |
| admission.reserve | 仅该服务当前连接可申请；绑定已开始的原意向与交互，校验当前授权、公示和接单策略；同一交互/协议绑定只有一份原预留 |
| 预留期限 | held 默认最长120秒，且不超过意向、模板及本轮用户许可截止；到期先关闭未付费/未签署资格再释放；重试不延长原截止 |
| admission.commit | 仅零拟卡费提案或待批准使用；待批准还须核具体选择、委托方签1及原卡，提交后才能签2。有拟卡费提案必须走协调付款入口 |
| ap2.pay 控制 | 外层含 admissionId 与原 ap2 body；当前委托方连接提交，平台准备 AP2 校验后，在同一短事务内复核双方租约、原绑定、范围预算与预留并过账；返回原 AP2 响应 |
| 原结果恢复 | admission 自有操作与付款关联按业务生命周期保存；普通消息清理不删除活动预留及原付款事实。恢复原结果不重新检查已经完成动作的当前许可，也不重新执行 |

新接入服务的公网 AP2 地址不得绕过外层交互、执行代次与 admission；SDK 传输适配通过当前长连接提交原 AP2 body，不增 AP2 字段。有效范围授权不等于具体合同确认；待批准意向只有在用户选定原卡后才可预留。未完成的执行、签署或付款保持明确未就绪。

## 原协议执行适配

委托中心核对原交互、admission、调用方向及协议对象绑定；接收端复用原 A2C Provider/Client 执行，不在平台复制合同状态机。服务端每个交互单独保存协议 Store、任务与宿主 Session；同一服务的多个交互可并行，本单控制消息不能因其他委托等待模型而阻塞。

待批准的签1卡可在 held 仍有效时投递并取得审查开始许可。该许可仅允许审查；SDK 在原 Provider 的审查回调通过后提交 admission，成功后才返回批准并允许原 SDK 签2。提交失败或预留到期则拒绝，不产生签2。平台返回含签2的结果前复核 committed、原签1与绑定卡及服务方签名；不能要求“提交后才投递签1”，造成双方相互等待。提案正式请求仍须先完成拟卡费或零费用的容量提交。

正式提案的市场签3也须核已提交 admission 与原 requestDigest，不能从公共签认入口绕过零拟卡费提交。首次取得有效合同卡后固定其 cardDigest；已接受 work.start 的未知结果按可能已开始处理，直到真实结清或合法终态核实，不按模型“完成”释放名额。协议期限使用签名原件判断，投递或上传不能刷新时效。

委托中心保存正式请求的签名原件、实际接收开始事实及首次签认卡绑定，保留期随接单业务，不依赖临时消息正文。签认操作经当前服务连接调用；准备与最终提交间发生断线接管、撤权或期限变化时拒绝新提交。市场快照和原签3回执一起提交，提交失败不留下可用的另一份承诺。已成功的原签认恢复不重新签署，也不因后续撤权改写原事实。

履约首次接收有效成约卡时，核对原接单、已选 cardDigest、固定的签1/2/3及归属，保存冻结模板、合同和证据。后续原任务继续依据这些事实，不再使用新候选的当前公示、意向 TTL 或范围“尚未选择”检查。首次 work.start 仍核原开工窗口；其开始许可或真实回执一经保存，未知结果按可能已开始处理。环节请求及答复必须绑定原卡、原交付任务和卡载用户密钥，不能只接受任意自签的 jwk。

原 SDK 可能在 work.start 前取得合同付款 checkout，故首次合法 checkout 同样可以登记成约证据；不以已有开工回执为前提。冻结原件与原 Task/环节请求属于委托中心的权限依据，不是另设一套履约状态机。新候选资格与既有合同权限分开核验；平台公共 HTTP 原市场入口不能绕过同一接单与结清约束。

存证按合同与期次保存不可替换的原清单、签4及签5；准备与提交分开，最终复核当前执行代次和已有证据前缀。同一原操作恢复原签5，不能签出同一期另一份清单。结清复用原 Market 校验，并核对相应定金/分期/解除的实际过账凭证；原结清日志、接单释放与关闭通知同一应用事务提交。市场信誉只能引用该真实日志，不能由服务方自报次数或仅凭“模型完成”增加。

## 承诺窗口与释放

| 情况 | 释放前必须满足 |
|---|---|
| held 到期 | 尚未付款或有效签署；原子关闭原付款/签署资格后释放 |
| 待批准已签2、未开工 | 至少保留至签2时刻 + startWithin，再按 A2C 核未开工及终态 |
| 待批准已提交但签2未知 | 保留原签1 + respondWithin + startWithin 的可能承诺窗口，并核无已获许可的开工；不能把缺少本地签2当作未签署证明 |
| 提案已签3、未开工 | 至少保留至签3时刻 + respondWithin + startWithin；只等响应窗口结束不够 |
| 已开工 | 依据 A2C 终态和必要凭证核实，不因失联或模型结束释放 |
| 已付拟卡费但无承诺 | 明确拟卡拒绝/失败或期限结束；先关闭原入口并核无在途有效签名，再结束预留；保留实际付款凭证 |
| 付款或签署未知 | 先查原操作、凭证、任务及签名；保留 committed，不按 holdUntil 自动释放 |
| 未中选提案 | 用户页面选择不撤销协议承诺；保留至合法窗口关闭 |

无法自动核实的情况进入待核实，不以清库或手动改本地计数释放。服务重启先对账再接新单；活动 admission 按业务生命周期保存，不受普通消息元数据清理影响。

## 验收、仲裁与证据

| 项目 | 规则 |
|---|---|
| 验收器分发 | 按摘要寻址，SDK 解析包地址并核摘要；包只在 A2C WASM 沙箱执行 |
| 正常验收 | 委托方使用自己的模型执行 L2；模型观察，验收器程序判定；平台不替用户签7 |
| 仲裁模型 | disputeModels 仅用于仲裁复算，须来自部署方明确登记的集合；缺配置拒签相应模板 |
| 争议受理 | 核当事方归属、合同签名链、交付摘要与验收报告，不接受任意第三方冒名申请 |
| 裁定 | 独立文书引用合同摘要；不直接触发付款 |
| 信誉 | 服务方提交原结清卡，复用 A2C card.close 核签名链与结局，再按可验证结果签发信誉条目；接口不接受自报成功次数，助手通信不记成交易信誉 |

卡载金额、亲签条款、验收及支付依据按 A2C 原义处理。模板轮换只影响新签约，旧模板与原验收依据须保留，轮换策略见注册中心。

## 异常与恢复

| 情况 | 处理 |
|---|---|
| 预留响应丢失 | 按原请求查询台账，恢复原预留，不重复占位 |
| 正式请求过期 | 返回协议错误；发送端先核未知效果及授权，再准备新的合法请求，不改旧签名时间 |
| 认证或输出未知 | 保留原签署检查点与 committed，查原任务/合同，不另造签名承诺 |
| 结果延迟读取 | 按原协议核验结果；不能一概要求重签已有效结果 |
| 通信关闭请求 | 已成约必须依据合同终态，未成约也须核承诺与费用；投递关闭不能替代业务解除 |
