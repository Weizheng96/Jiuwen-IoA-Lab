# 委托中心 · 接单与容量

本页是[委托中心](../接口.md#接口)的子页。

## 成约方式与台账状态

普通用户服务默认待批准或提案模式；预批准仍是 A2C 合法模式，本期普通服务不启用。各模式复用 A2C 的同一合同与算价规则。

| 模式 | 比较阶段可取得的对象 | 用户具体确认与成约时点 |
|---|---|---|
| 提案 | 服务方签 2、市场签 3 的正式提案卡 | 用户选择并确认该卡后，委托方签 1 采纳，才形成合同 |
| 待批准 | 依据有效模板确定算价的未签卡，明确标为待服务方批准 | 用户选择并确认具体卡后才发起预留、签 1 与复签请求；服务方签 2 即形成合同 |

| 台账状态 | 含义与计数 |
|---|---|
| held | 尚未开始付款或有效签署的短期预留，绑定 holdUntil；计入容量 |
| committed | 付款或有效承诺已开始，后续按真实业务终态核实；计入容量 |
| released | 已核实安全释放，不再计入容量；保留历史关联 |

## 委托意向与交互

| 接口 | 用途 | 输入与结果 | 拒绝与恢复 | 测试 |
|---|---|---|---|---|
| `Admissions.intent_in(conn,sender,service,origin,body,expires)` | 消息中心受理 `delegation.intent` 时登记业务绑定 | body 为 formation、templateDigest、scopeDigest、bindingDigest 与原未签 request 或 card；核模板为该服务当前有效公示、摘要为 A2C 原语、支付方为本平台，并经支付中心核范围资格 | 非助手到服务 403；模板未公示或索引未就绪 not_ready 409；对象校验失败 invalid_input；摘要或支付方不符 403；同一协议对象重复 id_conflict 409 | delegation_admission、agent_delivery |
| `Admissions.link_in(conn,service,origin,iid,binding)`、`relation(conn,iid)`、`intent(conn,origin)` | 原接收端建立交互时不可变登记意向到 UUID 的关联 | 后续预留与付款使用同一关系 | 非原服务或绑定不符 403；已关联其他交互 id_conflict 409 | delegation_admission、protocol_relay |
| `Admissions.start_in(conn,service,origin)` | `request.start` 为意向授予开始许可 | 复核意向未关闭未过期、模板仍公示、范围仍有效 | closed、expired、not_ready 409 | delegation_admission |
| `Admissions.offered(service)`、`owned_service(owner,actor)` | 当前可用于新委托的模板；服务归属 | 读注册中心发布状态 | 索引未就绪 not_ready 409，recovery=recover_publication | delegation_admission |

## 接单策略与预留

控制操作经当前服务执行连接的 WS 控制帧到达，由 `Admissions.apply_in(conn,owner,actor,kind,operationId,payload)` 处理并按 actor、种类与 operationId 幂等。

| 控制操作 | 用途 | 输入与结果 | 拒绝与恢复 | 测试 |
|---|---|---|---|---|
| `admission.configure` | 设置容量与接单开关 | expectedRevision、maxActiveDelegations 1—1000、accepting；只影响此后新增预留，不取消已有 held、committed 或合同 | 修订不符 revision_conflict 409；无有效模板却开启 not_ready 409 | provider_admission |
| `admission.reserve` | 为已开始的原意向申请预留 | interactionId、originMessageId、bindingDigest；held 最长 120 秒且不超过意向、模板与用户许可截止；admission ID 由交互 UUID 确定性派生，同一交互只有一份原预留 | 未取得开始许可 403；暂停 service_paused 409；满额 capacity_full 409；意向或模板过期 expired 409 | delegation_admission、provider_admission、quote_admission_rejection |
| `admission.commit` | 零拟卡费提案或待批准的提交 | admissionId 与待批准时的原签 1 卡；待批准核卡摘要、仅签 1、新鲜度与响应期限 | 非该服务 403；有拟卡费提案须走协调付款 403；预留已过期或服务离线 expired、not_ready 409；已提交后换卡 id_conflict 409 | delegation_admission、protocol_relay |
| `admission.status` | 查询预留或当前策略 | 带 admissionId 返回原回执，不带返回策略与活跃数 | 非当事方 403 | provider_admission |
| `Admissions.operation(owner,actor,kind,operationId)` | 查询原控制操作结果 | `GET /api/v1/operations/{operationId}` 与 `operation.get` | not_ready 404，recovery=retry_original | provider_admission |

`Admissions.policy(conn,service)`、`receipt(row)`、`admission(conn,id)` 返回策略、原回执与台账行，供消息中心与其他分组使用。接口文档列有 `admission.release`，代码未提供，见[票据](../../进展/04-接单释放控制操作.md)。

## 到期与释放

| 接口 | 用途 | 输入与结果 | 拒绝与恢复 | 测试 |
|---|---|---|---|---|
| `Admissions.expire_in(conn)` | 关闭到期的 held 预留 | 到期先失去付款与签署资格再释放 | — | delegation_admission |
| `Admissions.expired_proposals_in(conn)` | 列出可证明到期且未中选的已签认提案 | 核原请求、模板、签 2、签 3 完整，已过签 3 + respondWithin + startWithin，未被选择、未登记合同、无合同付款 | 缺证据或校验失败则跳过，保留 committed | proposal_expiry |
| `Admissions.can_close_in(conn,origin)`、`close_in(conn,origin)` | 交互关闭前核无 committed 义务 | 关闭只释放 held 并关闭意向 | 有 committed not_ready 409，recovery=reconcile_original | delegation_admission、proposal_expiry |
| `Admissions.finish_in(conn,admissionId)` | 真实结清或可证明到期后释放 | 由 web服务 的结清用例或消息中心维护循环在同一事务调用 | — | resident_fulfillment、proposal_expiry |
| `Admissions.evidence_in(conn,admissionId)` | 原义务事实供仲裁取证 | 台账行、模板、签名请求、签认提案；不检查当前公示或期限 | 不存在 not_ready 404 | arbitration_evidence |

## 不变量

| 规则 | 说明 |
|---|---|
| 不先成约再比较 | 不得为横向比较向多个待批准候选先请求复签再让用户选一家；可比对象见[个人助手端](../../../客户端/个人助手端/接口.md) |
| 一交互一承诺 | 同一交互只保留一个未结束承诺，旧承诺有效时不发替代版本；换对象须重新检查，不复用原资格 |
| 离线意向 | 可按消息 TTL 排队；不承诺接单、不支付拟卡费、不声明成约；建立交互只确定关联，不授予容量 |
| 先容量后签署 | 待批准在用户确认具体卡、原绑定与委托方签 1 有效后，服务方审查并提交预留再签 2；有拟卡费提案先预留，经协调付款入口在同一事务提交预留并过账；无拟卡费提案不造虚假支付，但输出有效签名承诺前仍须提交预留 |
| 提案输出 | 复核响应期限与预留，持久化签署检查点，再签署并请求市场认证；模型、排队、断线均计入原期限 |
| 暂停与满额 | 暂停时新预留以 service_paused 明确拒绝，委托方按业务拒绝结束；既有预留重传不重新占用或检查新开关；满额拒绝新增，已有委托的授权、交付、验收、付款、解除与恢复照常 |
| 容量与模型并发 | max_active_delegations 控制接单，max_model_runs 控制模型并发，两者分别检查；等待用户时接单名额继续占用，模型名额可释放 |
| 外层门禁 | 已登记服务的公网 AP2 与市场入口不得绕过外层交互、执行代次与 admission；有效范围授权不等于具体合同确认 |
| 承诺窗口 | 待批准已签 2 未开工保留至签 2 + startWithin；待批准已提交而签 2 未知保留原签 1 + respondWithin + startWithin；提案已签 3 未开工保留至签 3 + respondWithin + startWithin；已开工依 A2C 终态与凭证核实 |
| 已付拟卡费无承诺 | 明确拟卡拒绝、失败或期限结束后，先关闭原入口并核无在途有效签名再结束预留；保留实际付款凭证，不自动退款 |
| 未中选提案 | 用户页面选择不撤销协议承诺；自动释放须同一事务完成接单释放、原意向关闭、交互关闭与双方可靠通知，保留原提案与实际拟卡费，不生成结清、裁定或信誉 |
| 重启对账 | 服务重启先对账再接新单；活动 admission 按业务生命周期保存，不受普通消息元数据清理影响；预留响应丢失按原请求查询台账恢复 |

### 验收条件

单模块的可验证条件；跨模块条件在流程页的“端到端验收”节。

| 场景 | 必须满足 | 测试 |
|---|---|---|
| 并发争抢最后名额 | 仅一个成功预留，其他明确满额；被拒绝者不付拟卡费 | delegation_admission |
| 已签提案未选中 | 不提前释放仍可成约/开工的名额；全窗口后核原请求、签名和终局回执，再原子释放、关闭并通知；保留拟卡费和提案，不增加信誉。已选择、合同/开工/付款存在、调用未知或证据缺失均不自动释放；重复维护及事务失败不重复通知或部分释放 | proposal_expiry |
| 满额后的后续消息 | 原单授权、交付、验收、付款、解除继续可用 | delegation_admission、resident_delegation |
| 零拟卡费 | 仍先提交接单预留，再签署有效承诺，不能绕过容量检查 | delegation_admission |
| 提案签认竞争 | 只签认原已开始请求对应的服务方签2卡；容量/用户/期限/当前连接提交前复核；快照、原签3、卡绑定及操作回执原子保存，丢响应不重签 | protocol_relay、quote_admission_rejection |
