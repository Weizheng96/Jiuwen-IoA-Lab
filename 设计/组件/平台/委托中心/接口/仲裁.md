# 委托中心 · 仲裁

本页是[委托中心](../接口.md#接口)的子页。字段与入口只在[仲裁接口](../../web服务/接口/仲裁接口.md#仲裁接口)定义。

## 争议案件与原证据

本模块拥有案件、证据快照、评估与裁定，不复制 A2C 合同状态机。接单台账提供原承诺与请求，合同权威提供原卡、签名与回执，协议中继提供完整原请求与全部进展，支付中心提供实际原凭证。取证不执行验收器、模型、付款或业务，不更新原合同，不依据监控投影或模型描述判案。

| 对象 | 规则 |
|---|---|
| 争议对象 | 以原 admissionId 关联；subject 区分 contract 与 proposal-request 及其原摘要。拟卡费超时可能尚无合同，不伪造卡或合同结清日志 |
| 预览 | 返回原对象、理由、期次、assessedAt、截止、eligible、route、依据摘要及缺少的材料；只是当前取证，不创建案件或批准 |
| 案件标识 | 平台生成 caseRef，受理时持久保存并返回双方；后续查询、材料、通知与结束回执均引用它，不增加 A2C 字段 |
| 原申请 | 相同身份与 operationId 的同内容恢复原案件，异内容拒绝。同一 admission 只受理一个终止型案件；换理由、期次、操作或申请方不能另起并行裁定，双方通过原 admission 取得已有 caseRef |
| 案件状态 | queued、evaluating、needs_review、unknown、ruled；申请与受理不是裁定。无效或尚不成立的理由在受理前拒绝；程序与人工终局均为 ruled，不另建撤案重开引擎 |
| 完整历史 | 读取原协议请求及全部已受理进展，按原签名请求摘要去重环节并关联原答复；不能只读最后一个 step 或用空 steps、vouchers 代替历史。保留期不足须明确 history_gap |
| 证据完整性 | 核原双方身份、模板、请求、合同签名、真实存证前缀、失败报告原签名及实际凭证；已签历史按原时刻验证，当前模板过期不使旧合同证据失效 |

| 理由 ground | 申请方与必须成立的事实 | 处理路径 |
|---|---|---|
| acceptance-failed | 委托方；本期原签 5、原清单、委托方亲签失败报告及摘要匹配的交付件 | 市场按签认快照调用原 A2C recompute；模型只观察，程序裁定 |
| start-overdue | 委托方；原有效卡超过 startWithin，确无有效接单回执 | 按原 start_deadline 判断，不要求存在交付记录 |
| deliver-overdue | 委托方；原接单回执、完整环节停表记录，本期无签 5 或实际签 5 晚于 deliver_deadline | 复用原期限函数，不忽略等待授权的时间 |
| accept-overdue | 服务方；签 5 后超过 acceptWithin，既无签 7 也无亲签失败报告 | 按原 accept_deadline 判断，失败报告不能算拖延验收 |
| payment-overdue | 服务方；本期原签 5、签 7、正额应付款，超过 respondWithin 仍无实际付款凭证 | 已付及零额不成立；不因客户端漏存凭证宣称未付 |
| authorize-overdue | 服务方；合法原环节请求超过 authorizeWithin，确无原答复 | 按实际请求及全部答复判断 |
| proposal-overdue | 委托方；原提案请求实际已提交、实际拟卡费已付，超过 respondWithin 无正式答复 | 请求摘要为对象；仅付款而未提交请求不成立 |
| fetch-failed、declaration-mismatch、authorize-refused | 原取件调用、拒收文书与材料或原拒绝答复，不能仅用网络异常或布尔值推断因果 | 不能由原程序直接判断的因果交独立人工复核 |
| termination-refund、termination-compensation | 原解除、真实定金与退款及报价；单方补偿须遵守原 A2C 本期上限 | 不凭空增加退款时限或自动确定补偿，由独立人工复核 |

## 接口

| 接口 | 用途 | 输入与结果 | 拒绝与恢复 | 测试 |
|---|---|---|---|---|
| `ArbitrationEvidence.preview(owner,payload)`、`capture(…)`、`current(…)` | 取证预览、受理用快照、复核用当前事实 | `POST /api/v1/arbitrations/preview`，agentId、admissionId、ground 与按理由要求的 period；返回公开快照 | 非当事方或理由属于对方 403；字段或理由无效 invalid_input；原证据校验失败 history_gap 409，recovery=reconcile_original | arbitration_evidence |
| `ArbitrationCases.prepare(owner,actor,kind,operationId,payload)`、`apply_in(conn,owner,actor,kind,prepared)` | `arbitration.request` 控制帧：事务外取证并核材料字节，事务内复核后受理 | admissionId、ground、period、basisDigest 与至多 32 项材料引用（deliveryFiles、fetchEvidence、inputMaterials）；返回 caseRef、admissionId、subject、acceptedAt、existing；需人工的理由直接入 needs_review | 理由不成立 not_ready 409，recovery=read_original；证据、材料或模型映射在受理前变化 revision_conflict 409；同操作异内容 id_conflict 409 | arbitration_cases |
| `ArbitrationCases.operation(…)`、`get(owner,actor,caseRef)`、`by_admission(owner,actor,admissionId)`、`material(caseRef,fileId,…)` | 原操作结果、案件公开视图、按 admission 查已有案件、读取本案材料 | `GET /api/v1/arbitrations`、`/arbitrations/{caseRef}`、`/materials/{fileId}`；视图含评估尝试、evaluation、ruling、decisionEvidence 与 execution | 非原当事方 403；非本案文件 404；冻结输入或决定证据损坏 history_gap 409 | arbitration_cases、arbitration_review |
| `ArbitrationCases.recover()`、`process_one()` | 取得核心数据所有权后恢复，再由唯一工作者逐件评估 | 遗留的 evaluating 且无结果转 unknown；评估结果先持久保存再单独提交终局 | 事实或模型映射变化转 needs_review；其他异常转 unknown，不自动重调模型 | arbitration_processing |
| `MarketService.evaluate_case(basis,route,materials)`、`prepare_ruling(…)`、`commit_ruling_in(conn,basis,ruling)` | 确定性期限判定或原 recompute；签发裁定文书；事务内记入市场 | 交付字节须与本期原签 4 清单的名称与摘要集合完全一致；已有合法终态只允许中立且不再记裁定 | 需人工的理由 history_gap 409；复算未给出终局 unknown_result 409；已有其他裁定拒绝覆盖 | arbitration_processing、arbitration_review |
| `ArbitrationCases.admin_list(operator,…)`、`admin_get(operator,caseRef)` | 独立管理员的案件列表与本案证据 | `GET /api/admin/arbitrations`、`/{caseRef}`；每次读取写审计；详情含 review 视图与 expectedEvidenceDigest | 非管理员 403；本账号为当事方 403 | arbitration_review |
| `ArbitrationCases.admin_review(operator,caseRef,payload)` | 人工复核并终局 | operationId、expectedEvidenceDigest、reason、liable（client、provider、none）与可选 compensation | 页面依据已变 revision_conflict 409；当前不可复核 not_ready 409；翻转已知程序结果或市场结局 403；同操作异内容 id_conflict 409 | arbitration_review、arbitration_review_policy |
| `ArbitrationCases.admin_reevaluate(operator,caseRef,payload)` | 对无已知结果、原评估写入者已结束的 unknown 案件明确重评 | 材料、原依据摘要与固定模型集合不得改变；回到 queued | 条件不满足 not_ready 409 | arbitration_review |
| `ArbitrationCases.guard_in(conn,admission,op,body)`、`payment_in(…)`、`ruled_in(…)`、`request_outcomes(provider)` | 裁定后的协议与付款守卫；无卡请求裁定供信誉统计 | 裁定后只放行付款通知、已签 7 期次的分期 checkout 与已有协商解除余额 | 其余 closed 409 | arbitration_processing、arbitration_review |
| `arbitration_review.request(kind,payload)`、`decision(basis,route,known,payload,operator,*,deterministic)` | 复核请求校验与可选结论的边界 | 纯规则 | invalid_input；forbidden 403 | arbitration_review_policy |

### 材料与复核边界

| 边界 | 要求 |
|---|---|
| 材料快照 | 申请携带本案所需材料分组和完整文件引用，受理时冻结。核原上传身份、就绪状态、名称、摘要、大小和实际字节；所有分组合计沿用消息附件最多 32 项及单文件与账号配额，不接受 URL 或服务端路径 |
| 已收到的文件 | 收到读取权不等于可以再次转授原引用。SDK 使用本机已获准读取的原字节，按本次用户确认另建所属上传引用；不能把其他账号的 fileId 直接报送或共享 |
| 交付复算 | deliveryFiles 必须与本期原签 4 清单的文件名与摘要集合完全一致；原程序仍核实际字节，不接受另一份卡或模型说明代替交付件 |
| 后续读取 | 材料属于冻结申请，不提供追加后重试挑结果的接口。双方只能读取本案件；非当事网页管理员只读本案提交的证据，不能据此取得原账号的其他私有文件或消息正文 |
| 人工入口 | 管理员先取得案件列表及本案证据，再按原依据摘要复核或明确重评；每次读取和提交均核当前角色及非本案当事身份，记录实际操作者。本案授权不等于全局消息审计权限 |
| 固定模型 | 固定原卡的 disputeModels 及受理时部署登记的非凭据模型映射摘要。恢复或明确重评前核同一映射；改变登记时停止并核实原资源，不默换模型。密钥轮换不进入该摘要或案件公开内容 |

### 复核依据与决定证据

| 依据 | 规则 |
|---|---|
| 冻结申请 | 原申请、原 basisDigest、材料和已知程序结果保持不变；不追加材料或重写原结果 |
| 当前事实 | 原事实收集与理由成立判断分开。案件详情可读取同一 admission 最新已验证的卡、签名、环节、实际付款及协议进展；已验收或已付款导致原理由不再成立，不阻止独立管理员查看这些真实事实 |
| 复核确认 | 管理员看到冻结申请、已知结果和当前事实后，提交其实际看到的复核依据摘要。提交事务内重收集并比较；事实、程序结果或案件状态变化时拒绝旧确认，不以冻结申请摘要冒充当前依据 |
| 复核条件 | 仅 needs_review 或 unknown 且本案没有活动评估写入者时允许人工复核；queued、evaluating 继续原评估，ruled 只恢复原文书。独立网页账号、明确理由和原操作幂等回执必须同时满足 |
| 程序判据 | 已知程序结果不删除、不重算或翻转，人工只可沿原归责或明确中立。尚无完整复算结果时只可中立或按原模型明确重评，不能凭人工意见补出验收 pass 或 fail；确定性理由可沿当前原期限判据复核，理由已消解只能中立 |
| 最终决定 | 案件另存决定时的实际原事实，含当前市场结局；仍未结束的原卡调用 A2C record_ruling，可补付义务以决定时真实原卡为准。原申请快照仍保留，不能漏掉申请后的签 7 或协商解除 |
| 已有合法终态 | 原卡已正常结清或解除结清时，案件仅可中立；保留原市场结局、信誉及已释放容量，不再次 record_ruling 或释放，案件执行状态标为已结束。已有其他裁定时拒绝覆盖 |
| 公开证据 | 双方与管理员可核对决定证据的公开视图及其签名绑定摘要；原 AP2 请求凭据和私人传输封套不公开。SDK 从公开视图重新计算摘要，核其原合同身份、签名及本单引用，不只相信摘要字符串相等 |
| 人工补偿 | 只在原单方解除补偿案件中明确提出；金额为非负十进制定数，不超过原卡该未验收期金额，币种与原卡一致；只是裁定说明，不进入 AP2 自动付款 |

无卡请求保持原 subject；原 respondWithin 之后不得新签认正式提案，已有正式答复也不能再按未答复受理。取证与承诺检查使用同一权威时钟。

### 评估所有权与核实

核心数据所有权先按[部署](../../../../工程/安装与升级/进程与数据.md#平台核心的数据所有权)取得，再恢复案件。queued 可开始评估；前一核心写入者退出后遗留的 evaluating 转 unknown，不自动再次调用模型。原评估结果先持久保存，后续只恢复该结果的提交；重复申请、重启或换发起方都不能重算挑结果。复算不持数据库事务；提交终局前重新核对证据摘要与最新权威事实，事实变化则待核实。

人工复核可明确 liable=none，表示双方均不归责，仍为终局裁定并终止原卡；中立文书不新增服务方失败或完成，不进入成功率分母。无合同卡的原请求裁定由案件所有者提供可验证结果，归责明确时只计一次信誉，不写伪造合同 ledger。

## 裁定、执行与容量收尾

| 阶段 | 规则 |
|---|---|
| 终局提交 | 冻结决定证据、原裁定、A2C 市场结局及双方可靠 contract.ruling 通知由同一应用事务提交；仍未结束的已成约卡用决定时真实原卡调用 record_ruling，已有合法终态按上文保留，未成约请求不冒充合同 ledger |
| 合同最终性 | 裁定终止原卡，拒绝新增开工、交付、环节、验收及新定金；不能用新的操作 ID 重启本卡。双方继续合作须新卡 |
| 资金 | 裁定不触发划转；冻结原卡中已签 5、签 7 的应付款及已有协商解除余额仍按原 AP2 和有效用户许可处理。不得补付被裁定禁止的新定金、接受新签 7 或用裁定新增付款用途 |
| 本地收敛 | SDK 确定性消费原裁定，停止未开始工作，等待原模型、生产与工具的实际写入者结束；未知效果保留名额和原证据，不把断线、停止请求或超时当结束 |
| 结束回执 | 原服务方提交 caseRef 及原执行关联；平台核裁定、实际写入者与原协议 Task 收敛，以及冻结卡的上述原应付款齐全后，原子释放容量并关闭交互。原 Task 可真实 canceled，不伪报正常完成；不调用 Provider.close 或造解除。实现差距见[票据](../../进展/05-裁定后执行结束回执.md) |
| 恢复 | 同一裁定、通知及结束动作沿原记录恢复；执行结束与债务已付分别展示，未核实原效果时不释放。一个义务最多一份终局裁定 |
