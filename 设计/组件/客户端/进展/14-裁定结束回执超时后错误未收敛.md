# 14：裁定结束回执超时后迟到的平台拒绝不收敛

**目标行为：** 服务方 SDK 的 `provider.arbitration` 作业提交 `arbitration.finish` 后本地等待超时（作业转 unknown），若平台随后返回原操作的拒绝（如原应付款未齐、协议任务未收敛），SDK 能确定性地把原作业收敛为 rejected，并在退避后用新的操作标识重新提交；不靠人工或模型续接。

**阻塞于：** 无

**状态：** ready（开发中，与当前设计有偏离）

**范围：** 服务方端 `provider/arbitration.py`。现状：`Rulings.advance` 对 unknown 且未执行的作业只读取原操作的已存响应 `runtime.store.response(actor,'arbitration.finish',operation)`。若超时时尚无响应，而原 outbox 之后重发并收到平台错误，`store.response` 会得到 `ok=false` 的记录，代码已据此 `resolve` 为 rejected 并写 `retryAt`；但当超时发生在原操作尚未被平台受理、连接重建后 outbox 未重发或响应未落库时，作业一直停在 unknown，`advance` 每轮只读不动作，`case.finish` 永不写入，接单名额与交互一直保留。[接单与任务恢复 · 仲裁操作](../服务方端/接口/接单与任务恢复.md#仲裁操作)要求“结果未知只消费原操作的已存响应，不另起结束”，这一条保持不变；缺的是让原操作本身得到确定结果。

修复方案：结束回执是平台幂等的控制操作（同 actor、同 operationId 恢复原回执；拒绝不落库）。unknown 且未执行时：

1. 若 `store.response` 已有响应，按现状收敛为 completed 或 rejected。
2. 若无响应，读原操作：先用 `GET /api/v1/operations/{operationId}?agentId&operation=arbitration.finish` 查平台已受理结果；有结果则保存回执、收敛为 completed。404（无受理结果）时以同一 operationId 经 `connection.submit` 重发原载荷（outbox 幂等，不改载荷与标识），由下一轮读取响应收敛；不得换新标识，避免同一回执被重复提交。
3. 每个作业的查询与重发按 `RETRY_SECONDS` 节流，避免扫描循环每 0.25 秒发网络请求。

`operation.get` 的分派当前仅对 `arbitration.*` 查 `arbitration_operations`，`arbitration.finish` 的成功回执已在其中，平台侧无需改动。

需读[服务方端 · 接单与任务恢复](../服务方端/接口/接单与任务恢复.md#仲裁操作)、[共用运行时 · 操作与恢复](../共用运行时/接口/操作与恢复.md)与[委托中心 · 仲裁](../../平台/委托中心/接口/仲裁.md#裁定执行与容量收尾)。

**定向测试：** arbitration_processing

- [ ] 超时后平台迟到拒绝：作业由 unknown 收敛为 rejected，30 秒后以新操作重提并最终释放
- [ ] 超时后平台已受理但本地无响应：经 operation 查询恢复原回执，不重复提交
- [ ] 超时后平台未受理：同一 operationId 重发原载荷，标识与载荷不变
- [ ] 接口页仲裁操作节补写上述恢复顺序
