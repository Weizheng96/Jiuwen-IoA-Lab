## 实施方案

用户已授权开始开发，并要求完成后先不提交。先明确新适配模块的代码/设计目录、接口、依赖和测试，更新架构模块表与相关流程并按 design 升版，再实现；实际进度和验证记录随本票及模块实现页维护。

本机已实现本地 MCP 模块、公共客户端入口、持久表单、标准 Apps 资源/桥接、浏览器入口及 `messaging.interface` 的草稿—预览—可信确认—发布—恢复链路。协议采用官方 MCP Client 验证，页面采用隔离 Chromium 验证；真实九问/其他宿主及新服务器验收仍待完成，不据此删除本票。实际命令、结果与全仓回归中的既有环境失败见[开发记录](../../../工程/实施资料/MCP接入开发.md)。

1. 本地 MCP Server 仅提供工具与界面资源适配；配置、账号、业务操作、状态与恢复归客户端公共能力。优先 stdio 薄入口连接所属实例的受控 IPC，单一业务写入者；不新增云端 MCP Server。
2. 定稿工具与资源清单：流程打开、普通字段提交、校验/预览、查询和恢复如何映射现有操作；声明输入输出 Schema、资源 URI、版本、错误、取消和可见性。协议请求编号与业务操作引用分开，不暴露任意本地命令或通用批准工具。
3. 实现能力探测和配套浏览器表单；标准 App 容器通过宿主桥接调用工具，浏览器通过本地受控入口使用同一公共能力。九问首期采用浏览器；A2UI 支持不作为标准 Apps 支持的证据。
4. 用已有账号选择一条可独立核验的草稿、预览和真实确认链路，绑定对象、版本、会话和有效期；复用可信用户确认能力。秘密录入另走受控路径，工具、模型及日志只见脱敏结果。
5. UI 逻辑目录按身份、注册、消息、委托、支付和服务方划分，流程层仅导航；定义页面资源来源、浏览器会话与请求来源校验、重放保护及关闭后的恢复方式。
6. 核验宿主重连、重复启动、关页及重启对原常驻业务的影响；MCP 接口不可用时公共操作仍可由 Skill/CLI 使用。
