# 17：委托交易图形化闭环

**目标行为：** 用户提出委托后，通过通用表单完成需求、授权、候选和具体合同确认，查看履约、交付、验收、支付与结清；服务方复用已有 SDK 完成发布、接单管理及交付。

**阻塞于：** 12、13、15

**状态：** ready

**验收环境：** 委托方与服务方真实宿主、本地客户端和[新服务器验收基线](../../../工程/实施资料/部署发行.md#新服务器验收基线2026-11-11)，覆盖浏览器与无 Apps 路径。

**范围：** [个人助手端](../个人助手端/接口.md)、[服务方端](../服务方端/接口.md)、[共用运行时](../共用运行时/接口.md)、本地 MCP/UI；平台依赖和授权顺序沿[委托交易](../../../流程/委托交易.md)及[服务方接入](../../../流程/服务方接入.md)，总体见[专题](../../../工程/专题/接入易用性与Agent调用效率.md)。

**定向测试：** resident_delegation、resident_contracts、resident_fulfillment、resident_payment_recovery、protocol_operations、service_publication、user_confirmations、task_recovery_receipts；后续补表单分阶段确认与恢复用例。

## 待实施方案

本轮只登记方案；后续先细化唯一归属接口和流程并按 design 升版，再实现。

1. 通用需求表达目标、材料、范围、约束、交付、期限、预算和验收；用户提出制作小程序时只填入业务值，不专设小程序协议或生产路径。
2. 按现有 SDK 推进授权、发现、报价/候选比选和合同准备；页面展示原业务证据与真实对象，业务判断仍由模型或用户完成。
3. 任务授权、具体合同、合同环节、验收和付款保留各自依据与所需真实确认；不能把一次表单提交视作整个流程的无限授权。
4. 按既有 A2C/支付边界处理履约、补充材料、交付、验收、付款、结清及拒绝、终止、争议和未知结果；页面不定义另一份状态机。
5. 服务方表单覆盖通用服务规格、报价/容量、生产配置、公示、开放/暂停接单与本单交付；管理权限与入站本单执行分开。
6. 页面分别归 `registry/`、`delegation/`、`payments/` 和 `provider/`，`flows/delegation/` 只做导航；MCP、浏览器、Skill/CLI 共用同一业务操作。本期不实现悬赏或委托分解。

## 验收项

- [ ] 至少一个真实委托从需求到结清，含服务发现/比选和服务方实际履约；另覆盖服务发布及暂停/恢复接单
- [ ] 各阶段展示正确原件及证据，审批对象、版本、角色和有效期可核验，模型或工具伪造批准无效
- [ ] 多期合同、补充材料、拒绝、协议支持的终止/争议和未知结果沿原规则处理
- [ ] 无 Apps 可完成同一闭环；关页、断线、丢回执、重复提交和重启不会重签、重复收费、生产或通知
- [ ] 记录实际合同/付款回执及真实宿主、客户端、平台版本；没有执行的分支保持未验证，不以静态表单代替业务验收
