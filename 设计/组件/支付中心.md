# 支付中心

## 目的与范围

通过 AP2 接口执行虚拟币记账、授权核验和按证据付款。虚拟币仅为实验记账单位，协议币种使用 SDK 支持的 CNY，界面明确标注虚拟币。本期不实现 A4P。

支付中心不决定服务是否接单，不替用户确认合同或验收，不根据普通观察事件或模型声明付款。A2C 负责合同与付款依据；本组件按其证据过账。

## 职责与数据

| 对象 | 权威记录与约束 |
|---|---|
| 虚拟币余量 | 按已核实过账记录计算；更新受数据库事务保护 |
| 授权凭证 | 绑定付款身份、用途、类别、预算/费用限制和有效期；核验签名与适用范围 |
| 付款操作 | 稳定操作标识、付款/收款方、用途、协议摘要、金额及最终结果 |
| 付款凭证 | 成功操作的原始凭证；相同操作重传返回原凭证 |
| 登录发放记录 | 与身份中心确认的登录操作绑定，防止同一登录重传重复发放 |

付款公钥与收款身份以[身份中心](身份中心.md)绑定为准。运行时私钥和用户确认保留在本地，支付中心只接收相应签名与必要凭证。

## 登录赠币

| 情况 | 规则 |
|---|---|
| 用户名密码成功登录 | 每次新的明确登录按配置发放，默认 100 虚拟币 |
| 注册后的首次自动登录 | 按该登录操作发放 |
| 同一次登录网络重传 | 恢复原登录操作，只发放一次 |
| cookie/Bearer 复用、票据续取、WS 重连、重复身份绑定 | 不构成新的登录，不发放 |
| 登录失败 | 不发放 |

身份中心发布的登录成功记录与发放记录按稳定操作关联；跨组件处理失败时恢复原操作，不能要求客户端重新密码登录来补发。

## 授权与过账

| 检查 | 必须满足 |
|---|---|
| 主体 | 付款方、服务收款方及用途公钥与已绑定身份一致；付款账号必须拥有请求/合同中的委托方智能体，且其中的 client 公钥与平台绑定一致，准备及提交均核验 |
| 用户授权 | 真实授权在有效期内，覆盖用途、类别、总预算和拟卡费限额；不能只解码 JWT 而不验证签名及截止 |
| 协议依据 | 拟卡费、定金、各期款和解除款分别使用 A2C 规定的依据；每期款依签5(i)及签7(i) |
| 金额 | 从可验证卡/请求及协议计算取得确定数值，不能接受模型任意填写的费用 |
| 幂等 | 同操作同内容返回原结果；同操作异内容冲突，不另行过账 |
| 可用余量与额度 | 在同一过账事务中核实并更新；同一付款授权并发使用不能绕过总额度 |
| 成功证据 | 持久化过账和凭证后才返回成功；观察事件只是其投影 |

首次委托授权、具体合同确认、合同声明的环节授权及验收确认分别执行，不能相互替代。具体取得确认的过程见[委托交易](../流程/委托交易.md)；本地保护规则见[本地接入组件](本地接入组件.md)。

## 付款准备、提交与恢复

### 委托范围与授权台账

委托范围是不可变上下文；授权是用户对该范围的签名许可，两者分开。A2C 卡和请求的 `delegationScopeDigest` 使用 A2C 摘要原语计算完整上下文，不包含后续可变化的授权有效期。此处是 IoA 运行凭证，不新增 A2C 对象类型或合同字段。

| 记录 | 完整定义及约束 |
|---|---|
| context | schema=`ioalab.scope/1`、scopeId（UUID）、platform、actor、user（id/jwk）、purpose、categoryIds、currency、budget、proposalFeeLimit；金额为两位小数非负字符串，拟卡费属于总预算；categoryIds 为精确分类 ID 列表，null 表示不限制、空列表不允许新候选 |
| grant | revision（初次1，续期按平台当前授权修订加1）、issuedAt、expiresAt；最长7天，签署时点最多超前60秒；续期只换许可有效期，不改 context，不重置支出或已选合同；撤回也推进当前修订，因而签名许可修订可以存在间隔 |
| proof | 用户已绑定 Ed25519 密钥，对 `{context,grant}` 的 A2C 摘要签署 JWS，slot=`ioa-scope`；签署时间等于 issuedAt；平台校验主体、公钥、签名、时间及修订 |
| scopeDigest | A2C `digest(context)`；同一 scopeId 不得换上下文，同一修订不得换签名对象；原已接受授权重传可查询原结果，不恢复已关闭权限 |
| 平台预算 | 同范围持久保存已付拟卡费、已选 cardDigest/完整合同价款、合同已付款及逐笔付款关联；读改均在同一平台短事务 |

SDK 只有在本机可信用户入口批准具体 context 和许可期限后才用 user 密钥签发 proof。平台不能从模型文字判断用户是否批准；本地批准和平台签名核验分别守住各自边界。平台只接收必要用途摘要，不上传原始私人对话。

登记、续期、查询和关闭均绑定原账号及 actor。关闭表示撤回当前授权，原子推进授权修订并拒绝新动作，保留原证据和支出；不等于解除合同。旧许可或撤回前按旧修订准备的在途续期不能恢复权限。用户明确重新批准后，可读取最新修订、签发下一修订重新授权原范围，以继续履约或付款，预算和原合同绑定均不变。过期或撤回后的原成功付款仍可查询；不能改卡载摘要或自动重新登录替代新授权。

### 合同选择与预算计算

| 动作 | 原子预算规则 |
|---|---|
| 新拟卡费 | 尚未选择合同，且累计拟卡费加本笔同时不超过 proposalFeeLimit 和 budget；只在实际过账事务计入，不因付款准备或网络超时直接增加/释放 |
| 选择具体合同 | 在签1形成承诺前，SDK取得具体合同确认，用户另签 `{scopeDigest,cardDigest}` 的选择证明（slot=`ioa-contract-selection`）；平台校验完整原卡、签名、价格、绑定和当前授权，再预留完整合同价款 |
| 合同额度 | 只允许一个被选 cardDigest；已付拟卡费加合同完整价款不超过 budget；重复选择同卡恢复原记录，不产生第二份额度 |
| 合同付款 | 只消费被选合同额度，核每笔 A2C/AP2 依据；合同累计付款不得超过已预留完整价款，不能把预留和付款重复加到总预算 |
| 结果不明 | 平台未提交则预算与过账一起回滚；已提交按原付款标识恢复。客户端未知仍保留本地占用，不能据此再建付款 |

选择证明和平台额度回执属于 IoA 运行数据。提案、待批准均先取得额度回执再执行相应签1；服务方签2及接单容量仍由委托中心保障。不得先形成合同再补预算检查，也不得给每一期重新开放整份预算。

一个范围只选择一份合同，选定后不再发起新的付费征集或自动改选。选择或签署未知时保持原绑定；新业务须另取用户授权，不用“释放再选”掩盖旧承诺。保留完整价款不表示预先划走虚拟币，也不改变 A2C 分期付款规则。

已成约的定金、分期及解除付款使用原 admission 和被选卡的预算；不重新申请新候选容量，也不要求服务方当前在线。每笔仍复核当前有效许可、金额、币种、用途、期次及相应原证据。接单记录、原 AP2 过账、范围支出与原回执由同一应用事务协调。原 Client.accept 的通过后付款与显式 pay 恢复使用同一付款记录，不能创建两笔；验收签名已经发生而付款未知时，两类事实分别保存。

金额记账使用十进制定值，禁止 NaN、无穷值、负数或超两位小数。分类限制以注册中心实际归属核验，不能采用来信自报的分类。具体网络格式见[平台接口](../接入/平台接口.md)。

| 阶段 | 规则 |
|---|---|
| 准备 | 在事务外复用 A2C 参考实现核验签名、合同及金额；候选凭证和参考实现的临时 paid/ledger 与平台状态隔离，准备本身不产生实际过账 |
| AP2 边界 | PM、CM 和 Checkout 均核签名及 iat/exp；本平台适配允许最长15分钟、iat 最多超前60秒，过期不发起新付款；Checkout 的原请求/合同摘要、用途、期次和币种必须对应实际依据 |
| 提交 | 使用调用者传入的同一短事务；重核身份绑定、期限、已付款键和解除金额所依赖的既有付款，按实际提交时点签署已验证结果，统一写扣增、过账记录、已付款事实及原 voucher/Payment Receipt |
| 付款唯一性 | 协议摘要、用途、期次构成付款键，另绑定认证付款方和完整原请求摘要；同键同请求恢复原件，同键异请求不再次过账 |
| 原始凭证 | 过账 paymentId 与已签 AP2 回执中的 payment_id 一致；重启、并发重传和丢响应均返回同一原凭证，不重新签署 |
| 已成功后过期 | 原请求完全匹配已有已验证结果时可恢复原件；不因旧授权到期阻止读取已发生事实，也不授予新付款权限 |
| 投影 | 提交后才发布过账观察；观察失败不撤销付款或使客户端误以为未过账 |
| 历史迁移 | 既有 paid/过账若缺少原凭证，保持待核实；不清除标记重付，不重新签出虚构的历史原件 |

提交阶段不等待网络、模型或用户。A2C 合同字段、验收及金额仍由原 SDK 判定；本平台只增加 AP2 接入校验和运行记录。涉及授权预算或接单的付款由应用用例在同一事务协调，不能因单独的支付模块已实现而绕过这些前置条件。

## 与接单预留的事务边界

当前 AP2 模拟支付与委托中心使用平台内明确的应用事务协调，无需引入分布式交易框架：

1. 委托中心核实预留归属、绑定摘要、有效期和未关闭状态。
2. 支付中心核实授权、付款操作与费用依据。
3. 同一事务将预留提交为 `committed`，执行虚拟过账并保存原凭证；任一检查失败不产生本次过账。

支付中心不自行创建接单承诺。拟卡费为零时无需虚构付款，但仍由委托中心在服务方有效签署前提交预留。已经开始付款或签署的未知结果必须先对账，不能按短预留到期直接释放，详见[委托中心](委托中心.md)。

## 异常与恢复

| 情况 | 处理 |
|---|---|
| 付款响应丢失 | 按原操作查询并返回原凭证或明确未生效状态，禁止更换标识重复付款 |
| 付款结果未知 | 保留原凭据与关联预留，进入待核实；不能把超时解释成未付款 |
| 授权过期或超限 | 拒绝新过账并说明原因；不自动扩大授权或移动费用用途 |
| 拟卡失败但已付费 | 保留实际费用凭证；不自动退款、重新收费或抹掉记录 |
| 仲裁裁定 | 文书供当事人使用；裁定本身不自动触发过账 |
| 客户端进程退出 | 从原付款操作、合同与授权检查点恢复；不按模型会话是否结束判断付款结果 |

已产生付款事实的数据不使用“保留账号并清空交易”的重置方式；实验使用新身份或独立数据目录，保留原凭证与账本以供核实。

服务方接单资格与本地模型资源不同；有拟卡费的新接入服务必须通过当前委托方执行连接提交原 AP2 请求，应用层在同一事务提交容量、范围预算和付款。平台按协议对象摘要恢复原付款；有旧付款而缺失对应范围或容量关联时保持待核实，不能补造扣款或假定已登记。具体绑定与截止规则见[委托中心](委托中心.md)。
