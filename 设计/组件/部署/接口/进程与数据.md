# 部署 · 进程与数据

本页是[部署](../接口.md#接口)的子页。

## 进程与网络

Linux受管部署采用Python3.11、隔离venv、systemd和可选Nginx，是唯一的部署方式。跨设备部署只需平台公共HTTPS/WSS入口可达；本机入口只监听回环。个人助手和服务方主动连接，不要求公网IP、端口映射或用户服务反代。

| 实例 | 内容 | 数据与模型 |
|---|---|---|
| 平台核心 | 身份、注册、委托、支付、消息、观察与 Web | 平台数据库/机构密钥；发现和仲裁模型独立配置 |
| 官方服务 | 用 SDK 共用运行时加载官方服务配置，经九问适配按需执行 | 独立服务密钥、合同、工具和会话；独立模型设置 |
| 管理员助手 | 同一运行时的个人助手角色及原版九问，自动配置 ISC_001 | 独立账号、日程、通知凭据和会话 |
| 普通参与方 | 自己电脑/服务器上的运行时及九问 | 用户自己的本地数据、模型、技能和工具 |
| 实验客户端 | 通过公开 SDK 产生委托与助手通信 | 独立实验身份与可追溯输入，标记 experiment |

核心默认本地 8750。反代支持 `/ws/agents` 与 `/ws/admin` 升级、心跳和足够空闲超时；断线由运行时恢复，反代不能将消息缓存成另一套投递队列。正式外网使用 TLS，回环测试可显式使用明文。

安装顺序：安装核心 → 初始化账号与分类 → 配置官方服务及管理员助手 → 校验九问/模型/工具 → 绑定身份并发布 → 建立连接 → 开放接单。未配置模型或通知能力时显示具体不可用项，不能用桩替代真实运行。

部署清单显式选择 `src/official/` 的资源及初始化数据，通过受控本机初始化命令或管理员授权入口创建内部账号与分类。核心校验传入数据，不跨目录读取官方参与方源码；初始化不能覆盖已有账号凭据或重置运行状态。自有JSON来源的清单摘要按UTF-8/LF规范字节计算，Windows检出产生的CRLF不改变同一来源；业务内容变化仍使摘要失效。第三方归档与wheel继续按原始字节核验，不做换行归一。私钥由参与方本地创建，身份绑定与服务模板发布通过同一 SDK 完成，不能把初始化当作代签。

## 运行与数据迁移

| 目录 | 数据性质与管理 |
|---|---|
| `data/` | 持久身份、密钥、业务数据库、日程及本地配置；不入库，按所属方备份 |
| `logs/`、`recordings/` | 运行日志、原始录屏及浏览器状态；不入库，公开证据经脱敏另行发布 |
| `dist/` | 可再生成的安装包；不入库，构建输入和摘要受版本管理 |
| `temp/` | 一次性调查、临时文档和脚本；由仓库忽略规则排除，不作为部署输入或持久数据目录 |
| `experiments/` | 正式可复现实验源码与非私密配置；入库，通过公开 SDK 运行，实测私有数据仍放运行目录 |

核心、服务、助手分别备份；数据库和业务文件使用一致性快照，恢复后核对签名、支付操作与接单台账，再开放新任务。部署、SDK、业务工具不得隐含读取临时目录才能工作。

升级需保留身份、原合同、模板、授权、支付与投递回执；不能清理数据来规避期限或容量。尚未具备接管条件的合同先在原环境完成或按协议结束，再停止原进程部署；新旧执行器不能同时持有同一智能体的活动执行权。

模型调用中断后先核操作回执再恢复。业务工具使用运行时传入的稳定操作键保存业务回执；工具自己的预约/邀请状态与运行时检查点分别管理，邮件/付款结果未知不得自动重做。离线期间合同计时继续。队列、磁盘和配额达到上限应拒绝新业务并可观察，保留已有合同的控制及恢复通道。

验收分别覆盖无 GitHub 的依赖安装、原版九问接入、协议闭环和 Linux 实机/systemd；各层证据独立保存。部署成功不自动代表真实邮件、原生网页审批或视频质量已验收。

## 平台核心的数据所有权

| 边界 | 要求 |
|---|---|
| 取得 | Platform完整角色在固定公共地址、写A2X凭据、打开/迁移DB及装配组件前，取得数据目录的真实OS排他锁；init/serve入口不得提前写配置或日志。同目录的第二实例明确拒绝，不能先修改配置再报占用 |
| 归属 | 存储层提供所有权句柄，由平台生命周期持有；普通DB连接仍只是连接，不等同一个Core角色，不从SDK或部署包反向导入实现 |
| 证明 | 核实际OS锁和持有句柄，不以PID文件、旧状态、进程内RLock或端口占用声称全程单实例；不删除其他实例的锁或运行数据 |
| 失败 | 构造/启动失败及lifespan异常均有清理路径；未启动实际writer时可安全释放，不留下须重启进程才能解除的占用 |
| 退出 | 先停新工作并等待本Core实际后台writer/传输退出，再关闭DB和释放句柄；writer仍活跃时不得报告已停或允许第二实例恢复同数据 |
| 崩溃 | OS释放排他句柄后下一实例才能接管；持久queued与未知已开始动作区分，不能自动重跑后者 |
| 其他入口 | 初始化、停服备份和清理也先取得同一所有权；运行中明确拒绝。锁文件只作持有句柄，不作为可删除的PID标记；清理和备份不删除或恢复该文件来改变锁状态 |

部署仍使用同一默认命令，管理员不需手动维护PID或锁文件。该机制不改变参与方SDK的各自数据所有权，也不修改原版九问。
