# 部署

## 目的与范围

把本仓源码变成受审内容发行与不可变运行环境，并在 Linux 受管部署（systemd）下认领目录、生成私有配置、启动、停止、升级与修复平台核心、官方服务、管理员助手及可选试用。只经各组件的公开命令装配，不运行协议、不改业务数据，也不接管普通用户已有的九问。调用方是部署者（逐步操作只见[部署教程](../../工程/部署.md)）与开发工具。

| 安装与生命周期记录 | 账号、路径与单位归属，初始化与准备回执，最近就绪；停止或启动阶段 | `状态根/.deployment/installation.json`、`lifecycle.json` |
| 生成的角色配置 | 首次生成后保留人工修改；平台 JSON 由 `configure` 从模板创建，格式归平台基础 | `配置根/core/platform.json`、`配置根/agents/{official.json,official.env,swarm-admin.env,assistant.env}`、`状态根/.deployment/admin-assistant/config.json` |
| 发行与环境 | 构建环境、内容寻址发行、各单元不可变环境、环境集合及 `current` 链接 | `运行根/` 下 `build/`、`releases/<releaseId>/`、`envs/<单元>-<摘要前缀>/`、`envs/sets/<setId>/`、`envs/current` |
| 部署方九问工作区 | 归属记录 `ioalab.owned-swarm/1` 与准备锁；工作区内容归原版九问 | `状态根/agents/swarm-official/`、`swarm-admin/` 下的 `ioalab-workspace.json`、`ioalab-setup.lock` |
| 备份 | 切换前一致性快照与校验清单 | `状态根/backups/<operationId>/` |
| 受管单位 | 带 `# ioalab-deployment:<UUID>` 注释的 systemd service | `/etc/systemd/system/ioalab-*.service` |
| 依赖锁 | build 锁与 linux-x86_64 三单元的精确锁及摘要 | `deploy/locks/` |

### Linux 受管入口

`python -m deploy <命令>` 要求 Linux、CPython 3.11 与 systemd；completed 或 waiting 退出码 0，其他 1，异常统一为 `{status:not_ready,error:{type,message}}`。

| 接口 | 用途 | 输入与结果 | 拒绝与恢复 | 测试 |
|---|---|---|---|---|
| `deploy/install.sh`、`python -m deploy install`（`__main__.submit`） | 认领三根、固定安装输入，提交或观察独立 systemd 临时 service 执行的安装任务 | `--config <私有JSON>`，可选 `--root`、`--state`、`--config-dir`、`--core-user`、`--agents-user`，默认 `/opt/ioalab-runtime`、`/var/lib/ioalab`、`/etc/ioalab`；返回任务观察结果 | 输入文件非属主私有、三根与源码相交 ValueError；未完成原任务的来源、动作或输入不同 RuntimeError，先观察或续接原任务 | deployment_entry、deployment_jobs、vendor_deployment |
| `deploy/upgrade.sh`、`python -m deploy upgrade` | 同上，动作为升级 | 同 install；脚本不接受 Git 引用参数 | 原安装未完成 RuntimeError；升级阶段规则见[激活与升级](接口/升级与修复.md#激活与升级) | deployment_upgrade_flow、vendor_deployment |
| `python -m deploy status --state <目录>`（`__main__.status`） | 只读查询部署、任务、当前集合、单位与运行阶段 | units、task、currentSet、lastReadiness；已初始化时附 `lifecycle.status` | 单位归属无法核实时该项 ownership=unverified，recovery=inspect_original_unit_and_record | deployment_entry、deployment_lifecycle |
| `python -m deploy start`、`stop [--wait-seconds 0—300]`（`lifecycle.start`、`stop`） | 按固定顺序启动或排空本部署单位 | start 返回 waiting，运行就绪由 status 报告；stop 组空且执行锁可取得后 completed | 部分运行须先完整 stop；观察超时 waiting 并保留原记录；锁未释放不报告已停 | deployment_lifecycle、deployment_entry |
| `python -m deploy repair-bootstrap --state <原状态根> --operation <失败操作>`（`repair.submit`） | 对已停止、失败于 bootstrap 的首次安装提交控制器修复子任务 | 子操作标识由父操作与新来源摘要确定；重复提交只观察同一子任务 | 不接受替换根、输入或强制参数；非控制器文件变化、父任务未停止或归属变化拒绝 | deployment_repair |

## 不变量

| 规则 | 说明 |
|---|---|
| 单一写入者 | 每个部署同时只有一个安装任务；前台命令只提交或观察，进程状态未知、原组仍有进程或 OS 锁不可取得时不得重启任务 |
| 原任务续接 | 同一来源、动作与输入重复提交必须续接原任务；未完成原任务不得换来源或动作 |
| 只接管自己的 | 只操作带本部署标识的三根、账号、单位、环境与进程；未知归属拒绝，不删除、不按进程名终止 |
| 停止证据 | 报告已停止前必须核控制组为空且执行锁可取得；SIGKILL 与父 PID 退出不作为停机证据 |
| 数据保留 | 停止、升级、重部署与修复不得删除或重置账号、密钥、工作区、人工配置、业务数据与操作回执，不自动回退数据 |
| 配置不重放 | 生成文件就绪后不再重写；初始输入变化必须显式修改原文件；平台 JSON 是唯一参数源 |
| 不可变发行 | 发行目录与环境按内容摘要定位，完成后不原地修补；`current` 只以一次链接替换切换完整集合 |
| 单向依赖 | 平台与参与方运行包不得导入 `deploy`；部署只经组件公开命令与实际执行锁装配，不读业务库 |

### 验收条件

单模块的可验证条件；跨模块条件在流程页的“端到端验收”节。

| 场景 | 必须满足 | 测试 |
|---|---|---|
| 源码与资源独立性 | 可安装包离开仓库源码布局仍可加载必需资源；不靠手工 sys.path、调用者工作目录、temp 或相邻 A2C 仓库运行；预置旧构建缓存时，wheel 仍仅包含现行源码模块 | package_installation |
| 无 GitHub 的干净部署 | 第三方源码、许可、摘要及预构建资产完整；普通依赖走配置的国内镜像，不使用 VCS 安装或现场网页构建 | vendor_deployment |
| 安装单元隔离 | 平台、统一 SDK、九问适配的依赖闭合；九问本体在独立宿主环境；平台环境不安装参与方 Process SDK；技能清单锁定兼容组合；并发读写安装元数据取得完整快照，不把文件替换竞争误作损坏；真实损坏仍停止。验收失败保留目录及原安装任务，不清理仍在工作的环境 | production_release、deployment_builder |
| 默认初始化 | 部署清单显式输入内部账号与分类；重复初始化不覆盖已有凭据/状态；参与方自己生成密钥，经同一 SDK 绑定身份和发布服务 | seed_manifest、deployment_configs、deployment |
| 升级与接管 | 保留原合同、密钥、授权和操作回执；新旧执行器不同时活动；不能接管的在途业务先完成或按协议结束 | installed_upgrade、deployment_activation |
| 目录与数据 | temp 及私人运行数据不入库；正式 experiments 可复现且不依赖临时文件；Linux systemd 实机结果单独记录 | deployment_layout |
| 默认部署闭环 | 核心/参与方/九问分离并核版本、依赖及禁止组件；目标平台锁与输入匹配；本地 Git 依赖只用随仓 wheel；清单变更生成新环境，失败保留现场；首次准备/管理员授权/serve 与重启分离，长期进程无管理员凭据；目录短摘要须与完整身份核对 | production_release、deployment_entry |
| 安装与升级保护 | 未登记目录/越界链接/摘要失配拒绝；原凭据、模型、身份和业务不被重装覆盖；真实释放后备份、切换，未知不强制重做；Linux/systemd 实机结果单独记录 | deployment_layout、deployment_repair |
| 部署方九问准备 | 新空工作区有部署归属及真实 OS 锁；原版公开初始化后由新解释器配置，安装模板和已有用户实例不变；缺模型不就绪；中断恢复原资源不重复创建，冲突不覆盖；重装保留模型/权限/技能修改并从公开目录解析选择键，不泄露密钥 | owned_workspace |
| 默认部署入口 | 单一受管布局与本地源码输入；独立 build 和三运行环境；两个系统账号的真实目录/凭据隔离；实际 8 账号 50 服务及 ISC_001 同 SDK 接入；启动不请求模型生产；不走旧轮询入口 | deployment_entry、seed |
| 升级闭环 | 候选先核验；实际 SDK 锁和原控制组已释放后备份；三个环境与发行资源随一个集合原子切换；保存原身份/合同/会话/未知效果，恢复此前实际运行及原开机设置；中断继续原升级操作，不强杀、不自动恢复旧数据、不重新授权或赠币 | deployment_upgrade_flow、deployment_activation、deployment_backup |
| 安装任务与服务账号 | 前台退出后原安装临时 service 继续，重复命令观察同一任务；主进程结束但组仍有进程时禁止二次执行。真实低权限账号可读取/执行已安装环境及 SDK 安装身份，不能写环境或读取核心/部署私有凭据；后续工作区查询不生成 root 所有文件 | deployment_jobs、linux_service_management |
