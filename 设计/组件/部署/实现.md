| 项 | 值 |
|---|---|

## 入口

`test_server.py`实现显式测试重置和单版本清理，由同一`Installation`任务在`test-reset`阶段调用；复用原systemd管理、核心/SDK执行锁、配置初始化、激活集合与bootstrap，不建立第二安装链。

散文件模块；没有其他模块导入本目录，下列文件是开发工具导入的库面，`tools/verification/`、`tools/smoke.py` 与测试另行导入内部文件做白盒验证。

| 入口文件 | 公开名 | 说明 |
|---|---|---|
| `configure.py` | `initialize`、`main` | `tools/llm.py` 调用 `initialize` |
| `configuration.py` | `load`、`validate`、`platform`、`model` | 安装输入与模型输入校验；`tools/llm.py`、`import_model_source.py` 导入 `model` |
| `layout.py` | `Layout` | `tools/llm.py` 与验证工具导入 |
| `files.py` | `path_without_links`、`regular_file`、`linked`、`sha`、`save`、`writer` | 文件原语；`tools/llm.py`、`import_model_source.py`、`lock_deployment.py`、`check_deployment.py` 与验证工具导入 |
| `release.py` | `load`、`FORMAT`、`UNITS`、`TARGETS`、`HEX`、`digest`、`pins`、`canonical`、`file_record`、`wheel_metadata`、`read_json` | 发行清单格式；`tools/lock_deployment.py`、`check_deployment.py` 导入 |
| `build.py` | `build`、`build_wheels`、`assemble`、`main`；构建步骤 `build_wheel`、`validate`、`inputs`、`build_skills` | 发行构建的唯一库面：`tools/build_deployment.py`、`build_packages.py`、`check_vendor.py`、`build_access_skills.py`、`lock_deployment.py`、`check_deployment.py`、`install_swarm.py` 只从这里导入 |

## 其他入口

| 文件 | 调用方式 | 说明 |
|---|---|---|
| `install.sh`、`upgrade.sh` | Linux 受管入口脚本 | `umask 077` 后转交 `python -m deploy install` 或 `upgrade` |
| `__main__.py` | `python -m deploy`：install、upgrade、status、start、stop、repair-bootstrap、`_worker` | 部署者命令；`_worker` 只由 `Job.submit` 经 `systemd-run` 调用 |
| `configure.py`、`migrate_configuration.py`、`environment.py`、`workspace.py`、`build.py` | `python -m deploy.<文件>` | 平台 JSON 创建、一次性导入、单元环境安装核验、部署方九问工作区、发行构建；`Installation.candidate` 在 build 环境以 `-c` 调用 `build` |

## 内部分区

| 分区 | 文件 | 职责 |
|---|---|---|
| 命令入口 | `__main__.py`、`install.sh`、`upgrade.sh`、`configure.py`、`migrate_configuration.py` | 命令解析、提交或观察原任务、平台 JSON 创建与一次性导入 |
| 发行与安装链路 | `build.py` → `wheels.py`、`vendor.py`、`dependencies.py`、`skills.py`、`release.py`；`install.sh`、`upgrade.sh` → `__main__.py` → `jobs.py` → `installation.py` | 构建内容发行；受管安装与升级由独立任务执行，配置、单位、备份和激活各调用所属模块 |
| 布局与输入 | `layout.py`、`configuration.py`、`configs.py` | 三根认领与部署标识；安装输入与平台投影校验；角色配置一次生成 |
| 发行与环境 | `build.py`、`wheels.py`、`vendor.py`、`dependencies.py`、`skills.py`、`release.py`、`builder.py`、`environment.py`、`activation.py`、`processes.py` | 发行构建（项目 wheel、vendor 核验、单元锁输入、产品技能 ZIP）；发行清单核验；build 环境；单元环境安装与导入核验；环境集合与 `current` 切换；子进程最小环境 |
| Linux 任务与系统 | `jobs.py`、`installation.py`、`repair.py`、`lifecycle.py`、`units.py`、`linux.py`、`backup.py` | 临时 service 任务与父子请求；安装与升级阶段；控制器修复准入；启动停止；单位生成；账号、权限与 systemd 窄操作；切换前备份 |
| 九问工作区 | `workspace.py` | 部署方九问工作区准备与模型配置 |
| 文件原语 | `files.py` | 无链接路径、普通文件核对、文件摘要、私有 JSON 原子写入（0600、fsync、临时文件改名）、OS 写锁；各原语只此一份 |
| 模板与种子 | `platform.json.example`、`deployment.json.example`、`default-seed.json`、`nginx.conf`；`official.example.json`、`access-runtime.json.example`、`access-jiuwen.json.example` | 平台 JSON 与安装输入模板、种子清单（`tools/build_seed.py` 生成，构建时进入发行）、反代示例；后三个分别是官方服务与 SDK 的配置示例，由其文档引用 |

## 存储与迁移

数据位置见[接口](接口.md#独占数据与配置)。记录文件都带 `format` 字段（`ioalab.deployment-layout/1`、`initial-configuration/1`、`installation-job/1`、`deployment-environment/1`、`environment-set/1`、`deployment-release/1`、`owned-swarm/1`），格式或身份不符一律拒绝而不重建。可变记录（含环境 `owner.json`、`state.json`、`deployment.json`）一律经 `files.save` 以 0600 临时文件改名写入；安装任务与受管单位本就以 `UMask=0077` 运行，原 `environment.atomic` 写出的文件同为 0600，统一后服务账号可读性不变，环境可读由 `linux.expose_runtime` 授予；初始与生成文件经 `layout.write_initial` 排他创建，已存在时只核同内容。唯一的格式迁移是 `migrate_configuration`：把已完成部署的 `core.env` 导入平台 JSON，原输入归档为 `initial.before-platform-config.json`，意图记于 `configuration-migration.json`。

## 管理员助手替换与国内邮件

`administrator.py`提供mail-login与replace-admin-assistant入口：前者只初始化受管Agently CLI与agents私有OAuth，后者要求原部署全停和锁释放，按阶段停用原ISC身份、撤下接口、归档旧运行目录及工作区，再准备新的admin实例。`agently.py`只处理固定官方二进制的SHA512验证与独立工具目录；Python运行环境不现场补包。正常start先等核心就绪并准备/更新邮箱投影，再起原生宿主与参与方。

首次替换尚无新 SDK 配置时，`execution_leases`核对显式替换阶段、原归属及归档身份，持有归档 SDK 的真实执行锁，不把缺配置视为锁已释放。正常启动等待不同于停机前的 InvocationID，避免 systemd 尚返回旧标识时错误绑定；邮箱就绪投影读取当前显式邮件选择，不沿用初次安装的空配置。
