# A2C 适配

## 目的与范围

本文定义 IoA Lab 如何复用原 A2C Client、Provider、Market 及 AP2 执行一次委托，包括开工、环节授权、交付、验收、付款与结清。它是 SDK 与平台公共协议服务之间的适配契约，不增加 A2C/AP2 字段、签名或合同状态机。用户顺序见[委托交易](../流程/委托交易.md)，调用入口见两角色 SDK。

## 原操作与协议存储

| 对象 | 契约 |
|---|---|
| 协议存储 | 每个 agentId/interactionId 独立命名空间，保留原 Store 接口，存入同一个常驻数据库；不新建私钥库或第二个写入进程 |
| 业务操作 | 本地 RPC、作业及宿主工具调用均先保存稳定操作 ID；一次操作中的原方法调用关联该操作，多个业务动作可调用同一原方法 |
| 原方法调用 | 独立 messageId、原方法/body/taskId、文件摘要与操作回执；同键异参数报冲突，不以 `(交互,方法)` 限制整份合同只能调用一次 |
| 重试 | 恢复已保存的原报文、签名、文件及消息 ID，不重新生成时间戳；改变业务输入另建动作，不能覆盖原记录 |
| 数据升级 | 升级已有调用表时保留所有原 messageId、任务、结果和引用；旧初始流程的运行键继续可恢复 |

发送前保存准确原件，平台接收后再授予文件读取权。原请求不得跨交互复用。首次拟卡/复签仍受单份承诺约束，允许多次方法调用不表示允许同一预留生成另一份报价承诺。

## 履约调用

| 阶段 | 原接口与方向 | 前提与真实结果 |
|---|---|---|
| 开工 | Client.start → Provider work.start | 有效成约卡、已选完整价款及原接单关系；原定金付款、材料授权、接收回执分别保存 |
| 环节请求 | Provider.request_step → 原交付任务进展 | 仅合同声明的环节；保存原 stepRequest 并推送 auth-required，不由模型声称已授权 |
| 环节答复 | Client.answer_step → step.authorize | 当前 stepRequest 摘要、卡载用户密钥与独立真实答复；保持原交付 taskId，同意或拒绝均按原协议记录 |
| 交付 | Provider.deliver → Market delivery.anchor | 真实字节与签4清单，取得原签5后才报告已存证；同一期不得改换已经认证的清单 |
| 取件 | Client.fetch_delivery → delivery.fetch、acceptance.notify | 复用原清单及字节核验、签6和缓存；本机文件保存、路径回执及输出失败边界见[个人助手端 SDK](个人助手端SDK/委托交易入口.md#取件文件保存) |
| 预览验收 | Client.verify | 本地 WASM 验收器报告；不签7、不付款 |
| 确认验收 | Client.accept → acceptance.notify、AP2、payment.notify | 独立验收确认后复验；通过才签7，原 SDK 随后请求相应分期付款；验收及付款各自报告 |
| 付款恢复 | Client.pay → 原 AP2 及 payment.notify | 核原签5/7、用途和期次，沿原付款尝试恢复；明确拒绝后的新尝试须先核实并独立确认，不重验收、重签7或重复过账 |
| 解除报价 | Client.termination_quote → termination.quote | 原成约卡已登记；返回本期签名报价，不解除、不付款 |
| 解除决定 | Client.terminate → termination.notify | 独立真实确认后保存原通知；协议解除、送达、补款/退款、执行收敛分别报告 |
| 结清与信誉 | Provider.close → Market card.close；查询信誉 | 平台核原终态与实际应付款凭证后，原结清结果、接单释放及关闭通知一起提交；信誉来自真实结清日志 |

验收确认预览显示本期交付、实际报告与通过后应付金额；不新增替用户作决定的默认值。`accept` 可能已签7但付款未完成，结果必须区分接受证据、支付状态与通知状态；失败或未知不能将已有签名抹掉或伪装成全部完成。付款仍须遵守当前有效预算许可，续期不重置支出。

验收及验收预览通过持久作业异步返回，本机RPC不持锁等待WASM或模型。accept首次调用先登记原操作并进行预览验收：失败则返回真实报告，不请求确认；通过则保存对应卡、期次、报告及应付金额，创建独立用户确认并返回waiting。用户同意后沿原operationId续接同一作业，原Client.accept再次验收，通过才签7和请求付款。重传恢复原预览/确认，不能把模型观察或预览完成作为用户同意。等待期间，本地恢复器依据原确认自动收尾拒绝或过期的操作并释放本地作业等待；不要求模型再次调用。用户批准只供原操作续接使用，不触发另一个操作。已发生效果或结果未知的操作继续按原证据恢复，不能以确认到期删除其事实。

### 已验收期的付款恢复

| 已核实事实 | 恢复规则 |
|---|---|
| 原成功 | 核付款凭证并交原Client.pay补通知；只有对应payment.notify实际ok=true才完成通知，不能仅因本地已有voucher结束恢复 |
| 原明确拒绝 | 核本机准确AP2 body、原控制ID、账号/身份、admission及平台认证原操作拒绝回执；由可信适配器向上游报告PaymentRejected，保留原尝试，不修改上游私有状态 |
| 原未知 | 沿准确原body与控制ID核实，跨业务操作恢复也不得换ID重新提交；404、通用异常或模型声称未付均不是明确未付款 |
| 再次付款 | 先核实际付款记录及同付款键全部本地控制尝试/outbox；只有原尝试均明确拒绝、无付款且无未决，才由可信宿主回调返回上游PaymentReconciliation，并在独立付款确认及当前有效预算内申请新授权 |
| 原验收作业 | 已有真实签7、原验收通知及可信付款拒绝时，收敛为已验收、未付款并保留拒绝，不重调accept；签名、付款、通知与结清各自报告 |
| 升级前只读付款作业 | 没有本次付款预览与真实批准的旧pay检查点只允许查凭证、恢复原通知；明确未付时结束并提示创建新付款操作，不能因SDK升级变成付款动作 |

可信核对是SDK装配能力，不接受模型提供的未付款、无未决或已回滚布尔值。新确认绑定原卡、期次、应付金额及已核原尝试；已有事实恢复不重新签字，新增过账前复核执行资格与授权。新尝试保存旧准确body和拒绝，不覆盖未知或从未决尝试分叉。

已有运行数据中的拒绝证据可沿原认证WS回执恢复，但不能把任意forbidden视为付款拒绝。旧版唯一的提交回滚错误须匹配完整已知code/message、准确原请求和控制ID，且公开付款及原操作查询未发现成功、同键尝试无未决；缺任一事实仍保留unknown。该核对只解释原记录，不重写历史或建立旧付款执行分支。

### 多期履约

| 约束 | 行为 |
|---|---|
| 原链路 | 同一合同、交互UUID、work.start任务及固定Session贯穿各期；不为下一期重签合同、重收拟卡费或新建交互 |
| 逐期推进 | 服务方只在前期签7及应付的真实付款凭证齐备后排产下一期；首期或中间期完成不释放整单容量 |
| 独立授权 | 环节请求及用户答复绑定卡、期次和原请求摘要；上期同意不能授权下期，等待用户期间控制仍可处理 |
| 原文件与操作 | 各期文件与原签6/7、付款用途/期次及方法调用分别保存；同名文件不覆盖已取得的早期成果，重传不增加签名或付款 |
| 重启与未知 | 保存原身份、Session、模板和全部期次记录；依据原回执恢复丢响应，不自动重跑未知生产或把上期确认用于下期 |
| 取件网络中断 | 仅HTTP传输失败，且原本地卡尚无本期签6、无本期缓存时，可确认本次读取失败，返回failed及retry_read；原operationId重传仍返回原失败。在原取件请求内可创建新读取操作，沿原合同/期次/Task核原清单，无需新增验收或付款授权；已有签6或结果不明仍按原证据核对，不重新签收 |
| 结清 | 全部期次依原协议终态及实际应付款凭证完成后才调用原结清；原结果去重，信誉和容量只更新一次 |

## 原任务与生产

| 对象 | 契约 |
|---|---|
| 接收执行 | 原请求开始许可和本地检查点在先；以原消息派生稳定任务 ID，先推送进展，再运行原延期部分 |
| 交付任务 | work.start 的原 Task 贯穿环节、交付和结清；Task.op 保留创建方法，后续 step.authorize 等请求不能改写它 |
| 快照 | 保存 id、op、state、artifacts、status；Reply.files 与 Task.files 分别传递，同名文件不得覆盖 |
| 推送 | 原任务进展持续更新；可附实际签名卡原件供 SDK 验签后展示可取件期次，不能把自然语言进度当交付 |
| 本地读取 | get_task 读取已落库的最新推送；原 Client.poll 读取环节请求，取件不以先建立市场观察任务为前提 |
| 生产调度 | on_start 只登记生产并返回，不持原 Provider 锁等待模型；生产在独立受控作业中使用本单原 Session |
| 业务等待 | 发出环节请求或本期交付后持久等待并结束本轮；原答复/验收/付款条件满足后续接同一业务，不自动重跑 unknown |

服务方的 Agent、工具及技能定义在第一次业务轮次前固定，阶段变化不偷偷扩大权限或换 Session。每轮给出实际阶段及允许动作。环节拒绝不能视为同意；本单工具检查原请求和答复，已拒绝或未答复时不得执行受保护动作。后续期次的本地排产策略不暂停 A2C 时钟，也不改写合同期限。

提案准备可使用本单验收器打包回调；它只创建有界、按摘要寻址的验收包，不提供服务管理或生产效果。其身份、阶段、复用与未知处理以[服务方端SDK](服务方端SDK.md)为准；前台管理上传与该回调共用同一实现。

生产工具只接受本单数据及有界成果。文件来源可以是 text、bytesBase64，或本次工作区 artifacts 下的相对文件；解析后须仍在本单目录，拒绝越界、符号链接逃逸及其他交互文件。自测使用原验收器沙箱，报告与委托方验收分开；真实交付不等于已经通过对方验收。行业知识、实名业务工具与具体生产程序由本机配置的业务技能/工具提供，不写进通用协议模块。

自测先在短锁内登记原调用及冻结输入，再释放共享写锁执行验收和模型观察，最后保存真实报告；不得持SQLite事务或共享调度锁等待。原SDK的单交互串行约束继续保留，不绕过其签名和任务规则。两角色的观察接入与会话范围统一见[SDK共用机制](SDK共用机制.md)。

## 证据与恢复

拟约的前半段核验与后半段业务决定由原A2C Provider持有。续接拟约使用Provider.resume_request及原finish，不删除原请求版本记录、不重新request.submit，不在平台SDK复制拟卡或签认逻辑；可续接范围和宿主结束证明见[服务方端SDK](服务方端SDK/接单与任务恢复.md#原拟约任务的恢复)。

平台在首次履约时核对原成约签名、已选卡、原承诺及归属，保存冻结模板和实际签名证据。旧模板退出公示、委托意向或新委托授权到期，不删除已有合同，也不阻断其证据及必要控制；新的资金动作另外检查当前许可。不得用面向新候选的资格检查拒收既有合同。

首次委托意向取得本地保存的明确拒绝回执，且经平台原操作查询确认没有受理记录时，原报价作业收敛为rejected；正常推进与重启恢复使用同一规则，不重新提交意向、拟约或付款。原操作查询须区分从未受理的404与回执已离开保留期的history_gap；只有404、只有本地异常、历史缺失、平台查询失败或平台已有受理记录，均不足以按未受理结束；保留unknown并核原结果。进入原A2C调用后的恢复继续依赖对应签名与原回执。

首次成约后，个人助手以 contract.bind 控制操作登记原有效卡；未知时恢复原签名和登记，不能重签。登记不依赖定金或开工，也不发起生产。合同用途的 ap2.checkout 或 work.start 可核实同一原件，不能取代成约登记。登记只消费实际成约签名，不另生成合同。原接单、原公示模板、已签提案/复签结果和用户选择须共同对应同一张卡；以后只能沿其固定身份与签名链继续。环节答复除验自签外，还须匹配冻结卡载用户及原 Task 中的 stepRequest；后续方法不能借用另一合同的交付任务。

开始许可一旦发给 work.start，结果未知按可能已开始处理，不能因消息 TTL 或模型结束释放容量。签名链、实际原回执和任务约束是恢复依据；没有足够证据则保持 unknown，不重新开工、签署、通知或付款。准确的已保存事实可补齐原 Store、原任务与结果投递，不另造协议状态。

已开工合同的模型生产轮次按[服务方端SDK的原生产恢复契约](服务方端SDK/接单与任务恢复.md#原生产任务的恢复)核实并显式续接，继续使用原work.start任务、合同及Session；不重发开始或已发生的效果，不把所有者审阅声明改写成原Host或协议终局证据。

控制消息只推进其对应的原协议任务。实际签7、付款凭证和市场结清分别保存；未知生产不授予新的业务执行权限，也不妨碍校验、接收已有签名及核实原结果。容量、付款与释放的不变量分别归委托中心、支付中心和本地接入组件。

## 解除与结清

| 阶段 | 约束 |
|---|---|
| 原合同 | 平台分别保存不可变成约原卡及已核进展；request.start许可携带contractCard及实际支付记录中的原depositVoucher，由宿主调用Provider.bind_contract校验导入；不伪造work.start、重付定金或覆盖已有进展 |
| 报价 | 协商模式先取得原 termination-quote；核原服务方、合同、首个未验收期次、金额上限及应答期限。报价不构成用户同意 |
| 用户决定 | 预览原报价、实际已付定金、补款或退款及单方解除的后果；真实确认绑定本次模式、合同进展、实际定金与报价摘要；签署前若预览依据已变则重新预览确认。已签原通知恢复不要求用户重新批准同一既成决定。不得按模型 confirmed 自行解除 |
| 协议生效 | 原 Client.terminate 在发送前保存签名通知和本地解除事实；平台验签并保存该事实后阻止新的履约开始。服务方复用原 Provider 接收，不另造协议状态机 |
| 结算 | 复用上游 termination_balance/payment_terms，定金仅认实际过账。正余额由委托方补付，负余额由服务方经原 AP2 Port 向原委托方退款，零余额无付款/凭证；单方解除无协商结算依据 |
| 逆向收款单 | 原服务方在同一交互请求 ap2.checkout，个人助手仅为已确认的同单负余额调用 Client.refund_checkout；双方沿原控制通道收发，不发布收费个人助手接口 |
| 执行收敛 | 本地接入组件停止新排产及新业务工具，等待原执行者和已开始工具真实收尾；未知外部效果保留检查点。解除通知已确认不等于模型/工具已停止，不立即释放名额 |
| 完成 | 服务方在执行已收敛后，用原 Provider.close 提交真实卡。平台核全部原签名、实际应付款及必要退款，再原子保存结清、释放接单、关闭交互；重传不增加信誉 |
| 恢复 | 原通知、报价、AP2授权、回执及请求标识保持原件；丢响应先查询原记录。消息TTL不延长协议签名或应答期限；过期且未能核实的动作保持待核实，不重签或重付 |

未开工、未交付合同可以依法定协议解除；不存在签4/5时不强造存证。已有交付必须逐项匹配市场实际存证前缀，已验收期次须核实际付款；不能借解除省略既成义务。合同解除、资金处理、执行收敛及市场结清是不同事实，状态查询分别返回。

## 仲裁与原执行结束

| 适配点 | 契约 |
|---|---|
| 原依据 | 双角色SDK从本单记录确定原admission，取证预览与案件沿共用平台接口，不传替代卡；用户确认、受理和裁定分开 |
| 原协议 | 委托中心以原签认快照调用Market.recompute，依原判据处理；已成约终局调用record_ruling，不把平台异常伪装成程序结论 |
| 本地推进 | 核市场文书签名、原case/admission/subject、公开决定证据摘要及原卡签名后停止本卡新履约；签名时间与issuedAt一致，历史有效文书不使用新请求新鲜度过期。复用已有调度排空及未知效果核对；同UUID/Session的原结果仍可恢复 |
| 结束 | 裁定禁止后续anchor与card.close；原执行/协议Task收敛及冻结卡既有应付款齐全后，提交IoA原结束回执，不走正常结清或解除，不新增合同字段 |
| 证据保留 | 原已验收付款依据及实际凭证保留，裁定不执行付款；结束状态与债务状态分别返回 |

完整成立条件、案件最终性及容量规则只在[委托中心](../组件/委托中心.md#争议案件与原证据)维护；本节只定义跨端适配。无已成约卡的拟卡费争议使用原请求文书，不调用合同record_ruling。
