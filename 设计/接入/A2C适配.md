# A2C 适配

## 目的与范围

本文定义 IoA Lab 如何复用原 A2C Client、Provider、Market 及 AP2 执行一次委托，包括开工、环节授权、交付、验收、付款与结清。它是 SDK 与平台公共协议服务之间的适配契约，不增加 A2C/AP2 字段、签名或合同状态机。用户顺序见[委托交易](../流程/委托交易.md)，调用入口见两角色 SDK。

## 原操作与协议存储

| 对象 | 契约 |
|---|---|
| 协议存储 | 每个 agentId/interactionId 独立命名空间，保留原 Store 接口，存入同一个常驻数据库；不新建私钥库或第二个写入进程 |
| 业务操作 | 本地 RPC、作业及宿主工具调用均先保存稳定操作 ID；一次操作中的原方法调用关联该操作，多个业务动作可调用同一原方法 |
| 原方法调用 | 独立 messageId、原方法/body/taskId、文件摘要与操作回执；同键异参数报冲突，不以 `(交互,方法)` 限制整份合同只能调用一次 |
| 重试 | 恢复已保存的原报文、签名、文件及消息 ID，不重新生成时间戳；改变业务输入另建动作，不能覆盖原记录 |
| 数据升级 | 升级已有调用表时保留所有原 messageId、任务、结果和引用；旧初始流程的运行键继续可恢复 |

发送前保存准确原件，平台接收后再授予文件读取权。原请求不得跨交互复用。首次拟卡/复签仍受单份承诺约束，允许多次方法调用不表示允许同一预留生成另一份报价承诺。

## 履约调用

| 阶段 | 原接口与方向 | 前提与真实结果 |
|---|---|---|
| 开工 | Client.start → Provider work.start | 有效成约卡、已选完整价款及原接单关系；原定金付款、材料授权、接收回执分别保存 |
| 环节请求 | Provider.request_step → 原交付任务进展 | 仅合同声明的环节；保存原 stepRequest 并推送 auth-required，不由模型声称已授权 |
| 环节答复 | Client.answer_step → step.authorize | 当前 stepRequest 摘要、卡载用户密钥与独立真实答复；保持原交付 taskId，同意或拒绝均按原协议记录 |
| 交付 | Provider.deliver → Market delivery.anchor | 真实字节与签4清单，取得原签5后才报告已存证；同一期不得改换已经认证的清单 |
| 取件 | Client.fetch_delivery → delivery.fetch、acceptance.notify | 核原清单及字节，保存原签6和本地文件；已取件恢复原缓存，不重复签收 |
| 预览验收 | Client.verify | 本地 WASM 验收器报告；不签7、不付款 |
| 确认验收 | Client.accept → acceptance.notify、AP2、payment.notify | 独立验收确认后复验；通过才签7，原 SDK 随后请求相应分期付款；验收及付款各自报告 |
| 付款恢复 | 原 AP2 及 payment.notify | 沿原用途、期次和原支付操作恢复；不能再调用 accept 重签7或创建第二笔付款 |
| 结清与信誉 | Provider.close → Market card.close；查询信誉 | 平台核原终态与实际应付款凭证后，原结清结果、接单释放及关闭通知一起提交；信誉来自真实结清日志 |

验收确认预览显示本期交付、实际报告与通过后应付金额；不新增替用户作决定的默认值。`accept` 可能已签7但付款未完成，结果必须区分接受证据、支付状态与通知状态；失败或未知不能将已有签名抹掉或伪装成全部完成。付款仍须遵守当前有效预算许可，续期不重置支出。

验收及验收预览通过持久作业异步返回，本机RPC不持锁等待WASM或模型。accept首次调用先登记原操作并进行预览验收：失败则返回真实报告，不请求确认；通过则保存对应卡、期次、报告及应付金额，创建独立用户确认并返回waiting。用户同意后沿原operationId续接同一作业，原Client.accept再次验收，通过才签7和请求付款。重传恢复原预览/确认，不能把模型观察或预览完成作为用户同意。等待期间，本地恢复器依据原确认自动收尾拒绝或过期的操作并释放本地作业等待；不要求模型再次调用。用户批准只供原操作续接使用，不触发另一个操作。已发生效果或结果未知的操作继续按原证据恢复，不能以确认到期删除其事实。

## 原任务与生产

| 对象 | 契约 |
|---|---|
| 接收执行 | 原请求开始许可和本地检查点在先；以原消息派生稳定任务 ID，先推送进展，再运行原延期部分 |
| 交付任务 | work.start 的原 Task 贯穿环节、交付和结清；Task.op 保留创建方法，后续 step.authorize 等请求不能改写它 |
| 快照 | 保存 id、op、state、artifacts、status；Reply.files 与 Task.files 分别传递，同名文件不得覆盖 |
| 推送 | 原任务进展持续更新；可附实际签名卡原件供 SDK 验签后展示可取件期次，不能把自然语言进度当交付 |
| 本地读取 | get_task 读取已落库的最新推送；原 Client.poll 读取环节请求，取件不以先建立市场观察任务为前提 |
| 生产调度 | on_start 只登记生产并返回，不持原 Provider 锁等待模型；生产在独立受控作业中使用本单原 Session |
| 业务等待 | 发出环节请求或本期交付后持久等待并结束本轮；原答复/验收/付款条件满足后续接同一业务，不自动重跑 unknown |

服务方的 Agent、工具及技能定义在第一次业务轮次前固定，阶段变化不偷偷扩大权限或换 Session。每轮给出实际阶段及允许动作。环节拒绝不能视为同意；本单工具检查原请求和答复，已拒绝或未答复时不得执行受保护动作。后续期次的本地排产策略不暂停 A2C 时钟，也不改写合同期限。

生产工具只接受本单数据及有界成果。文件来源可以是 text、bytesBase64，或本次工作区 artifacts 下的相对文件；解析后须仍在本单目录，拒绝越界、符号链接逃逸及其他交互文件。自测使用原验收器沙箱，报告与委托方验收分开；真实交付不等于已经通过对方验收。行业知识、实名业务工具与具体生产程序由本机配置的业务技能/工具提供，不写进通用协议模块。

自测先在短锁内登记原调用及冻结输入，再释放共享写锁执行验收和模型观察，最后保存真实报告；不得持SQLite事务或共享调度锁等待。原SDK的单交互串行约束继续保留，不绕过其签名和任务规则。两角色的观察接入与会话范围统一见[SDK共用机制](SDK共用机制.md)。

## 证据与恢复

平台在首次履约时核对原成约签名、已选卡、原承诺及归属，保存冻结模板和实际签名证据。旧模板退出公示、委托意向或新委托授权到期，不删除已有合同，也不阻断其证据及必要控制；新的资金动作另外检查当前许可。不得用面向新候选的资格检查拒收既有合同。

首次登记可由合同用途的 ap2.checkout 或 work.start 触发；定金付款先于开工，不能要求先开工才能付款。登记只消费实际成约签名，不另生成合同。原接单、原公示模板、已签提案/复签结果和用户选择须共同对应同一张卡；以后只能沿其固定身份与签名链继续。环节答复除验自签外，还须匹配冻结卡载用户及原 Task 中的 stepRequest；后续方法不能借用另一合同的交付任务。

开始许可一旦发给 work.start，结果未知按可能已开始处理，不能因消息 TTL 或模型结束释放容量。签名链、实际原回执和任务约束是恢复依据；没有足够证据则保持 unknown，不重新开工、签署、通知或付款。准确的已保存事实可补齐原 Store、原任务与结果投递，不另造协议状态。

控制消息只推进其对应的原协议任务。实际签7、付款凭证和市场结清分别保存；未知生产不授予新的业务执行权限，也不妨碍校验、接收已有签名及核实原结果。容量、付款与释放的不变量分别归委托中心、支付中心和本地接入组件。
