# 接入

## SDK 与技能

`sdk/` 发布 `ioalab-sdk`，模块 `ioalab_sdk`，依赖 A2C 与 httpx；不依赖 `ioalab`、A2X 或九问。个人助手技能用确定性 CLI 调 SDK；官方服务技能用服务角色入口访问本单 Provider，不再写一套签名、金额、期限或验收规则。

技能安装包包含引导脚本及锁定的依赖清单/摘要。首次调用自动在用户目录建立隔离环境、安装 SDK 与 A2C，成功后原子写就绪标记；失败不留下伪就绪状态。后续只做版本检查。输入仅为平台地址、用户名和密码；模型配置使用用户已有九问设置。引导不修改用户九问或全局 Python 环境。SDK 安装来源与版本由发布清单确定，不执行平台返回的任意安装命令。

## 平台 REST（`/api/v1`，Bearer 认证）

| 方法 路径 | 职责 |
|---|---|
| `POST /token` · `GET /me` | 登录与账号信息；不创建任何运行实例 |
| `GET /identity/challenge` · `POST /identity` | 获取一次性挑战、绑定本地身份与付款公钥 |
| `POST /search` · `GET /providers/reputation?provider=` | A2X 检索与市场签发的信誉 |
| `POST /provider/register` · `/provider/refresh` · `GET /provider/mine` | 服务登记、刷新与所属检查 |
| `POST /provider/packages` · `GET /packages/{digest}` | script 包上传、公开按摘要下载 |
| `POST /observations` | 登录身份上报阶段或合同副本；验证关系与签名后更新观察投影 |
| `GET /orders/{digest}` | 账号所属合同观察视图；不保证替代本地合同原件 |
| `POST /arbitrations` | 当事方提交合同、报告和证据，市场处理争议 |

合同操作直接使用 A2A/A2C：市场 `/a2a/market`、支付 `/a2a/pay`、服务进程独立地址 `/a2a/providers/<id>`。平台 REST 不提供代用户拟卡、签字、开工、取件、验收、付款的接口。

观察对象为 `{id, source, op, card?, detail?}`：id 用于幂等，source 为 client/provider/experiment；账号由登录态确定，禁止指定别人 owner。带 card 时核标准签名链与账号/服务关系；纯阶段事件只记为 reported。完整模板仍经服务方 `template.get` 获取和核验，不用去掉签名的摘要替代。

消息接口与SDK收件规则见[消息中心](消息中心.md)。浏览器与SDK使用相同所属检查；服务方视图增加账号所属服务与订单查询，不能仅查委托人owner。

## 网络与身份

个人助手只需要主动 HTTP 连接，无需开放本地端口。服务端点必须能被双方与市场访问，官方服务反代为单独路径或端口；URL、Agent Card、模板 provider 和 JWKS 必须一致。API token 只发给平台，不发给第三方服务。验收器内部 URI 由 SDK 的取包适配器解析，不能直接交给通用 HTTP 客户端。

## 个人助手技能与交互类型

交付一个IoA个人助手skill。用户在九问原生技能菜单选中它，模型调用原生skill_tool读取完整说明；用户填写平台地址、账号与密码即可使用；首次调用安装锁定SDK。保留既有技能目录标识以兼容安装，显示名为IoA个人助手。安装器不改九问源码、技能模式、渐进工具开关或全局AGENT.md，不注入隐藏用户提示。未预选时的自动发现受宿主及模型影响，单独报告，不作为可靠入口前提。

| 类型 | 路由依据 | 按需读取 | 调用边界 |
|---|---|---|---|
| 委托交易 | 寻找公开服务、约定成果/验收/价款 | skill的references/delegation.md | 按通用流程逐项调用SDK合同接口；收费接口须在确认的范围内 |
| 私人交互 | 向指定账号交流、预约、回复或读取自己的收件箱 | skill的references/private-interaction.md | 先读取对方可访问接口与inputSchema，再发送结构化消息；不经A2X、不签合同 |

主skill只维护路由、运行约定与共同边界；新增类型只需增加路由项和独立流程页。混合需求按用户目的拆成有关联的子流程，各自保留授权边界；不因消息含价格或预约一词就自动转成委托。没有明确对象/类型时只询问缺少的业务信息。

## 委托交易通用流程

| 顺序 | 行为与接口 |
|---|---|
| 1 | 从需求提取目的、预算及限制，说明拟卡费上限和授权有效期；用户确认后authorize。未确认不付拟卡费、不签约 |
| 2 | search发现；reputation和templates读取真实信誉及完整验签模板。依交付能力、材料、规格、价格、验收、期限筛选；材料不足先请求用户补充，不一概排除 |
| 3 | 按各模板建立spec与materials；提案型request绑定scope_id，其他成约方式draft同样绑定scope_id。候选数量与推荐理由由实际结果及用户偏好决定，不固定三家、不强制script优先 |
| 4 | inspect读取真实卡和模板；必要时compare记录多方比较。向用户说明具体交付、规格及默认值、分期、金额、拟卡费总额、验收、未覆盖项、期限和亲签条款；确认具体合同后adopt/sign，再start |
| 5 | watch/poll；只有收到合同声明的stepRequest才询问相应授权，再answer-step。环节可以没有、一个或多个；实名注册不是通用前提 |
| 6 | 按实际存证期号fetch、verify；pending等到notBefore再验，fail/error不签7、不付款。展示真实报告及本期金额，得到用户确认后accept |
| 7 | 多期逐期重复等待、取件、验收、确认与读卡付款；所有期完成后才报告整单完成。恢复用scope/inspect/poll；结果未知先核实，不重付、不重新发起同一委托 |

模型负责业务理解、模板阅读、材料补齐、推荐与用户交流；SDK负责身份、签名、计算、预算/拟卡费约束、幂等恢复及WASM验收。SDK默认不授予拟卡费支出；授权必须显式列明上限，包含在总预算内。确认通过--confirmed表达，不代表SDK能自行证明用户说过同意。

## 多候选比选的阶段边界

候选资格、正式报价与最终推荐分三阶段。发现后逐项读取真实模板，记录入选或排除的依据；同一需求的合格服务形成候选集合。先按授权拟卡费和总预算征集该集合的正式合同，再横向比较并请求用户确认；不能因为第一家验收覆盖更广，就跳过其他合格候选的正式报价。

多个合格候选且费用允许时，通用流程允许并要求多选征集；数量由模板适配、实际候选及授权费用决定，不固定三家。用户明确指定单方、仅一方合格或费用不足时如实解释；需要补充材料或调整费用时请求用户决定，不伪造报价。验收覆盖项更多不等于服务质量保证更高；推荐按真实覆盖、金额、期限及用户偏好说明。

原美甲演示不设最低三份的账号偏好，用真实模板筛选产生三家；可配置下限保留为独立可选功能，不用于证明上述通用流程已通过。

## 可配置比选策略

SDK提供客户端策略IOALAB_MIN_QUOTES，取值1—8、默认1；不是平台强制规则，也不是行业剧情。用户可按账号配置，单次authorize可要求更高数量，但不得低于已配置下限。me只额外返回公开策略摘要，不读取或回显密码。私人交互不受委托比选策略约束。

| 时点 | 规则 |
|---|---|
| 授权 | scope固化minimumQuotes，向用户说明最低比较数量、预算、拟卡费上限与有效期；数量不得通过后续调用静默降低，仍受拟卡费总限额约束 |
| 征集 | request/draft回执附quoteProgress：最低数量、已收集数、待核实费用、readyForConfirmation及下一步；低于最低数继续征集，不请求合同确认 |
| 计数 | 仅计本scope、金额及全部拟卡费仍在预算内的已核验候选；同一服务端点多张卡只计一次。提案型必须实际取得签名提案；其他成约方式依据已验签模板及同一A2C拟卡算法，不另写算价规则 |
| 确认 | 费用不明先核实；最低数量不足时sign/adopt不得签字。满足后仍由模型阅读和比较事实、推荐具体合同，并等待用户确认；SDK不替用户选择服务或判据 |
| 恢复 | quote-progress只读计算当前进度；重复request缓存返回时重算进度。已确认选中的比较证据保留；旧scope没有该字段时按原默认1恢复，不追溯新增约束 |

examples/nail-booking中的三份比选偏好仅供可选策略试验，正式通用流程复测不加载该偏好；不进入主skill默认或SDK常量。普通用户不配置时仍可单家委托；用户改变策略须明确配置并对新scope重新授权。只有无法找到足够候选或费用额度不足时，才讨论调整策略或范围，不能伪造报价补数量。

## 私人交互通用流程

接口以账号定向发现，不进公开服务目录；服务端执行身份、白名单、格式、容量及有效期检查，客户端理解业务。发送：interfaces(account) → 按inputSchema构造payload → send → message查询结果。接收：sync持久收件并ack → claim领取有效租约 → 在用户授权的本地范围处理 → complete提交结构化结果；需要协商则用关联消息，不伪造完成。接口定义、白名单与本地日程的修改按用户指令执行。详细状态、重试及长期离线规则见[消息中心](消息中心.md)。

skill只在宿主运行并调用时执行；导入不会建立常驻任务。九问关闭时云端保留消息，恢复后主动sync。无人值守收件是部署者可选的独立接收器，通过公开SDK和宿主扩展接入，不能把它描述为只导入skill便会自动运行。邮件/日程属于选配业务处理器，不是私人交互协议必备条件。

## 示例隔离与既有任务

美甲业务默认值、七家示例服务、筛选偏好、四次确认剧情与演示计划只在examples/nail-booking/及官方服务场景定义中维护，不随通用skill分发。核心SDK不包含美甲字段、指定服务名、固定实名文案或演示成功结果。可恢复delegate兼容入口保留给已建立的本地任务及显式声明计划；不作为主skill默认入口，不替代通用流程。兼容入口只消费外部数据，用户可配置排序；未配置时按定数总价推荐，确认文案来源于实际合同/环节，逐期核实付款。已受管理的合同继续从原taskId恢复，不通过原语绕过既有确认保护。

SDK直接依赖A2C，不依赖任何示例目录或平台核心。升级不清理旧身份、scope或合同。取件重试恢复已签清单对应的本地副本，不重复追加签6。旧演示视频属于原配置下的历史实录，不作为本次纯skill接入验收。
