# 重构后的解耦差距

## 范围与判断依据

本页记录第三阶段整理时，保留实现相对[架构](../设计/架构.md)的职责差距，供后续开发拆分使用；不另定义产品规则。用户已确认第二阶段完成，三片为“发布服务演示”“发起委托演示”“私人交互演示”。本次不重开 Demo 制作，也不将其完成推定为所有非 Demo 功能已经验收。

审查对象为 main 的当前工作区，含原有未提交的部署编排工作；这些在途改动不随本报告提交，不能据此声称远端已经交付。下列结论来自函数、调用方、构建及测试配置的静态核对，不是新一轮真实业务或服务器验收。现行实现进度仍由[开发计划](开发计划.md)维护，运行证据由[验证记录](../demo/verification/README.md)维护。

“未解耦”指跨职责调用或状态所有权仍未收敛；目录名称尚未迁移、功能尚未实现、能力尚未验收分别列出，避免混为一谈。旧路径有明确调用者时仍是有效实现，不能因为名字旧就移入历史备份。

## 保留实现中的职责耦合

### 1. 平台装配入口仍承载业务用例和数据写入

| 代码事实 | 与设计的差距 | 影响与收敛条件 |
|---|---|---|
| [platform.py](../src/platform/ioalab/platform.py) 的 `register_user`、`grant`、`transfer`、`_search` 不只装配对象，还协调身份、支付、发现和事件；`register_external_provider`、`refresh_external_provider` 直接写 `agents` 并刷新 A2X | 架构将启动/关闭交给装配入口，跨中心协调归 `operations.py`，数据写入归所属中心 | 新 `AccountOperations`、`ServiceOperations` 已存在，但旧用例仍绕着装配对象组织。后续应将用例和组件写接口迁入所有者，Platform 留下装配与生命周期 |
| 同文件 `reset_transactions` 直接删除订单、事件、支付和市场存储；有已付款检查，但仍跨多处数据所有者 | 实验维护操作也需要明确协调入口和所属组件边界 | 不能直接删除保护检查或将其当通用生产清理命令；若仍需此能力，由维护用例显式调用各组件接口，并验证拒绝及保留路径 |

这不是“核心运行了私人助手”的证据。本次核对未发现平台 Python 代码导入 `ioalab_sdk`、`ioalab_jiuwen`、`ioalab_services` 或 `ioalab_tools` 来执行参与方业务；主要问题是核心内部的用例归属。

### 2. 旧 market 模块仍混合注册与委托职责

| 代码事实 | 与设计的差距 | 影响与收敛条件 |
|---|---|---|
| [market/__init__.py](../src/platform/ioalab/market/__init__.py) 导出 `Discovery`；`MarketService` 接收 discovery，同时拥有 A2C `AdmissionMarket`、模板签认、认证记录、信誉和裁定方法；[market/discovery.py](../src/platform/ioalab/market/discovery.py) 实现 A2X 检索与索引 | 注册发现应归 registry；A2C 公共服务、信誉、仲裁归 delegation；身份认证需遵守 identity 所有权 | registry 已有公示/分类等新模块，delegation 已有容量/案件等模块，但 market 仍是混合入口。拆分时保留原 A2C 对象与协议调用，不重写协议状态机 |
| `platform.py` 给 ScopeLedger 传入 `self.market.market._template`；[participants.py](../src/platform/ioalab/participants.py) 的 `party` 同样访问这个内部方法 | 跨组件接线依赖了嵌套实现及上游内部方法，而非平台所属组件的窄接口 | 市场包装层变化会牵动身份核验、授权和观察。应由委托组件提供原模板/合同证据读取接口，再切换这些调用 |
| [runtime/llm.py](../src/platform/ioalab/runtime/llm.py) 的同一个 `LLM` 同时实现发现 embedding、分类和仲裁 `model_ports`；[runtime/packages.py](../src/platform/ioalab/runtime/packages.py) 持有验收包管理 | 发现/仲裁模型分别归所属中心，验收包管理归委托中心；平台 runtime 不应与参与方常驻组件混名 | 这里是中心职责集中与位置差距，不表示平台执行服务生产。迁移时同步配置注入、资源读取和既有模型/摘要验证 |

### 3. 合同观察投影仍有两套写入路径

| 代码事实 | 与设计的差距 | 影响与收敛条件 |
|---|---|---|
| 新 [observation/](../src/platform/ioalab/observation/) 与 `ContractProjection` 已存在；旧 `participants.observe` 验签后仍写 `orders`、`observations`，并更新服务 `agents.meta` 的 lastSeen/execution | 合同展示快照应由 observation 独占，身份/服务元数据也应通过所属组件接口更新 | 旧上报观察与新原件投影的写者尚未收敛，后续字段调整和恢复容易遗漏一条路径。应先迁移旧上报所需覆盖和调用，再淘汰旧投影 |
| `Platform.sync_orders` 读取市场 ledger 后更新旧 `orders` 并发事件；其调用者是后台 `_sync_loop` 及旧 `POST /arbitrations`。`order_detail` 仍拼装旧订单、付款、裁定和事件 | 投影构建/读取和跨中心事实组合仍放在装配对象，旧观察路径还依赖市场内部存储 | 应把观察更新和授权查询收归 projection/view 的接口，并保留历史事实、迟报和终态测试 |

这里的 `orders` 是旧合同展示/上报记录；静态证据不支持把上述写入说成更改 A2C 签名原卡或推进付款。`GET /orders/{digest}` 读取详情并核验参与方，本次未发现它调用 `sync_orders`。新工作台不能据旧上报遥测认定履约成功。

### 4. SDK 仍交付直接客户端与常驻运行时两套执行组织

| 代码事实 | 与设计的差距 | 影响与收敛条件 |
|---|---|---|
| [client.py](../src/access/sdk/ioalab_sdk/client.py) 的 `LabClient` 自持身份、`contracts.sqlite`、`outbox.sqlite`、租约和协议 Client；[messaging.py](../src/access/sdk/ioalab_sdk/messaging.py) 的 `MailboxClient` 自持 `mailbox.sqlite`、轮询和处理；[provider/agent.py](../src/access/sdk/ioalab_sdk/provider/agent.py) 的 `ProviderAgent` / `DurableProvider` 自持任务与协议状态 | 目标是两角色复用一个常驻运行时，技能/CLI 通过认证 IPC 调用，身份、收发、恢复只有一个写入所有者 | [ResidentRuntime](../src/access/sdk/ioalab_sdk/runtime/resident.py) 已有统一锁、账号、runtime.sqlite、连接、调度和 IPC，但旧客户端仍由实验、测试和旧服务调用。不能直接移动这些模块；先迁移调用及原有恢复/协议覆盖，再整组退出 |
| `LabClient` 导入 `a2c.integrations.jiuwenswarm.mcp_server.load_identity`；SDK 顶层及 provider 包仍导出旧执行器 | 通用 SDK 的身份组织仍有一条路径绑定上游九问集成；新旧能力同时暴露给开发者 | 新产品接入已走常驻链路，但 SDK 整包还未完成收敛。替换时保留已有身份与未知结果，不自动重建密钥，也不增加旧接口别名 |

共享 `AccountSession` 和互斥锁已经降低重复写入风险；两套入口的存在本身不证明它们当前同时持有同一个身份。需要解决的是旧调用尚未替换、状态及恢复责任仍分散，而非简单重命名文件。

### 5. 旧通知与收件处理仍绑定宿主协议和旧消息 API

| 代码事实 | 与设计的差距 | 影响与收敛条件 |
|---|---|---|
| [SDK swarm_web.py](../src/access/sdk/ioalab_sdk/swarm_web.py) 的 `SwarmWebBridge` 实现九问 WebChannel 的 `ioa.notification.deliver` RPC、桥接令牌及回执持久化；[personal-assistant/assistant.py](../personal-assistant/assistant.py) 直接装配它 | 九问协议实现应归 hosts/jiuwen，SDK 共用运行时只面向 `AgentHost` | 新宿主已有网页通知实现，旧通知路径仍在 SDK 包内。先切换旧助手及回归，再移走旧桥接，保留送达未知/幂等回执验证 |
| [ioalab_tools/handlers.py](../src/official/tools/ioalab_tools/handlers.py) 的 `AssistantHandlers` 直接持有旧 mailbox、其 store/home，并调用 publish/get 等旧接口；旧助手循环 `sync/process` | 日程和邮件已正确移出 SDK，但旧业务处理器仍与旧收件执行机制耦合；通用消息调度应归常驻组件 | 新工具工厂和旧处理器不是同一条执行入口。后续将所需预约/邀请回执和测试迁入新工具/角色路径，再归档旧收件器；不能为文档整理发送真实邮件 |

新 SDK 的角色与共用运行时代码，本次未发现直接导入 `ioalab_jiuwen` 或官方工具实现；这一依赖方向已基本建立。上述差距集中在仍保留的旧入口。

## 不能一概称为未解耦的项目

| 类型 | 现状与处理 |
|---|---|
| 纯目录布局 | `platform.py` / `store.py` 与目标 `app.py` / `storage.py` 名称不同，tests 未按目标分组，examples 尚在顶层，Demo 平铺与中文目录仍存在；单凭这些不能认定业务越界。是否迁移取决于职责及引用是否随之收敛，不建立空目标目录 |
| 非 Demo 功能完善 | 角色端仲裁流程、更多异常恢复和管理员业务助手完整体验等，需按开发计划逐项实现/验收；例如已存在 `adapters/arbitration.py` 的原件验证/读取接口，不能等同角色流程接线完成。这属于第五阶段功能工作，不靠归档完成 |
| 网页体验 | 布局、完整交互和并发活跃网络的验证属于第四阶段；已有工作台和观察投影保留，不以旧页面数量推断新 UI 完成度 |
| 官方服务质量 | 领域资源/公示与单项履约不等于所有官方服务质量通过，属于第六阶段逐项验证 |
| 服务器与 GitCode | 完整默认 Linux/systemd 安装、升级、权限、启停、恢复和 GitCode 同步属于第七阶段；工作区部署代码、Windows检查或独立HTTP/WS证据均不能替代服务器实机验收 |

## 后续开发顺序

1. 第四阶段沿现有新工作台完善 UI，查询继续调用授权观察投影；避免为旧上报投影新建展示兼容层。
2. 第五阶段先迁移仍使用旧执行器的实验、smoke 和回归覆盖，再按状态所有权收敛 SDK、核心 market/Platform 和旧通知路径。每次切换同时处理包入口、资源、配置、测试及恢复，不仅移动文件。
3. 第六阶段使用同一 SDK/宿主与独立官方资源、工具验证服务质量；固定演示数据归场景，官方参与方不增加专属执行引擎。
4. 第七阶段统一部署所需锁文件和运行单元，完成实机部署、升级及恢复后退出旧配置/单位，并同步 GitCode。

目录清洁不能替代以上收敛。任一旧实现只有在调用、构建、部署及必要验证全部切换后，才满足整组移入历史备份的条件；运行数据、私钥及未知业务结果留在原权威位置核对。
