# 验证与诊断

修复故障、选择测试或交付时阅读。

1. 先定位真实失败边界：用户/服务配置不足，设计矛盾，还是代码违反设计。超时先查持久作业及工具检查点，失败用例名不等于实际失败阶段。保存输入、稳定标识及真实回执；不在日志暴露密钥。
2. 配置问题修配置并明确引导；设计问题先改唯一职责页；代码问题在所属模块修复。不要用延长等待、救援提示或宽松验收掩盖原因。
3. 新测试覆盖有价值的不变量或已复现故障：重传、重启、未知效果、并发、权限/期限变化。在准备、提交、返回边界注入故障，同时核对权威数据和原始回执；状态探测也可能短暂持锁，须检查探测与实际工作者同时争锁的路径。沿用原覆盖，不以改断言迁就错误行为。
4. 桩测试证明确定性规则；真实九问、原生确认、网页可见性、邮件及视频分别需要实际证据。读脚本和模型的成功报告不证明已执行，须核原调用、真实实例及业务状态；后台completed或安装清单不证明用户已看到或已接受。 生命周期验证须并发取消观察方与停止服务，区分停止回执与原执行写入者释放：用认证实例和实际OS锁核对；IPC消失、旧PID或等待超时不能单独证明退出，不能因观察超时重启仍存活的任务。 排空还须验证活动任务能够完成原授权工具，且新任务、已结束及失去许可的上下文仍被拒绝。
5. 交付核对设计验收、包安装独立性、公开端到端和本轮改动范围；检查实际安装包清单，防止旧缓存把已删除模块带回。报告实际通过及缺口，不能把旧视频或旧验收当作新实现的证明。

本仓生成并由Git跟踪的摘要文本，须在计算摘要前固定编码与换行，并核对暂存或克隆blob的实际字节；工作区校验不能代替发布快照校验。外部固定内容按来源清单保持原始字节。

检查层级遵守根 AGENTS.md；先按变更涉及的模块与不变量选择测试路径或 nodeid，不把每轮修改自动升级为整仓验收。耗时异常时核对原报告的当前用例、阶段日志与真实进程，区分慢测试、失败和未退出；有持续用例推进才能证明仍在执行，CPU增长本身不能排除忙循环。依据慢测试统计优化重复准备或无效等待，不能凭猜测削减覆盖。

配置生成验收由真实模型读取实际能力后自行起草，不在测试驱动中预填最终Schema掩盖能力声明缺口；先核对预览与工具原回执，再验证业务结果。格式校验须用反例确认对应校验器实际启用，不能因第三方库接受format声明就认定已检查。获准使用子智能体时，按独立文件和状态所有者分工，源码冻结后再跑共享真实链路；复用未变输入的报告，避免多个执行者重复构建、安装或验收同一业务。

真实业务仅在已授权的隔离场景运行，重拍前核对既成效果，不能为录制重复收费或发邀请。静态网页修改后运行`tools/stamp_static.py`更新内容摘要；页面验收同时核实际加载资源，避免旧缓存造成误判。
