# 验证与诊断

修复故障、选择测试或交付时阅读。

1. 先定位真实失败边界：用户/服务配置不足，设计矛盾，还是代码违反设计。保存输入、稳定标识及真实回执；不在日志暴露密钥。
2. 配置问题修配置并明确引导；设计问题先改唯一职责页；代码问题在所属模块修复。不要用延长等待、救援提示或宽松验收掩盖原因。
3. 新测试覆盖有价值的不变量或已复现故障：重传、重启、未知效果、并发、权限/期限变化。在准备、提交、返回边界注入故障，同时核对权威数据和原始回执。沿用原覆盖，不以改断言迁就错误行为。
4. 桩测试证明确定性规则；真实九问、原生确认、网页可见性、邮件及视频分别需要实际证据。读脚本和模型的成功报告不证明已执行，须核原调用、真实实例及业务状态；后台completed或安装清单不证明用户已看到或已接受。
5. 交付核对设计验收、包安装独立性、公开端到端和本轮改动范围；检查实际安装包清单，防止旧缓存把已删除模块带回。报告实际通过及缺口，不能把旧视频或旧验收当作新实现的证明。

定向检查用于开发循环；完整检查通过后，只有新改动、失败或未解决问题才扩大或重跑验证。真实业务仅在已授权的隔离场景运行，重拍前核对既成效果，不能为录制重复收费或发邀请。 静态网页修改后运行`tools/stamp_static.py`更新内容摘要；页面验收同时核实际加载资源，避免旧缓存造成误判。
