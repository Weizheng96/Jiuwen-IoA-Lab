# 按设计开发

先读根 AGENTS.md、设计索引和[开发计划](../../../设计/工程/实施资料/开发计划.md)，按本次需求读取架构、流程、组件、接入及验收职责页。职责页是规范；工程实施资料、旧代码与已有测试分别说明事实和当前行为。

## 工作顺序

1. 核对工作区、已提交基线及远端；保留在途业务和用户已有改动。遵守仓库及用户指定的分支约定，大改先保存回退检查点，以可验证的功能闭环提交。
2. 将需求映射到设计规则、代码所有者和验证证据。规则缺失、矛盾或无法执行时，先用 design 技能修正职责页、版本及历史，再写实现；实际差距记开发计划。
3. 按明确依赖和状态归属实现，复用 A2C/AP2；迁移资源、安装入口和检查工具时同步更新引用。完成替换后移除重复主流程，保留既有业务可恢复性。
4. 用公开接口验证输入、结果和异常恢复，核对数据及真实回执；通过检查后才更新产物 VERSION、开发计划并提交推送。

## 固定检查

使用项目 Python 执行 `python .agents/skills/develop/scripts/check.py`，默认只检查设计版本与文档链接；`--tests <测试路径或nodeid...>` 增加指定范围的 pytest；`--changed-from <已提交基线>` 复现 CI 基线到 HEAD 的快速路径范围；`--full` 显式执行四项完整检查。何时使用各层级以根 AGENTS.md 为准。

脚本实时显示输出，在 `temp/checks/` 保存各阶段日志、`report.json` 及 pytest 逐项耗时 XML；可用 `--report-dir <新目录>` 指定记录位置。先看原报告中的阶段、用例及退出码，不因长时间无最终摘要重新启动检查。脚本不修改版本或 Git。

用户反馈中的通用经验合并进对应参考页；产品规则归设计，场景专属配置归示例或 Demo，不将问题逐条堆入本技能。
