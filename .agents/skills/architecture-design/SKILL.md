# 架构设计与闭环审查

以仓库 `设计/README.md` 为规范入口，先读 AGENTS.md 和所涉职责页。技能提供方法，不定义另一套平台规则；业务参数、状态和接口以设计正文为准。

## 从完整行为建立方案

1. 从用户目的提取参与方、输入、成功结果、授权边界和不做的范围。分别列明已决定、可自行决定和必须向用户确认的事项。
2. 沿一次真实业务追踪：发起 → 定位对方 → 接纳 → 执行 → 返回 → 继续/结束。不要先按现有文件名堆模块；发现职责混杂时重新确定边界。
3. 对每种持久状态指定一个权威所有者，区分原件、镜像和观察投影。跨进程动作列明事务边界；“两端都检查”不能代替并发竞争的裁决规则。
4. 将交互方式、公共基础能力、宿主适配和业务示例分开；角色共用基础实现，场景通过数据及工具配置接入。只抽取已有共同职责，不预建通用工作流引擎。
5. 给主流程明确每一步的前提、请求、持久结果和下一步条件，再把异常放回同一生命周期。不能用“支持重试/恢复”一句话代替行为定义。

## 必查的跨端问题

| 检查对象 | 需要回答 |
|---|---|
| 标识 | 谁生成、何时持久化、谁需要知道、怎样回传、丢失怎样恢复？哪些标识不同，不能混作幂等键？ |
| 首请求 | 尚无业务 ID 时怎样关联？建立前拒绝如何退出等待？同源重复建立或建立与关闭竞争谁决定？ |
| 后续内容 | SDK 如何自动带关联？怎样核对双方/类型/修订？正常回复会不会被当成新请求？ |
| 结束 | 关闭阻止什么？已开始动作、迟到结果、查询和新请求分别如何处理？未成约失败与已成约终态是否不同？ |
| 回执 | 网络受理、持久送达、获准执行和业务成功是否分开？每种回执在落库前后哪一刻发送？ |
| 时间 | 消息 TTL、会话截止、授权期限、签名新鲜度和合同期限分别由谁检查？不能用一个超时覆盖所有含义。 |
| 容量 | 限制线程、模型轮次还是未结束承诺？预留、收费和签署之间是否会竞争？有效报价何时才可释放？ |
| 副作用 | 先存稳定操作键还是先调用？结果未知如何查原结果？不能将超时等同未付款/未发信。 |
| 恢复 | 断线、进程退出、重启、换设备和数据清理分别丢什么？旧连接会不会继续写？活跃业务是否被普通保留期清理？ |
| 授权 | 模型输出不能自证用户同意；撤权对未开始、进行中和已发生动作各有什么效果？ |
| 可用性 | 普通用户是否需要手写协议/Schema？能否由助手起草、SDK检查、展示摘要后确认？ |

发现问题时维护临时问题表：场景、矛盾、影响、统一解决规则、规则归属、验证方式。优先修正标识、生命周期或权威状态等根因，再删除不再需要的分支；不要每个故障加一个兼容入口。

对重要边界做成对推演：动作前/后断线、写入前/后崩溃、ACK 丢失、同请求重传、同键异内容、双实例、关闭与开始并发、费用未知。与实现相关的事实先查代码和锁定依赖的公开契约；不要凭常识宣称宿主支持恢复或原生网页审批。

## 术语与配置设计

- 用角色、行为、对象、状态四类组织术语，同一概念只保留一个正式名称；界面词和代码字段在术语表建立映射，不混作别名。
- 术语必须说明用途，例如“收信规则”是完整本地配置、“收信接口”是对外声明；避免无实际边界的新名词。
- Agent 流程写出选择条件、所需数据、SDK 操作、成功/失败回执与下一步；标识由 SDK 关联，不要求模型手抄。
- 自然语言配置采用起草 → 无副作用检查 → 摘要确认 → 幂等发布；生成配置不等于授权执行，公开声明与私有处理步骤分开。
- 示例仅用于解释，不把某个邮箱、服务名、数量或业务工具固化进通用机制。

## 落盘与验证

设计正文只写最终现行规范；文档职责和阅读路径由设计入口维护。历史、问题表、取舍和变更原因放 `设计/变更/`；实现差距放开发计划，实测结果放证据记录。

改设计先更新唯一版本和变更索引。未开发的产物不能随设计一起升版。同步 AGENTS、README、维护脚本与链接，但不以文档任务为由改业务代码或运行真实付费/通知动作。

对复杂方案做独立审阅时，提供用户需求和最终稿，要求审阅者指出无法贯通的流程，不先告知期望结论。把有价值的问题纳入同一问题表，逐项关闭；仍依赖宿主能力验证的项写明验证门槛，不表述为已实现。

结束前检查：规范无自相矛盾、术语可查、每条问题有归属、历史与现状分离、版本与链接检查通过。遵守仓库要求完成回归、提交、标签与远端核验；报告设计范围和实现差距。
