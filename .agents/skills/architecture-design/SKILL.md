# 设计文档编辑参考

先读仓库 `AGENTS.md` 和 `设计/README.md`。本技能总结用户反馈形成的编辑经验；产品规则以设计正文为准，维护命令按 AGENTS.md 执行。

## 组织与表达

- 按读者问题分层：整体架构讲目标与边界，流程讲参与方顺序，组件讲数据和规则，接入讲 SDK/技能契约，界面讲可见内容。拆开混合职责，不只移动文件。
- 一条规则只在一处写全，其他页面引用。整体架构留在设计根目录，其余按职责分目录；一个稳定主题一篇，不为每次需求新增补充页。
- 术语说明用途和边界，并映射代码标识。使用具体产品名称，区分接入技能、业务技能与 Codex 开发技能；避免单独用“Skill”“服务端”指代不同对象。
- 正文用职责表、步骤表和必要时序图，统一风格并保持简短。历史与取舍进 `设计/变更/`，实现差距进开发计划，实际结果进验证记录。

## 方案检查

- 从一次完整使用倒推模块：谁发起、如何找到对方、如何接纳和执行、如何返回、如何继续及结束。不要按旧代码堆模块或用异常补丁拼流程。
- 每个持久状态明确权威所有者。对标识检查生成、保存、回传、后续携带与丢失恢复；对副作用检查授权、幂等和结果未知。
- 推演关键竞争：重复消息、双方重启、关闭与开始、容量与付款。区分送达和成功、接单容量和模型并发、消息期限和合同期限。
- 两角色 SDK 共用基础能力，角色职责分开；通用流程留在接入技能，人物、服务和业务工具放场景配置。不要为场景改宿主源码或固化推荐结果。
- 让助手辅助普通用户配置：自然语言起草、程序校验、摘要确认、发布；模型生成的内容不等于用户授权。

交付前检查用户需求能贯通流程、各规则有唯一归属、示例不反向限定通用设计。尚需宿主验证的能力明确列为实施门槛，不能宣称已支持。后续反馈只补充会改变编辑决策的经验，合并同类项，不积累逐次复盘或业务参数。
