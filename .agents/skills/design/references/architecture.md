# 架构审查

修改模块边界、接口职责或完整流程时阅读。

先按本次影响范围列出四项：受影响业务职责与规则页；规则、数据和状态的唯一 owner；公共接口的输入、结果、拒绝与恢复契约；从发起到终态及恢复的调用闭环。小改可用现有任务说明中的短表或文字，不要求另建冗长架构文档。先核整体关系，再细化各模块，不能将多个局部方案拼接后才寻找数据权威。

| 目标 | 审查要点 |
|---|---|
| 高内聚 | 按业务职责划模块，同一规则、数据、状态和不变量只有一个权威 owner；副本与观察投影分开，不重复维护权威或状态机 |
| 低耦合 | 跨模块仅走明确公共接口或查询，不直接读写对方私有表、文件或依赖内部实现；说明依赖方向，避免循环及上层细节侵入基础层 |
| 简洁扩展 | 共享能力归真实所属组件，行业差异归业务资产，OS差异归适配器；通用抽象以已存在复用需求为依据。内部开发直接采用现行契约，不为当前修复、旧接口或假想扩展增加旁路、兼容链、空接口或重复引擎 |
| 项目结构 | 同时确定目录、进程、依赖和交付边界；通用执行、宿主适配、业务配置与演示场景分开，不以源码相邻路径作为安装运行契约 |
| 完整流程 | 从发起、发现、接纳、执行、返回到继续/结束逐步贯通；每步写明前提、持久结果和推进条件，不按旧代码堆模块 |
| 标识与状态 | 核对标识生成、保存、回传、后续关联和丢失恢复；区分送达与成功、接单容量与模型并发、消息期限与合同期限 |
| 证据可核验 | 内部取证与对外视图分开；签名须绑定客户端能重算的公开摘要，不能以隐藏凭据为由只比较不可重算的摘要字符串 |
| 既有终态 | 后续复核、补录或恢复先核原所有者的最新合法终态；明确新记录如何表达而不覆盖原事实、重复计数或释放 |
| 恢复与保留 | 联合核对标识、游标、幂等记录与保留期；推演部分记录仍活跃、其余已清理的情况，不能只分别验证写入和删除 |
| 异常收敛 | 推演重传、双方重启、关闭与开始、容量与付款等关键竞争；外部效果未知先查原操作，不自动重做 |
| 授权可用性 | 助手可起草配置，程序校验后由用户确认；生成内容不是授权，场景输入不能改变工具权限 |

发现矛盾先修正数据归属、生命周期或接口边界，再同步相关流程；避免逐个故障加兼容分支。通用流程留在产品接入技能，场景配置与宿主适配独立，不能为单一演示改宿主或固化推荐结果。

实现验收回到上述四项，验证公共正常、拒绝和恢复路径及依赖方影响，并检查实际导入、调用与持久化读写没有跨层耦合或重复状态。边界改变先遵循设计流程；正确规范不为实现错误改写。
