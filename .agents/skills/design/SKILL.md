# 设计文档

[设计索引](../../../设计/README.md)是唯一现行规范。只读本次改动涉及的职责页及其链接的唯一归属页；实施事实归工程实施资料，差距只归[开发计划](../../../设计/工程/实施资料/开发计划.md)。

## 先判断改动类型

问一句：这句话变了之后，代码应有的行为要跟着变吗？

| 类型 | 判据 | 做法 |
|---|---|---|
| 不变量变化 | 要变。状态或数据的唯一所有者、授权/付款/合同边界、字段含义、流程顺序、“必须/不得”条款 | 先给初始方案并在开发计划标开发中；改唯一职责页与术语；同一提交递增设计 VERSION 第三位、变更表登记一行、打 design 标签；再交 develop 实现 |
| 事实性修正 | 不变。数量、路径、命令名、包名、目录树、链接、错别字，以及其他只是追平代码现状的描述 | 随代码一起改，或攒到一次收口；不升版、不建变更详情。收口时一次升版并在变更表登记一行“同步事实” |

实现偏离正确设计时不为 bug 改规范；只在开发计划写修复方案并精确标“开发中，与当前设计有偏离”。

## 编写

1. 一条规则只在一个职责页写全，其他页面链接；新页面列入设计索引表。
2. 职责页只写现行规范，主体用表格，一行一条不变量；历史与取舍进 `设计/变更/`，操作事实进 `设计/工程/实施资料/`。
3. 完成后把最新完整方案收回职责页，删除开发计划里已完成的进展项，不叠补丁说明。
4. 边界、接口或完整流程变化时按[架构审查](references/architecture.md)列受影响职责、唯一 owner、公共契约和调用闭环；小改只核影响范围。
